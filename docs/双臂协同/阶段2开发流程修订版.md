## 2. M2.2：Controllers YAML 双份（1h）

### 2.1 目的

`ros2_control` 需要每个 controller 对应到具体 joint 名。M2.1 后 joint 名是 `left_j1..j6` / `right_j1..j6`，controllers.yaml 里的 `joints: [j1, ...]` 必须跟着改。

### 2.2 产出

在 `s622_moveit_config/config/`：

* `left_arm_controllers.yaml` — joint 全部 `left_` 前缀，controller 名 `left_arm_controller`, `left_hand_controller`, `joint_state_broadcaster`（后者不加前缀，因为每个 controller_manager 只需要一个 JSB）
* `right_arm_controllers.yaml` — 同理
* 保留原 `ros2_controllers.yaml` 用于单臂 M1.7 兼容性

### 2.3 关键设计

* **每个 controller_manager 独立命名空间**（`/left`, `/right`），所以 controller 名字加不加 prefix 都可以（namespace 已经隔离），但为了日志可读**建议加**：`left_arm_controller` 而不是 `arm_controller`
* **PID 增益初期直接复制原 yaml**，双臂启动后如果发现 left/right 有不对称问题（比如面对面导致重力方向不同），再针对性调整

### 2.4 验收

**只跑单 controller_manager 测试**（不需要完整双臂环境）：

```bash
# 手工用 left 参数启一次
ros2 launch <临时 launch> arm_prefix:=left \
    controllers_yaml:=$(ros2 pkg prefix s622_moveit_config)/share/s622_moveit_config/config/left_arm_controllers.yaml
    
ros2 control list_controllers -c /left/controller_manager
# 期望看到 left_arm_controller / left_hand_controller / joint_state_broadcaster

ros2 topic echo /left/joint_states --once
# 期望看到 left_j1..j6 + left_finger*_joint
```

**如果没时间做单独验证，M2.2 可以直接进 M2.4 集成测试**。

## 3. M2.3：MoveIt 双 group 配置（3-4h）

### 3.1 目的

创建"合并双臂描述"给 MoveIt 用。move_group 需要在同一个 `robot_description` 里看到两臂，才能：

* 检测两臂之间的 self-collision（阶段 2 关键需求）
* 提供两个 planning group 分别规划
* 未来支持双臂协同 planning group（阶段 3 预留）

### 3.2 产出

在 `s622_moveit_config/config/`：

* `dual_arm.urdf.xacro` — 顶层 xacro，include 两次单臂 xacro，各自 prefix
* `dual_arm.srdf` — SRDF，定义 4 个 planning group + collision 白名单
* `kinematics.yaml` — 两个 group 各自的 fairino_ik plugin 配置
* `moveit_controllers.yaml` — 告诉 MoveIt 通过 `/left/left_arm_controller` 和 `/right/right_arm_controller` 执行 trajectory
* `joint_limits.yaml` — 双臂 joint limits（复制原有的，key 前缀化）
* `initial_positions.yaml` 或 `left_initial_positions.yaml` + `right_initial_positions.yaml` — 初始关节角

### 3.3 关键设计要点

**dual_arm.urdf.xacro 结构**：

```
world (根)
├── table (可选,如果想让 MoveIt collision 桌子从 URDF 出而不是 planning_scene_service)
├── (fixed joint) → left_base_link  @ (0.35, 0, 0), yaw=π
│   └── left_arm 全套 link
└── (fixed joint) → right_base_link @ (-0.35, 0, 0), yaw=0
    └── right_arm 全套 link
```

**重要**：合并 URDF 里**不 include camera**，也**不 include ros2_control**。原因：

* MoveIt 只需要几何结构做规划，不需要 gazebo plugin
* 相机独立成 standalone URDF（M2.4 里 spawn），MoveIt 不需要知道相机存在
* ros2_control 在 Gazebo 的 URDF 里（M2.4 里 spawn），MoveIt 用的这份 URDF 不需要

**SRDF 生成方式**：**手写 + Setup Assistant 微调**

* **手写部分**（30 min）：4 个 group（left_arm, right_arm, left_hand, right_hand）+ 每个 arm 的 end_effector + 手写基础 disable_collisions（每臂内部相邻 link 对）
* **Setup Assistant 微调**（30-60 min）：加载手写 SRDF + dual URDF，让 Setup Assistant 自动跑一遍 sampling-based collision detection，补充非相邻 link 之间的 disable_collisions（比如 `left_shoulder ↔ left_wrist2` 之类）

**kinematics.yaml**：

```yaml
left_arm:
  kinematics_solver: fairino_planning_ros/FairinoIKPlugin
  # 参数从原 fairino 配置继承
  
right_arm:
  kinematics_solver: fairino_planning_ros/FairinoIKPlugin
  # 同上
```

**fairino_ik.dh.* ROS param 是否需要区分左右？** 需要确认。你之前说 fairino 插件从 ROS param 读 DH 参数（key 在 `fairino_ik.dh.*`），这个 key 现在是全局的。双臂用同型号 URDF，DH 参数相同，**全局一份就行**，两个 group 共享读取。

### 3.4 独立验收

**在完成 M2.4 之前就能验证 M2.3**：

```bash
# 只启 MoveIt + RViz (不启 Gazebo)
ros2 launch s622_moveit_config dual_arm_moveit_demo.launch.py

# RViz 里加载 MotionPlanning 插件
# 切换 planning group = left_arm, 拖 marker, 点 Plan, 应能成功
# 切换 planning group = right_arm, 同样测试
# 观察两臂在 world 系下位置正确 (面对面)
```

MoveIt 官方 launch 模板 `demo.launch.py` 有 `fake_controllers`，可以在没有 Gazebo 的情况下验证规划能力。

### 3.5 需要提前决定的事

* **SRDF 是手写 + Setup Assistant，还是全 Setup Assistant？** 我推荐前者（可控性强，手写基础后 Setup Assistant 补 disable_collisions 只需 30 分钟）
* **table 放 dual_arm.urdf.xacro 里还是 planning_scene_service 发？** 我推荐**继续用 planning_scene_service**（M2.0 已工作），MoveIt URDF 里不放桌子，避免和 gazebo/xacro 耦合

## 4. M2.4：完整 Bringup Launch（4-5h）

### 4.1 目的

一个大 launch 文件把双臂完整环境启动。这是阶段 2 最关键、最容易踩坑的一步。

### 4.2 产出

* `s622_bringup/launch/dual_arm_full.launch.py` — 完整启动入口
* 可选：拆成多个 sub-launch（gazebo, controllers, moveit, camera 各自 launch）

### 4.3 需要启动的组件（顺序）

```
1. Gazebo 空 world (只有桌子)
2. 独立相机 (from camera_standalone.urdf.xacro, spawn 到 world 系)
3. Left robot_state_publisher (from robot_gazebo.urdf.xacro, prefix=left_, attach_world=false)
4. Left Gazebo spawn (topic 模式, pose=(0.35, 0, 0), yaw=π)
5. Left controller_manager (namespace=left)
6. Left controller spawners (left_arm_controller, left_hand_controller, joint_state_broadcaster)
7. Right robot_state_publisher (同上 right)
8. Right Gazebo spawn
9. Right controller_manager
10. Right controller spawners
11. Joint state 合并 (subscribe /left/joint_states + /right/joint_states, publish /joint_states)
12. move_group (从 dual_arm.urdf.xacro 加载,单实例)
13. planning_scene_service (共享,发桌子)
14. RViz (可选,方便调试)
```

### 4.4 关键坑（会踩，先列出）

| 坑                                                | 症状                                                                     | 修法                                                                                    |
| ------------------------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| `/tf` 变成 `/left/tf`                             | 双臂 TF 断开，RViz 只显示一臂                                            | 每个 namespaced 节点加 `remappings=[('/tf', '/tf'), ('/tf_static', '/tf_static')]`      |
| `/joint_states` 分开发，move_group 只订阅其中一个 | move_group 认为一半 joint 未知，规划失败                                 | 加 joint_state_publisher 合并（或用 remap）                                             |
| Gazebo spawn 两次冲突，第二次失败                 | 只有一臂出现在 Gazebo                                                    | 确认每次 spawn 用不同 `-name` 和不同 `/robot_description` topic                         |
| Controllers 起来但发不出 joint_states             | joint_state_broadcaster 没起                                             | Controller spawner 顺序：先 JSB，再 arm/hand controller                                 |
| MoveIt 看不到 fairino_ik 加载                     | Plugin 加载失败                                                          | 检查 fairino_planning_ros 在 dual URDF 上下文里能不能定位到 group 的 base_link/tip_link |
| 相机 spawn 但 topic 不出                          | Gazebo 全局 Sensors 插件必须在**主 world plugin** 或**独立相机模型内部** | 独立相机 SDF/URDF 里带 `<plugin>`                                                       |

## 5. M2.5：双 Servo（1-2h）

### 5.1 目的

MoveIt Servo 提供实时笛卡尔 velocity 控制。双臂各自一个 servo_node，各自订阅 twist topic。

### 5.2 产出

* `s622_moveit_config/config/left_servo_config.yaml`
* `s622_moveit_config/config/right_servo_config.yaml`
* Launch 里加两个 servo_node

### 5.3 关键配置字段

```yaml
# left_servo_config.yaml
move_group_name: left_arm
joint_topic: /joint_states            # 全局(经合并后)
command_out_topic: /left/left_arm_controller/joint_trajectory
planning_frame: world
ee_frame_name: left_grasp_frame
robot_link_command_frame: world       # 或 left_grasp_frame,看 M1.7 用的哪个
# ... 其他 (velocity limits, singularity threshold) 从 M1.7 复制
```

### 5.4 关键坑

* **`joint_topic` 用全局 `/joint_states` 还是 `/left/joint_states`？** 服务只需要自己 group 的 joint 状态，用 `/joint_states`（合并后）能省一个订阅，但更稳的做法是订阅 `/left/joint_states`
* **`command_out_topic` 一定要对到 controller 的输入**：M2.2 里 `left_arm_controller` 订阅的是 `/left/left_arm_controller/joint_trajectory`（默认 remapping）

### 5.5 验收

```bash
ros2 service call /left/servo_node/start_servo std_srvs/srv/Trigger
ros2 topic pub /left/servo_node/delta_twist_cmds geometry_msgs/msg/TwistStamped \
  "{header: {frame_id: world}, twist: {linear: {z: 0.05}}}"
# left 臂应该慢慢上升

# 检查是否驱动了 right
# right 应该完全静止
```

## 6. M2.6：arm_actions 双实例化（2h）

### 6.1 目的

M1.7 的 `move_to_pose_server`, `visual_align_server`, `gripper_service`, `servo_lifecycle_manager` 都是单臂的。需要参数化 `arm_prefix`，能同时启两份（`/left/*` 和 `/right/*`）。

### 6.2 产出

* 参数化 `s622_arm_actions/launch/arm_actions.launch.py`（加 `arm_prefix` / `move_group_name` / `end_effector` 参数）
* `s622_arm_actions/config/left_arm_config.yaml`（named poses 可能左右不同）
* `s622_arm_actions/config/right_arm_config.yaml`
* 保留 `arm_config.yaml` 单臂兼容

### 6.3 需要检查的代码点

需要过一遍每个 server 的 Python 代码，看有没有硬编码：

* `joint_names = ['j1', 'j2', ...]` → 应该通过参数注入前缀
* `end_effector = 'grasp_frame'` → 参数注入
* `base_link = 'base_link'` → 改成 `world`
* Topic/action/service 名 → 依赖 `namespace` 自动前缀化

大部分应该已经参数化（M1.x 期间应该已经能通过参数配置了）。但双臂 base_link 从 `base_link` 变成 `world`，某些代码里如果硬编码了 `base_link`，需要改。

### 6.4 planning_scene_service 特殊处理

`planning_scene_service` 是**全局单实例**，不加 namespace：

```
/planning_scene_service      (单实例,共享)
├── touch_links 参数: [left_finger1, left_finger2, left_grasp_frame,
                       right_finger1, right_finger2, right_grasp_frame]
├── base_link: world
└── table_size, table_center 参数
```

Attach/Detach service 的 caller（BT 节点）需要传 arm_prefix，让 planning_scene_service 知道 attach 到哪个 EE。这是 M2.7 BT 层的事。

### 6.5 验收

```bash

ros2 action list | grep move_to_pose
# /left/move_to_pose_action
# /right/move_to_pose_action

# 直接发个 goal 到 left
```

## 7. M2.7：BT 双臂支持 + Left 独立跑通 pick-place（2-3h）

### 7.1 目的

BT 节点（C++）里 action client 需要通过 `arm_prefix` 参数指定要连的 server。left 臂在双臂环境下能独立跑通完整 pick-place。

### 7.2 产出

* `s622_bt_manager/src/*_nodes.cpp` 加 `arm_prefix` 支持（约 8-10 个节点要过一遍）
* `pick_place_left_tree.xml`（或复用 `pick_place_with_recovery_tree.xml` 但通过 BT 参数注入 prefix）
* `s622_bt_manager/launch/left_arm_bt.launch.py`
* `s622_bt_manager/config/left_pick_place_poses.yaml`（place 位置在 left 臂可达空间内）

### 7.3 BT 节点改造策略

**做法 A（推荐）**：BT executor 通过 ROS 参数注入前缀

```
bt_executor_node 参数:
- arm_prefix: "left"  

节点内部:
- action client 名从 "move_to_pose_action" 变成 arm_prefix + "/move_to_pose_action"
```

**做法 B**：每个 BT XML 节点属性里显式写完整 action 名

```xml
<MoveToPose action_name="/left/move_to_pose_action" .../>
```

**推荐 A**，一个参数搞定，所有 BT 树都能复用。

### 7.4 需要过一遍的 BT 节点（估计）

| 节点                   | 用途              | 是否需要 arm_prefix        |
| ---------------------- | ----------------- | -------------------------- |
| MoveToPose             | 关节/位姿规划     | 是                         |
| VisualAlign            | Servo 笛卡尔控制  | 是                         |
| SetGripper             | 手指开合          | 是                         |
| VerifyGrasp            | 检查 finger joint | 是                         |
| DetectObject           | YOLO 检测         | 否（相机全局）             |
| GenerateGraspCandidate | 反投影 + 姿态计算 | 是（EE 姿态相关）          |
| GeneratePlaceCandidate | Place 位置        | 是                         |

| AlignLockCheck         | 检查 pixel        | 否                         |

| DetachObject           | PlanningScene     | 是                         |
| StopServo              | Servo lifecycle   | 是                         |

### 7.5 验收

**关键验收目标**：left 臂在双臂环境跑通一次 pick-place。

```bash
ros2 launch s622_bringup dual_arm_full.launch.py &
sleep 15

ros2 launch s622_bt_manager left_arm_bt.launch.py \
  tree_file:=pick_place_with_recovery_tree.xml
sleep 3

ros2 topic pub /left/bt_trigger std_msgs/msg/Bool "data: true" --once
```

期望：

* Left 臂完成 pick-place 完整流程
* Right 臂全程静止在初始位置
* MoveIt 规划路径**避开 right 臂**（关键，验证双臂 collision 生效）
* 平均单次 4-8 分钟（M1.7 水平，允许略慢）

**可接受的降级**：3 次试 2 次成功（M1.7 是 7/10，双臂环境下 collision 检查更复杂，成功率略降是正常的）

### 7.6 Right 臂静止策略

**M2.7 里 right 臂不启动 BT，但需要保证 right 臂物理上稳定**。做法：

* Right 臂的 `initial_positions` 设为一个安全 pose（比如收缩姿态）
* Right controller 启动，joint_trajectory_controller 会 hold 住不动

不需要 right 的 arm_actions 或 BT 参与 M2.7。

## 8. M2.8：Handover 候选点可达性验证（1-2h）

### 8.1 目的

阶段 2 验收标准里"两臂工作空间存在交集"需要实测。定义 3 个 handover 候选点，两臂都能到达。

### 8.2 候选点建议

在 world 系下：

| 名字     | xyz          | rpy       | 说明                   |
| -------- | ------------ | --------- | ---------------------- |
| **high** | (0, 0, 0.30) | (π, 0, 0) | 桌面上方 30cm，EE 朝下 |
| **mid**  | (0, 0, 0.20) | (π, 0, 0) | 桌面上方 20cm          |
| **low**  | (0, 0, 0.10) | (π, 0, 0) | 桌面上方 10cm          |

三个高度试探哪个最好用于 handover。X/Y 都是 0（正中心），两臂距离都是 0.35m。

### 8.3 产出

* `handover_reachability_test_tree.xml` — 顺序让 left 到达 3 个候选点、回 home，再让 right 到达 3 个候选点
* `experiments/results/m28_handover_reachability.md` — 记录哪些点可达、耗时、EE 到位精度
* （可选）RViz 截图，直观展示两臂工作空间交集

### 8.4 测试树结构

```
Sequence
├── MoveToPose named=home (left)
├── MoveToPose target=high (left) → 记录耗时/成功
├── MoveToPose named=home (left)
├── MoveToPose target=mid (left)
├── MoveToPose named=home (left)  
├── MoveToPose target=low (left)
├── MoveToPose named=home (left)
├── MoveToPose named=home (right)
├── MoveToPose target=high (right)
├── ...
```

### 8.5 验收标准

* **3 个候选点，两臂都能到达 = 通过**
* 如果 mid 和 high 到达但 low 不到（够不到），也算通过，标注 low 不可达

## 10. 关键风险 & 预防

| 风险                                             | 影响                             | 预防措施                                                                                                     |
| ------------------------------------------------ | -------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **`/tf` 命名空间被前缀化**                       | RViz 只显示一臂，MoveIt 规划失败 | 每个 namespaced 节点显式 `remappings=[('/tf', '/tf'), ...]`                                                  |
| **两臂 URDF 里都有 `world` link**                | dual URDF 生成时 root 冲突       | M2.1 已解决（`attach_world:=false`）                                                                         |
| **fairino_ik plugin 对 left/right group 不识别** | IK 失败                          | M2.3 完成后先做 kinematics 单独测试（`ros2 run moveit_ros_planning_interface ...`），有问题及时 fallback KDL |
| **两臂 spawn 时相互碰撞**                        | Gazebo 崩或臂飞                  | Initial positions 设置为收拢姿态，两臂 base 距离 0.7m 足够避免初始碰撞                                       |
| **MoveIt collision 认为两臂总是相撞**            | 任何规划都失败                   | M2.3 SRDF 用 Setup Assistant 生成 `disable_collisions`（初始姿态下 always 相碰的 link 对要 disable）         |
| **单 move_group 的 planning 太慢**               | 双臂环境下 pick-place 超时       | 允许 `allowed_planning_time` 加大到 10s；如果还慢，考虑 M2.3 用双 move_group（每臂独立）                     |
| **Camera topic 冲突或 remap 错**                 | YOLO 无输入                      | 相机 spawn 用 `-name shared_camera`，topic 保持 `/camera/*`，YOLO 不改配置                                   |
