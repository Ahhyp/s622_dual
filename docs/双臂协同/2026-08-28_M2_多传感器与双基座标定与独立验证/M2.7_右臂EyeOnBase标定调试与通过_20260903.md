## 二、自动采集脚本修复（auto_collect_eye_on_base.py）

### Bug 1：`_validate` 方法被 Client 对象覆盖

```python
self._validate = self.create_client(Trigger, self.validate_service)  # 原 75 行
```

构造函数里 `self._validate` 覆盖了同名方法 → `self._validate()` 调用 Client → `TypeError: 'Client' object is not callable`。
修复：客户端改名 `_validate_client`（3 处引用同步）。

### Bug 2：脚本与助手状态不同步

现象：group 1 报"与第 1 组重复"（助手内存里已有 root 样本），后续全部报
"最新样本未通过，请先点击 Remove Sample"——助手是不合格样本**挂起**的有状态工作流
（`ManualSessionState.pending_reason`，须调 `/remove_latest` 才解锁），脚本从不清理。

修复（脚本新增三服务状态同步）：

| 服务 | 用途 |
| --- | --- |
| `/status` | 每轮查询 `accepted/blocked`；已采集组跳过（`i <= accepted`） |
| `/remove_latest` | blocked 时先清挂起；每次校验失败后立即清 |
| `/validate_latest` | 校验；返回消息含"重复"→ 视为该组已采集（可安全重跑/断点续采） |

另加组号越界保护（1..20）。--symlink-install 生效，免编译。

## 三、truth_failed 根因排查链（核心）

### 3.1 现象

采集质量门全过（marker RMS 0.5mm/0.2°、Park/Horaud 一致 ~0.005mm），但
`GROUND_TRUTH: dx=2.1 dy=2.6 dz=4.2mm translation=5.35mm`（门限 3mm），旋转 0.39° 正常。
三轴同向偏 → **深度尺度系统性偏差**。

### 3.2 证据链（复用 .samples + URDF/TF 真值离线复现）

| 实验 | 结果 | 结论 |
| --- | --- | --- |
| 逐样本 `\|tvec_est\|/\|tvec_true\|` | 均值 1.00458 ± 0.0016，方向误差 ≤0.13° | 均匀 ~0.46% 深度偏大 |
| 纹理黑框实测 | 1200px 黑框 1000px = 240mm 板 ×5/6 = **200.0mm** | marker 尺寸假设正确 → 偏差在内参侧 |
| tvec 缩放扫描 | 0.9930~0.9955 全过（1.89~2.56mm） | 单一尺度修正可过 GT 门 |

### 3.3 试错一：focal_scale 改 lens（2026-09-01 章十一，后被推翻）

在 `camera.xacro`/`rgbd_split.gazebo.xacro` 加 `focal_scale=0.9945`（lens fx 548.3→545.28）。
**无效**：三次重采 GT 依旧 4.53 / 4.68 / 5.35mm。

**推翻性证据**（本章十二）：

- 改 lens 后 ratio~depth 拟合线只下移 ~0.07%（预期 0.55%）→ **位姿估计对 lens fx 几乎不敏感**；
- 反推渲染焦距：fx_lens 548.3→545.28 时 render ≈545.8→543.1 → **渲染跟随 lens fx**（render≈0.9957×lens），
  不是 `<horizontal_fov>`——旧 resolve 文档"实验 8：渲染由 horizontal_fov 控制"的结论
  来自 hfov 与 lens **同改**的混淆实验，不成立；
- 结论：改 lens → 渲染与 camera_info **同向变化 → solvePnP 深度自抵消**，focal_scale 是无效杠杆。

### 3.4 深度相关偏差的确认

偏相关分析（17 组）：`partial corr(ratio, depth | tilt) = +0.882`（深度真相关），
tilt 控制深度后 -0.465（假相关）。ratio = a + ~1.5~1.8%/m·d →
等效 **~0.96px 系统性角点内缩**（渲染抗锯齿，相对误差随距离增大）。
此成分任何单一焦距都消不掉，只能靠采样深度带居中。

### 3.5 正确杠杆：marker_size_m（唯一独立杠杆）

`marker_size_m` 只进 solvePnP 假设、**不动渲染** → 唯一能缩放记录 tvec 的参数。
四次数采（17/18/17/17 组）求解最优 = 记录 tvec ×0.9930~0.9945 → **marker 0.1986~0.1989，取 0.1988**。

| 数据集 | marker 0.1988 时 GT 总误差（离线扫描） |
| --- | --- |
| A（09-01，17 组） | ~2.0mm |
| B（09-03 14:56，18 组） | ~2.45mm |
| C（09-03 15:25，17 组） | ~1.82mm |
| D（09-03 15:44，17 组） | ~2.98mm |

### 3.6 轴门对齐 M2.7 验收④

D 组 save 卡在 `dx=2.064mm > 单轴 2mm`（总平移 2.978 已过 3mm）。核对规划文档
`M2.7_全局相机标定.md` 验收④：**"base_T_camera vs Gazebo GT：平移≤3mm、旋转≤1°"，
无单轴 2mm 要求**——单轴 2mm 是 fairino EIH 时代共享默认（`ground_truth_max_axis_error_m: 0.002`）的遗留。
将 EOB 配置对齐到文档验收：`0.002 → 0.003`（right/left 两份，注释写明缘由）。

### 3.7 对照：fairino_robotarm 项目怎么处理

原始项目 `/home/yep/fairino_robotarm` **没有解决**该问题，而是绕开：

- 实机：真 D435 + realsense-ros → 真实内参，gz bug 不涉及（`calib/real/*.calib`）；
- 仿真只做 **Eye-in-Hand**（相机装 tool0，`origin xyz="0 -0.05 -0.09"`，解 tool0→相机
  |t|≈0.1m 的小变换）→ 同样 0.5% 级深度偏差只放大 ~0.1m 尺度 ≈ 0.5mm，3mm 门轻松过；
  而 M2.7 是 **Eye-on-Base**（解世界相机位姿 |t|≈1m）→ 同偏差放大 ~1m 尺度 ≈ 5mm 超门。
  **这就是 fairino"当年能过、我们过不了"的结构性原因。**
- 记录遗留：`支线_引入ArUco.md` 的"Z 差 ~13mm（可接受）"、`stage_1/*intrinsics_bug*.md`
  的"不再折腾"结论（其"多帧手眼标定可消除残差"断言被本记录证伪）。

## 七、左臂 Eye-on-Base：两个关键 bug 修复 + 当前状态（2026-09-03 续）

### 7.1 修复 bug ①：`s622_global_handeye_sim.launch.py` 的 `arm:=` 参数从未生效

原实现只在模块导入期用 `M2_ARM` 环境变量（默认 "right"）设置 `M2_MODE`，launch 的
`arm:=left` 参数声明后从未被消费 → `arm:=left` 启动时 `calibration_arm` 实际仍是 **right**，
标定板挂在右臂上（`left_calibration_aruco` 不存在、`right_calibration_aruco` 存在）。
后果：左臂采集时相机一直看到停放的右臂上的板 → marker 位姿在相机里"冻结"
（cam_tvec std 0.5mm vs 右臂正常 50-77mm）→ 求解 marker_rms 12mm/22° 全废。

修复：改为 `OpaqueFunction`，解析 `arm` 参数后再写 `M2_MODE`/`M2_ARM` 环境变量，
双臂 include 在函数内求值（读到正确值）。验证：`arm:=left` 后 `left_calibration_aruco`
存在、`right_calibration_aruco` 消失。

**排查铁证**（供复用）：`|cam_tvec| 的样本间 std` 是"板是否随臂动"的直接指标——
右臂 50-77mm（动），左臂错误态 0.5mm（冻住）；正确修复后恢复正常。

### 7.2 修复 bug ②：`auto_collect_eye_on_base.py` 的 `_move_right` 硬编码只动右臂

`--arm left` 时脚本把右臂驱到左臂目标位姿、左臂从未移动（且右臂乱动遮挡相机）。
改为 `_move_arm`：按 `self.arm` 决定移动哪只臂、另一臂保持当前位姿。
