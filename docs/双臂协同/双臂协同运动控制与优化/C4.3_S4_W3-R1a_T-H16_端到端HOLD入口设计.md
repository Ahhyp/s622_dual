## 0. 结论先行

T-H16 要验的是**执行器 ↔ 控制器的一次真实 HOLD 往返**，而不是再测 `HoldRequester` 的策略。

设计核查后得出三条结论：

1. **入口是“反应式”的，不是执行器主动发起**：执行器在自己的状态机进入 `Hold` 之后才去要求控制器冻结（`executor_node.cpp:162`）。因此「谁先 Hold」在语义上是**执行器先锁存、再要求控制器跟随**，与 C7-A 的「控制器冻结、执行器确认」方向相反但互补。
2. **往返存在两段不可压缩延迟**：控制器状态发布 10 Hz 抽稀（≈104 ms/条）+ 执行器 tick（8 ms）。因此任何“立即确认”的断言都不成立，只能用**事件与 seq 匹配**判定。
3. **正常路径可以在 OFF 生产库上完整跑通**；但「控制器在往返中进入 ERROR」这一分支**在 OFF 构建下无法制造**（注入被 `#ifdef` 隔离），只能标 `UNVERIFIED` 或另行申请 ON 构建。

## 2. 完整往返时序（executor → controller → executor）

设执行器 tick 周期 `Te=8 ms`，控制器控制周期 `Tc=8 ms`，状态发布周期 `Ts≈104 ms`。

| # | 时刻 | 执行者 | 动作 | 可观测证据 |
|---|---|---|---|---|
| 1 | t0 | 控制器 | 某安全判据触发（如 `collision`）⇒ `transport_->hold(..., Controller)` | 下一条状态里 `state=HOLD`、`failure_code=collision`、`hold_origin=controller` |
| 2 | t0+Δ | 控制器 | `publishStatus()` 抽稀命中 ⇒ 发布 | 执行器 `onStatus` 收到 |
| 3 | 下一个 `Te` | 执行器 | `sm_->tick()` 因 `state=HOLD` 进入 `State::Hold` 并锁存 | 执行器日志 `state A -> HOLD` |
| 4 | 同一次 `onTimer` | 执行器 | `driveHoldRequest()` 见 `State::Hold && !open && !confirmed` ⇒ `beginHoldRequest(failureCode)` | 日志 `requesting controller HOLD (seq=N)` |
| 5 | 同一函数 | 执行器 | `needSend()` ⇒ `async_send_request(seq=N)` | 服务端 `onHoldTransport` 被调用 |
| 6 | 服务线程 | 控制器 | `CAS(0→N)` 成功 ⇒ 回 `accepted=true, "hold queued"` | 执行器 `hold_reply_=1` |
| 7 | 下一个 `Tc` | 控制器 | drain：`hold_ok = active && running()`。**此刻已 Hold ⇒ running()=false ⇒ `result=2`**，origin/code **保持不变** | 这是本设计的**关键结论**，见 §3.2 |
| 8 | 之后 | 控制器 | `publishStatus()` 带上 `seq=N, result=2, origin=controller` | 执行器 `onStatus` |
| 9 | 下一个 `Te` | 执行器 | `HoldRequester` 规则②：`result==2 ∧ state==HOLD ∧ origin==controller` ⇒ **Abort `hold_owned_by_controller`** | 执行器日志 `controller HOLD NOT confirmed (hold_owned_by_controller)` |

### 2.1 ★ 由上表推出的两个设计事实

**事实 A（正常路径会走“Abort”而不是“Done”）**：因为执行器是在**自己的状态机已经 Hold**（第 3 步）之后才发请求，而控制器此时已经 `Hold`、`running()` 为假，drain 必然回 `result=2`。若控制器最初的 hold 来自它自己的安全判据（`origin=controller`），`HoldRequester` 会正确地判为 `hold_owned_by_controller` 并 **Abort**。

这不是缺陷，而是 C7-A 语义的**正确结果**：执行器不得冒领控制器的安全归因。但它意味着——

> **T-H16 的“成功路径”不是 `Done`。** 真正的 `Done` 只可能发生在「执行器先 Hold、控制器当时仍 Running」的窗口里（例如执行器因自身相位超时锁存 Hold，而控制器尚未 Hold），此时 drain 才能 `result=1`。

**事实 B（该窗口存在但很窄）**：执行器锁存 Hold 的一个来源是 `status_stale` / `phase_timeout` 等**执行器侧**判据；只要此时控制器状态还是 `RUNNING`，第 7 步就会 `result=1`、`origin=executor`，第 9 步 `Done("frozen_by_executor_request")`。这个窗口**长度约为一个状态发布周期（≈104 ms）**——因为执行器只能通过状态消息得知控制器是否已 Hold。

## 3. ACK seq、请求归因、陈旧状态与 Abort/Done 判据

### 3.1 seq 规则（已实现，`hold_requester.cpp`）

| 规则 | 实现 |
|---|---|
| 严格递增、永不为 0 | `beginHoldRequest`：`next_hold_seq_ = (next==0)?1:next`，随后 `next_hold_seq_++`（`executor_node.cpp:150-152`） |
| 跨 uint32 回绕比较 | `seqAtOrAfter(a,b) = (int32)(a-b) >= 0` |
| 同 seq 重试 | 重发复用 `hold_req_.seq()`，不换号 |
| 只认“不早于我的”回执 | `seqAtOrAfter(ack_seq, seq) && ack_seq != 0` |

### 3.2 归因（origin）判定矩阵

| 控制器 origin | 控制器 state | `result` | 执行器判定 | 是否正确 |
|---|---|---|---|---|
| `executor` | HOLD | 1 | **Done**（L3 成立） | ✅ 我方请求生效 |
| `executor` | HOLD | 2 | **Done**（L4：`result=2` 但 origin 证明已冻结） | ✅ 同 seq 重试的正常分支 |
| `controller` | HOLD | 1 或 2 | **Abort `hold_owned_by_controller`** | ✅ 不冒领安全归因 |
| 任意 | 非 HOLD | 2 | `COMPLETE` ⇒ Done；否则 Abort `not_running:<state>` | ✅ |
| 任意但状态陈旧 | — | — | **Wait**（不判 Done，不判 Abort） | ✅ |
| 无回执且超时耗尽 | — | — | **Abort `hold_ack_timeout`**，永不 Done | ✅ |

### 3.3 陈旧状态

- 判定依据 `obs.status_age_s = now − status.stamp_s`（`executor_node.cpp:180`），阈值 `status_stale_s`（默认 0.1 s）。
- 陈旧样本**完全不参与** Done/Abort 判定，只驱动 `Wait`。理由：旧的 `result=1` 不能证明“现在是冻结的”。
- 边界：`status_age_s` 用的是执行器**收到消息的本地时刻**，不是消息内时间戳（消息里没有发送时刻字段）⇒ 传输抖动会被算进 age。见 §5。

## 4. 失败场景矩阵

| # | 场景 | 触发方式 | 期望行为 | 可证伪点 |
|---|---|---|---|---|
| F1 | 正常：执行器先 Hold，控制器仍 RUNNING | 执行器侧 `status_stale`/`phase_timeout` | `result=1`、origin=executor、`t_traj` 冻结、Done | 若 Done 时 `t_traj` 仍在前进 ⇒ FAIL |
| F2 | 正常：控制器已因安全 Hold，执行器随后请求 | 控制器 `collision` | `result=2`、origin=controller 不变、Abort `hold_owned_by_controller` | 若 origin 被改写为 executor ⇒ FAIL |
| F3 | 控制器在收到请求后进入 ERROR | **OFF 构建无法制造**（注入被隔离） | 状态流中断 ⇒ 陈旧 ⇒ 最终 Abort `hold_ack_timeout` | 若此时判 Done ⇒ FAIL |
| F4 | ACK 丢失（服务回执到、状态未到） | 抑制状态订阅（测试侧） | 超时后同 seq 重发；耗尽 ⇒ Abort `hold_ack_timeout` | 若 Done ⇒ FAIL |
| F5 | 旧 ACK（seq 小于本次） | 注入一条 seq=1 的旧状态 | 不算 L3/L4；继续等 | 若 Done ⇒ FAIL |
| F6 | 旧状态（`result=1` 但 `status_age>0.1`） | 停止发布后再用最后一条 | 只 Wait | 若 Done ⇒ FAIL |
| F7 | 服务不可达 | 控制器未起来 | `service_is_ready()` 为假 ⇒ 不发送、不 Done；耗尽后 Abort | 若静默 Done ⇒ FAIL |
| F8 | busy（上一请求未 drain） | 背靠背两次 | 同 seq 重发；`max_attempts` 耗尽 ⇒ Abort `hold_request_rejected` | 若换 seq 重发 ⇒ FAIL |
| F9 | seq 回绕 | 强制 `next_hold_seq_=0xFFFFFFFF` | `seqAtOrAfter` 正确 | 单测已覆盖（`T_SeqComparisonSurvivesWrap`） |
| F10 | 控制器已 COMPLETE | 轨迹跑完后请求 | `result=2` + `COMPLETE` ⇒ Done | 若 Abort ⇒ FAIL |

## 5. 可真实观测 vs 只能静态证明

### 5.1 可观测（[OBSERVED] 候选）

1. 服务调用与回执（`accepted`、`message` 前缀 `busy`/`hold queued`）。
2. `TransportStatus` 的 `state/failure_code/t_traj/active/committed` 与 C7-A 三元组。
3. 执行器日志中的状态迁移与 `controller HOLD confirmed` / `controller HOLD NOT confirmed (...)`。
4. 执行器产出的 artifacts（`cycles.csv` 等）中的 `t_traj` 序列——**冻结的直接证据**是 `t_traj` 连续多个样本不变。
5. 两进程的 DDS 交互时序（由接收时间戳近似）。

### 5.2 只能静态证明（[PROOF]，不得写成动态 PASS）

1. **drain 与安全层的同拍先后**：`update()` 内 drain（`:745`）在安全层（`:790`）之前 ⇒ 同拍安全事件会把 origin 覆盖为 `controller`。这条**无法从外部稳定构造**，只能读代码顺序 + 记录到 T-H15。
2. **控制器在 `readState()` 失败时不处理请求**：`readState` 失败在 `:691-694` 直接返回，drain 未执行 ⇒ 请求滞留到下一周期或被拒绝。属代码顺序。
3. **`publishStatus` 的 `trylock` 丢拍次数**：丢拍在 RT 线程内部，不对外可见；只能通过“状态间隔出现 2×Ts”间接推断，不能计数。
4. **控制器冻结发生在哪一拍**：状态消息 10 Hz，无法分辨 8 ms 粒度。

### 5.3 不可观测

- 执行器 `async_send_request` 到服务端处理的排队时间（DDS + executor 调度）。
- 真实执行器的位置响应（mock 台架无时间戳语义）。
- 控制器 ERROR 后的进程状态（无 ERROR 状态字段，只能从“状态流停止”推断）。

## 6. 台架隔离设计

| 机制 | 设计 | 理由 |
|---|---|---|
| `ROS_DOMAIN_ID` | 每个用例 `30 + ((pid + counter++) % 50)`，且必须在 `rclcpp::init` **之前**设置 | 同进程多用例复用同一域时，上一用例残留的 `controller_manager` 会应答新用例 |
| 进程组 | 子进程 `::setpgid(0,0)`；TearDown `kill(-pid, SIGINT)` → 4 s → `SIGTERM` → `SIGKILL` | 直接 `kill(pid)` 会漏杀 `ros2_control_node`，导致后续台架起不来 |
| 泄漏断言 | TearDown 后 `pgrep -f ros2_control_node` 必须为空（或与 SetUp 前的基线一致） | 把“临时缓解”变成**可检测**，而不是靠人记住 |
| 目录隔离 | artifacts 与日志写 `/tmp/c43_th16/<case>/`，`ROS_LOG_DIR` 同隔离 | 避免 `~/.ros/log` 权限问题与相互覆盖 |
| 端口/共享内存 | 已知 `RTPS_TRANSPORT_SHM … Permission denied` 属沙箱限制，走 UDP 回退，**不是缺陷** | 不得写进失败原因 |
| 顺序 | 每用例 `stopBench()` → 设 env → `startBench()`（先建订阅/客户端，最后起进程） | `waitFor` 在 `node_` 为空时 `spin_some` 会段错误（T-H17 已验证的坑） |
