## 3. 批次 A｜冻结范围确认与阈值台账

**目的：**先形成适用范围准确、来源明确、不会制造假 PASS 的 YAML。

### A1. 最小范围核对

代码 Agent 在实施前仅执行与 W4 直接相关的只读确认：

1. 检查最新正式规划的 W4 定义、§7 测试矩阵、已批准修订。
2. 查看两项目标文件是否已存在；若存在，先比对，不覆盖现有有效内容。
3. 查找当前仓库中已批准阈值或契约的权威来源。
4. 核对 W2/W3 2026-10-28 收尾和阻断登记，确认哪些项目已有证据、哪些尚 HOLD。
5. 记录当前 `HEAD`、工作树状态与目标文件现有差异。

不重新审核 W0–W3 已经 PASS 的全体用例；仅遇到与 W4 台账直接有关的新增冲突时进行受影响范围核查。

### A2. 台账的数据语义

建议每个适用测试或量化指标至少具有下列**语义**（字段名可按现有仓库规范调整）：

| 语义/参考字段 | 要求 |
|---|---|
| `test_id` | 对应最新正式基线中的测试编号；必要时同一测试下分多个指标 |
| `metric` | 指标名称，避免模糊描述 |
| `unit` | 有量纲的指标填写明确单位；无量纲/事件类可标记不适用 |
| `criterion` | 比较关系、事件断言或判断方法 |
| `threshold` | 已批准的正式值，或显式 `[待标定]` |
| `threshold_status` | 区分 `APPROVED` / `PENDING_CALIBRATION` / `UNAPPROVED` 等 |
| `source` | 正式冻结文件、审批记录或适用来源的准确引用 |
| `evidence_state` | 证据的实际状态，如 `PASS`、`FAIL`、`HOLD`、`UNVERIFIED` |
| `evidence_ref` | 已留存、可定位的证据；缺失则如实声明，不虚构路径 |
| `scope` | 指标和既有证据适用的具体范围 |

**必要的分离原则：**

- 阈值获批准 **≠** 测试已通过。
- 软件测试 PASS **≠** RT 实时性 PASS。
- 历史实验值 **≠** 经批准的正式阈值。
- `[待标定]` **≠** 0、默认合格、已测通过。
- 仅台账结构检查成功 **≠** S4.1 正式 Gate PASS。

以上字段是执行设计建议，不是擅自宣布新的冻结接口。若项目已有经批准的台账结构，优先兼容原结构。

### A3. 数据录入规则

1. **已批准阈值：**照正式批准值和适用范围登记，不改数值，不把草案写成正式值。
2. **待标定项：**保留显式 `[待标定]`。初始规划中出现“建议值 + `[待标定]`”的，不得仅复制建议数字后去除标记。
3. **历史失败：**保留 W2 C3 原跨代 `≤1 ULP` 的 `7656/7656 FAIL`，并区分已批准 D2-B 的适用目的。
4. **环境阻断：**C6、相关 S4-T2/S4-T17 实时验收保持 `HOLD / UNVERIFIED`；不可填入未经执行的性能数值。
5. **有限覆盖：**W3 R1a C4 只记录实际可评估子集的 PASS，不扩展为全样本 PASS。
6. **安全审批：**B-4 P0、D3/D4/D5 保留准确状态；D4 失败码仍 `registered=false`。
7. **缺失证据：**对已丢失的 `/tmp` 原始产物记录“未留存/需定向补证”，不得编造文件路径。
8. **未到阶段的项目：**如 S4-T6/T7 等需要后续 Gazebo/真机条件的用例，可在台账中登记尚未执行，但不能伪称通过。

### A4. 批次 A 完成判据

- 最新正式基线确定的全部 W4 必需项目已映射到台账；
- 阈值、来源、状态、适用范围可以明确区分；
- 所有 `[待标定]` 标记可程序识别；
- 历史 FAIL / HOLD / UNVERIFIED / UNAPPROVED 无越权改写；
- 完成目标 YAML 与简明差异、未决问题说明。

**A 批不要求原生 Linux RT 机器或真实硬件。**

## 4. 批次 B｜自动检查脚本与阴性测试

**目的：**让 W4 台账的最小完备性可以自动判定，同时避免错误制造 Gate PASS。

### B1. 必须满足的原定能力

1. 读取 W4 YAML 并识别适用测试/指标；
2. **列出全部 `[待标定]` 项**（应包含便于定位的编号/指标）；
3. 对**缺少正式基线要求的必需项目**返回非零退出码；
4. 输出可理解的错误信息，支持定位问题。

必需项目集合**不能只从当前 YAML 本身推导**，否则删掉某个测试条目后检查器可能错误认为完整。应以与 YAML 待检查记录相独立的正式要求映射为依据。

### B2. 建议在不扩权前提下完成的最小防错增强

- 检查 YAML 解析错误、关键字段缺失和字段类型错误；
- 检查重复 `test_id` 或重复的测试-指标组合（允许合法的一对多表示）；
- 检查已标为正式批准的阈值是否有必要的批准来源；
- 保证 `[待标定]`、`HOLD`、`UNVERIFIED` 不会被脚本输出成“正式验收 PASS”；
- 对适用单位、判据和证据引用的结构做最小一致性检查。

这些属于防止台账误读所需的有限增强，**不要求新增复杂报表系统或实际证明外部环境验收结果**。

### B3. 退出码与判定语义

| 条件 | 期望结果 |
|---|---|
| 结构合规、必需项目完整 | 退出码 `0`；可同时报告未满足的验收条件 |
| 有 `[待标定]`，但结构与覆盖完整 | 可返回 `0`；必须完整列出待标定项，不能宣称验收 PASS |
| 有 `HOLD`/`UNVERIFIED`，但结构完整 | 可返回 `0`；状态必须原样可见 |
| 必需项目缺失 | **非零退出码** |
| YAML 无法解析、关键结构非法 | **非零退出码** |
| 重复冲突/批准来源结构不合规 | **非零退出码** |

退出码表示**台账软件检查结果**，不表示正式 S4 Gate 状态。具体非零码可由执行方在脚本内稳定定义并记录。

### B4. 定向测试矩阵

| 用例 | 预期 |
|---|---|
| 合法完整台账 | 检查成功 |
| 删除一个必需测试/指标 | 非零退出，准确列出缺项 |
| 重复测试编号或指标键 | 非零退出，说明冲突 |
| 非法 YAML / 字段类型不符 | 非零退出 |
| 已批准阈值缺失必需来源 | 非零退出 |
| 含若干 `[待标定]` | 全部输出，未将其当 PASS |
| 含 `HOLD / UNVERIFIED` | 状态保持不变，不误报 Gate PASS |
| 历史 FAIL 与新批准契约并存 | 两种记录均保留，不自动互相覆盖 |

如某条增强规则会要求改动正式冻结台账契约，先报告，不擅自修订上位标准。

### B5. 批次 B 完成判据

- 脚本可在已有普通软件开发环境中运行；
- 原始必达条件均有可复现测试；
- 最小阴性测试覆盖缺项与错误输入；
- 输出包括明确错误和待标定项目定位；
- 不增加不必要依赖，不修改生产控制逻辑。

- 需要批准新阈值、变更判据或扩大 W4 工作包范围；
- 需要修改生产控制代码、安全契约、D3/D4/D5 或 B-4 规则；
- 需要真实硬件操作；
- 出现实质性新风险，影响已归档历史结论。

普通 YAML 或脚本缺陷、测试失败等可由执行方在原授权范围内修复，不要求每次重新审批。

## 8. 执行轮次与协作方式

| 批次 | 主工作 | 本批次交付 | 下一批次条件 |
|---|---|---|---|
| **A** | W4 基线核对、YAML 台账 | 可检查的 YAML + 覆盖与来源说明 | 无重大范围冲突、无越权填值 |
| **B** | 检查脚本、正向/阴性测试 | Python 脚本 + 可复现实测结果 | 原始必达判据满足，问题已定位 |
| **C** | 集中验证、软件收尾归档 | W4 交付报告 + 遗留阻断状态 | 项目审批人作软件范围关闭判断 |

**角色分工：**

- **项目审批人**：批准新阈值、安全契约、范围变更与后续阶段启动。
- **ChatGPT 技术顾问窗口**：制定并维护 W4 计划、审阅每批执行报告、提出是否进入下一批的建议、撰写具体代码 Agent 执行提示词。
- **DeepSeek/Codex 等代码 Agent**：严格按被授权的单批执行提示词实施、测试并回报证据；不得自行授予下一工作包权限。

本计划书不是“现在一次性执行 A/B/C 全部工作”的命令。执行方在每批完成后提交结果，后续批次由项目协调窗口依据实际情况安排。

## 9. 最终验收和退出标准

W4 软件范围完成至少需要同时满足：

- [ ] 最新正式 W4 必需项目覆盖已确认。
- [ ] `c43_s4_acceptance.yaml` 存在且条目、状态、来源和 `[待标定]` 标记真实准确。
- [ ] `check_acceptance_yaml.py` 能列出**全部** `[待标定]` 项。
- [ ] 删除必需项目时，检查脚本稳定返回**非零**退出码。
- [ ] 最小正向和阴性测试有实际运行结果。
- [ ] 无未授权修改审批状态、生产控制逻辑或安全 Gate。
- [ ] 旧 FAIL、外部 HOLD、RT/真机 UNVERIFIED 和证据留存缺口仍被明确记录。
- [ ] 软件交付记录包含实际路径、命令、退出码、文件差异和遗留阻断。

达成上述条件，可提出 **`W4 SOFTWARE_ONLY COMPLETE`** 建议；正式记录与签署仍按项目现有流程进行。

**W4 完成不自动授权 W5，也不意味着 S4.1 的全量正式 Gate 已经通过。**
