## 1. 目的与不变式

执行器（`dual_arm_transport_executor`）需要请求控制器冻结双臂。今天它只能**自己**停止发命令并观察，无法让控制器主动冻结——已核实的原因是控制器没有冻结入口（`dual_arm_qp_controller.cpp:644-655` 只有 `pending_cmd_ = 2/1/3` 三条：`reset` / `resume` / `abort`）。

**不变式 N1–N7（沿用 Rev.1，本章不变）**

- **N1** `Hold` 是暂停，不是终止；`abort` 与 `hold` 语义不得混用。
- **N2** 请求≠生效：服务返回只证明"请求被接收"。
- **N3** 控制器必须如实报告冻结是**谁**发起的（自身安全层 / 执行器请求）。
- **N4** 执行器**不得无限信任**异步请求；必须有界等待与超时动作。
- **N5** 重复请求必须幂等；**过期/乱序请求不得解除 `Hold`**。
- **N6** `Idle` / `Complete` / `Abort` / `Fault` 状态拒绝新 `hold`，且**不得覆盖**既有 `failure_code`。
- **N7** 不改动 W1 已经验收的 4 条命令分派与其语义，不改 QP 数学、求解器、轨迹计算与冻结基线。

## 4. 接口设计（Rev.2）

### 4.1 新增 `srv/HoldTransport.srv`（7 行）

```
# C4.3 S4 C7-A Rev.2: ask the controller to hold the running transport.
# seq is executor-assigned, strictly increasing, never 0 (0 = no request).
string reason
uint32 seq
---
bool   accepted
string message
```

`accepted` 的语义**仅**为"请求已入槽"（L1），**不**表示已冻结。

### 4.2 `msg/TransportStatus.msg` 追加（+5 行）

```
# ---- C7-A Rev.2: hold-request ack -------------------------------------------
# Echo of the last consumed hold request.  seq==0 -> no ack so far.
uint32 hold_request_seq
uint8  hold_request_result   # 0 none / 1 applied / 2 refused
string hold_origin           # "" / "controller" / "executor"
```

### 4.3 RT 片段（修正版，替换 Rev.1 §4.3）

位置：插在 `const bool transport_active = ...` **之后**、`if (transport_active)` 分支**之前**；**不含任何 `return`**。

```cpp
    // [C7-A Rev.2] Executor HOLD request.  At most one request is in flight (the
    // service handler refuses with "busy" otherwise), so this exchange cannot
    // drop an outstanding request.  No early return: this pass must still write
    // the command and publish the ack, otherwise a refusal would delay its own
    // ack by one whole status period.
    const uint32_t hold_seq = hold_req_seq_.exchange(0, std::memory_order_acq_rel);
    if (hold_seq != 0) {
        const bool ok = transport_active &&
                        transport_->state() == TransportState::Running;
        if (ok) transport_->hold("hold_by_executor", HoldOrigin::Executor);
        hold_ack_.store(packHoldAck(hold_seq, ok ? kAckApplied : kAckRefused),
                        std::memory_order_release);
    }
```

`packHoldAck(seq, result) = (uint64_t(seq) << 32) | uint64_t(result)`（静态内联，3 行）。

**冻结能力不变**：`hold()` 使下一拍 `step()` 走 `out.committed == false` 分支 ⇒ 不累加 `q_cmd_`、只重发上一拍 `q_cmd_`（`dual_arm_qp_controller.cpp:777-786`）、`advance()` 不推进 `t_traj_`（`transport_task.cpp:208-212`）。

### 4.4 origin 下沉到 `TransportTask`（修正 B-3-1）

```cpp
// transport_task.hpp
enum class HoldOrigin : std::uint8_t { None = 0, Controller = 1, Executor = 2 };
// ...
void hold(const char* code, HoldOrigin origin = HoldOrigin::Controller);
HoldOrigin holdOrigin() const { return hold_origin_; }
HoldOrigin hold_origin_ = HoldOrigin::None;
```

```cpp
// transport_task.cpp（改动 3 处）
void TransportTask::hold(const char* code, HoldOrigin origin) {
    state_ = TransportState::Hold;
    failure_code_ = (code != nullptr) ? code : "hold";
    hold_origin_ = origin;                     // +1
}
// start() 与 reset() 各加一行 hold_origin_ = HoldOrigin::None;
```

**为什么这是必需的**：`transport_task.cpp:232` 的拒绝发生在 `TransportTask::step()` 内部，控制器无法在调用点打标记。把 origin 变成任务的属性后，5 个来源全部被覆盖，且控制器侧 0 处标记代码。

`publishStatus()` 追加 4 行：

```cpp
    const std::uint64_t ack = hold_ack_.load(std::memory_order_acquire);
    m.hold_request_seq = static_cast<std::uint32_t>(ack >> 32);
    m.hold_request_result = static_cast<std::uint8_t>(ack & 0xFFu);
    m.hold_origin = transport_ ? holdOriginName(transport_->holdOrigin()) : "";
```

### 4.5 语义表（Rev.2）

| 控制器状态 | 新 `hold` 请求 | 回执 | 既有 `failure_code` | origin |
|---|---|---|---|---|
| `Running` | ✅ 接受，转 `Hold` | `applied` | 改为 `hold_by_executor` | `executor` |
| `Hold`（`collision`） | ❌ 拒绝 | `refused` | **保持 `collision`** | 保持 `controller` |
| `Hold`（`hold_by_executor`） | ❌ 拒绝（已冻结） | `refused` | 保持 | 保持 `executor` |
| `Idle` / `Complete` / `Abort` / `Fault` | ❌ 拒绝 | `refused` | 不变 | 不变 |

**解除 `Hold` 的唯一途径仍是 `~/resume_transport`**（`dual_arm_qp_controller.cpp:650-655` → `resume()`）；`Hold` 期间收到的 `hold` 一律 `refused`，**不会**刷新或延长冻结 —— 因此"过期消息解除 HOLD"在结构上不可能（N5）。

### 4.6 冻结能力证明标准（L1–L5，任务 5）

| 层级 | 命题 | 可观测证据 | 谁必须证明 |
|---|---|---|---|
| **L1** 请求被接收 | 服务返回 `accepted=true` | `HoldTransport` 响应 | 执行器（日志） |
| **L2** 请求被处理并产生确定结果 | 状态里 `hold_request_seq == 我的 seq` 且 `hold_request_result ∈ {1,2}` | `TransportStatus.hold_request_seq/_result` | 执行器轮询 |
| **L3** 控制器进入规定 HOLD 状态 | `TransportStatus.state == "HOLD"` 且 `hold_origin == "executor"` | 状态消息 | 执行器 |
| **L4** 控制输出满足冻结契约 | 连续 ≥10 拍 `q_cmd` 逐位相同、`dq == 0`、`t_traj` 不变 | `TransportStatus.q_cmd/dq/t_traj` | 执行器（窗口观测） |
| **L5** 超时/重复/竞态/拒绝/故障下维持安全 | T-H2…T-H6、T-H10、T-H12、T-H13、T-H14 全绿 | 测试日志 | R1a 验收 |

> **报告规则**：任何证据只能主张其对应层级。`accepted=true` **不得**写成"控制器已冻结"；`state=="HOLD"`（L3）**不得**写成"控制输出已冻结"（L4）。L5 通过**不**代表真实执行器已停机（那是 S4.3 的 B4-5）。

## 7. 并发、实时性与内存模型（Rev.2）

| 关注点 | 结论 |
|---|---|
| RT 线程是否阻塞 | **否**。RT 侧只有 `exchange`(1) + `load`(1) + `store`(1)，全部 lock-free、无分配、无系统调用、无锁 |
| 服务回调是否阻塞 RT | **否**。`create_service` 回调在 executor 线程；内层只做一次 `compare_exchange`，不 `sleep`、不 `wait_for` |
| 是否丢请求 | **否**。槽被占用时服务**同步**回 `busy`，不覆盖；在飞请求数 ≤ 1 |
| 原子性 | `hold_ack_` 为单个 `std::atomic<uint64_t>`；`static_assert(is_always_lock_free)` 在编译期保证 |
| 内存序 | 入槽 `acq_rel`、回执 `release`、发布侧 `acquire` ⇒ 回执先于观测 |
| 与既有分派竞争 | 不复用 `pending_cmd_`（避免与 `resume/abort` 抢单槽），位置在 `applyPendingStart()` 之后 ⇒ 与 `abort` 的先后**确定**（T-H6） |

## 8. Q1 / Q2 / Q3（严格按 Rev.1 原始定义）

### Q1 — `hold_origin` 采用何种类型？

| 原始选项 | 依据 | 安全影响 | 时序 | 兼容性 | 推荐 |
|---|---|---|---|---|---|
| **A `string`** | 与现有 `state`、`failure_code` 同为 `string`（`TransportStatus.msg`），10 Hz、自描述、日志可读 | 无新增风险；**如实披露**：`publishStatus()` 已在 RT 线程内做 string 赋值（`m.state`、`m.failure_code`），本字段不改变该性质 | 无差异（10 Hz） | 纯附加字段，旧消费者忽略即可 | ✅ |
| B `uint8` 枚举 | 省 1 次小串拷贝 | 同上 | 同上 | 需额外映射表才能读日志 | ❌ |

**裁决建议：A（`string`）**。理由：与既有风格一致、审计可读；**并要求在验收记录中写明**"RT 线程内存在 string 赋值"是既存事实（非本次引入）。

### Q2 — `Complete` 状态下是否允许 hold？

| 原始选项 | 代码依据 | 安全影响 | 推荐 |
|---|---|---|---|
| **A 不允许** | `advance()` 仅在 `Running && committed` 推进（`transport_task.cpp:208-212`）；`Complete` 时 `t_traj_ == duration()`，无相位可暂停；`resume()` 只对 `Hold` 生效（`:274-302`）⇒ `Complete→Hold→resume` 会立刻又回 `Complete`，只污染审计轨迹 | 把"已完成"改写成"被打断"，使审计无法区分正常结束与外部中断 | ✅ |
| B 允许 | 同上 | 同上 | ❌ |

**裁决建议：A（不允许，回 `result=2`）**；停止已完成搬运请用 `abort`（语义不同）。

### Q3 — 是否等待回执？

| 原始选项 | 是否有 RT 阻塞风险 | 能证明到哪一层 | 推荐 |
|---|---|---|---|
| **A 同步阻塞等待**（服务内 `wait_for`） | 若服务在 RT 线程执行则**直接禁止**；即便在 executor 线程，等到的也只是服务回执 = L1，**永远证明不了 L3/L4** | L1 | ❌ |
| **B 异步请求 + 有限时间确认** | **无**：请求非阻塞发出，确认在**执行器侧**轮询状态完成 | L1→L2→L3→L4 | ✅ |
| C 不等待、无确认 | 无 | L1 | ❌ |

**裁决建议：B**。执行器实现为三步有界等待：
1. 发请求（同步返回，证明 L1）；
2. 轮询 `hold_request_seq == seq && result == 1`，**超时 208 ms** → L2；
3. 轮询 `state=="HOLD"` 且 `hold_origin=="executor"`，**再超时 100 ms** → L3；
4. 观测 `q_cmd` 连续 10 拍不变 → L4；任一超时 ⇒ 执行器本地 HOLD + `abort`（T-H14）。

**RT 阻塞核查结论**：本设计中**没有任何等待发生在 RT 线程或服务回调内**；"等待"只存在于执行器（非实时）。因此 Q3 选 B 不引入实时风险，且是唯一能证明 L3/L4 的选项。
