## 1. 背景与问题定性

S4-T17 要求“台架连跑 10×638 = 6380 周期（≈51 s）”，通过标准为：

| 指标 | 标准 | 原文 |
| --- | --- | --- |
| `update()` P99 | ≤ 6.4 ms | 规划 `:651`，标 `[待标定]` |
| 最大间隔 | ≤ 1.5·dt = 12 ms | 规划 `:651` |
| RSS 增长 | ≤ 1 MB | 规划 `:651` |
| 句柄数增长 | 不增长 | 规划 `:651` |

第一轮矩阵（4 组环境 × 6380 周期）实测：

| 组 | P99 (µs) | 最大间隔 (µs) | RSS (KB) | fd | 判定 |
| --- | --- | --- | --- | --- | --- |
| 空闲 | 350 | 16 009 | 220 | 0 | 间隔 FAIL |
| 空闲 + `taskset` 绑核 | 388 | 16 571 | 3 344 | 0 | 间隔 FAIL |
| 单核压力 | 3 662 | 21 291 | 204 | 0 | 间隔 FAIL |
| 双核压力 | 1 192 | 15 769 | 184 | 0 | 间隔 FAIL |

结论（`已证明事实`）：**P99 四组全 PASS；最大间隔四组全 FAIL（含最空闲的 16.0 ms）**；`taskset` 绑核反而更差。唯一一次全项 PASS 的运行（8 845.5 µs）是噪声采样，**不得单独作为通过证据**。

## 2. 当前环境事实（WSL2）

| 项 | 实测值 | 对复测的含义 |
| --- | --- | --- |
| CPU | AMD Ryzen 7 4800H，16 逻辑核 | 可作对照基线 |
| OS | Ubuntu 22.04.5，内核 `6.18.54.1-microsoft-standard-WSL2` | **非原生内核**；调度语义与宿主共享 |
| ROS | Humble | 目标软件栈一致 |
| `ulimit -r` | **0** | **无法设置 `SCHED_FIFO`**（`chrt -f` 会失败） |
| `isolcpus` | 无 | 无法隔离核 |
| cgroup `cpu.max` | `max` | 无 CPU 配额限制 |
| valgrind / heaptrack / stress | 均未安装 | 分配与压力证据受限 |

`技术推断`：最大间隔在**最空闲**条件下也达 16 ms，说明抖动来自 WSL2 虚拟化与宿主调度，而不是被测代码。因此“在 WSL2 上优化到 12 ms”没有工程意义。

## 3. 复测环境要求（合格条件）

只有同时满足下列条件的环境才算“合格环境”，否则测得的数字只能标记 `UNVERIFIED_ENV`：

1. **原生 Linux**（非 WSL、非容器内的共享宿主内核）；发行版与目标部署一致（Ubuntu 22.04 LTS）。
2. **实时调度能力**：`ulimit -r` ≥ 99（或具备 `CAP_SYS_NICE`），`chrt -f 80 true` 返回 0。
3. **CPU 亲和与隔离**：至少预留 2 个物理核（`isolcpus=` 或 cgroup cpuset），控制线程绑到预留核。
4. **内存锁定**：`mlockall(MCL_CURRENT|MCL_FUTURE)` 可用（`ulimit -l unlimited`）；否则 RSS 指标需说明未锁页。
5. **频率/功耗策略**：`performance` governor，禁用深度 C-state（或记录实际值）。
6. **可观测性**：`perf`、`/proc/interrupts`、`/proc/self/status` 可读。

若上述任一条件无法满足，**不得**把该环境的结果当作 S4-T17 的通过证据。

## 5. 测试矩阵（4 组环境 × 每组 3 次）

| 组 | 环境 | 负载 | 目的 |
| --- | --- | --- | --- |
| E1 | 合格原生 Linux，空闲 | 无 | 基准数字 |
| E2 | 同上，控制线程 `SCHED_FIFO` 80 | 无 | 验证实时调度收益 |
| E3 | 同上，1 核满载（`stress-ng --cpu 1` 绑到**非**预留核） | 单核压力 | 验证隔离有效性 |
| E4 | 同上，预留核外全核满载 | 全局压力 | 验证最坏情形 |

每组 **3 次**，取 3 次的**最差**值判定（不允许只报最好一次）。样本数、丢弃数、有效样本数必须与 `TimingRecorder::Summary` 一致。

## 6. 采集指标与统计口径

| 指标 | 来源 | 统计方式 |
| --- | --- | --- |
| 周期耗时 `cycle_us` | `timing.csv` 的 `cycle_us` | mean/min/max/P50/P95/P99/P99.9（与 `Summary` 同口径，**不得另定义**） |
| 求解耗时 `solve_us` | `timing.csv` 的 `solve_us` | 同上 |
| 最大间隔 `interval_us` | `timing.csv` 的 `interval_us` | 取 max |
| RSS 增长 | `Summary.rss_growth_kb`（`~/start_transport` 基线 → 结束） | 单值 |
| fd 增长 | `Summary.fd_growth` | 单值 |
| deadline 故障 | 控制器日志与 `Summary.overruns` | 次数与比例，**两者都要报** |
| committed / HOLD / FAULT / ABORT 分布 | `~/transport_status` 采样 + 控制器日志 | 计数 |
| 轨迹时钟推进/冻结 | `timing.csv` 与 `~/transport_status.t_traj` | 是否在 HOLD 期间冻结 |

**关于 `overruns` 的已知口径问题**（必须写进证据）：`update_rate = 125 Hz` 使标称周期**等于** dt = 8 ms，因此“间隔 > dt 的周期数 == 0”**按构造不可达**（实测 48.5%）。规划该子句记为 `SPEC_GAP`，本计划**沿用规划自带的 1.5·dt 判据**，不改标准、不以 48.5% 作为 FAIL 依据。

## 8. 判定规则

1. 环境不合格 ⇒ 该组全部标 `UNVERIFIED_ENV`，**不参与 PASS/FAIL**。
2. 环境合格：3 次运行的**最差**值满足四项标准 ⇒ 该组 PASS；任一项超限 ⇒ 该组 FAIL。
3. 4 组中 E1/E2 必须 PASS；E3/E4 若 FAIL，须给出“压力下 max interval 与预留核抢占”的归因证据，并单独申请该组是否纳入门禁。
4. 任何 FAIL 都**不得**通过调整判据、放宽标准或只报最好一次来消除。
5. `POLICY`：若用户最终接受“WSL2 作为参考、原生 Linux 作为门禁”，须在验收记录中写明两者的适用范围。

## 9. 当前状态与用户需准备的最小条件

**状态：`BLOCKED_EXTERNAL_ENV`** —— 目前没有满足第 3 节条件的机器。

用户需准备的最小条件（任选其一）：

- **方案 1（推荐）**：一台原生 Ubuntu 22.04 双系统/裸机（8 核以上），可设置 `rtprio`、可 `isolcpus`。
- **方案 2**：WSL2 之外的一台 x86 主机 + Ubuntu 22.04 + 允许 `CAP_SYS_NICE`（云主机通常不允许）。
- **方案 3（降级，不推荐）**：明确接受“S4-T17 原生平台验证推迟到 S4.3 真机阶段”，并把 W2 的 S4-T17 状态永久记为 `UNVERIFIED_ENV`（而不是 PASS）。

在任何一项准备完成前，**S4-T17 不得标记为 PASS**。

## 10. 与 S4-T2 的关系

S4-T2（638 周期）与 S4-T17（6380 周期）的**测量层不同**：

- L1 纯数学（无 ROS、无调度）：`solve()` 耗时与分配归属 → 服务于 S4-T2 的分配条款。
- L3 控制循环（ros2_control + mock 硬件）：`cycle_us` / `interval_us` → 服务于 S4-T2 的时间条款与 S4-T17。

**不得**用 L1 的快速循环替代 L3 做实时性判定；**不得**用 WSL2 的 L3 结果宣称目标平台实时性。
