三条必须先说清的事实：

1. **「无 `malloc`」不在 S4-T17 里，在 S4-T2 里**。S4-T17（规划 `:651`）的判据是「P99 ≤ 6.4 ms（`[待标定]`）；最大间隔 ≤ 1.5·dt；RSS 增长 ≤ 1 MB；句柄数不增长」，**没有**分配审计；分配审计在 S4-T2（`:636`）：「无 `malloc`（用 `heaptrack`/`valgrind --tool=massif` 抽查一次）」。两者的结论必须分开记，不能混成一条。
2. **E4 不是「由单次改成 5 次」的擅自变更**。已批准规划 `:484` 写的是「`update()` 实际间隔 > `2·dt` **连续 5 次** → `deadline_missed`」。**单次实现才是偏离**，本轮是把它改回原条款。这一条的证据链在 §C.3。
3. **`[待标定]` 的含义**（规划 `:6`）："凡是无实测依据的数字一律标注 `[待标定]`" ⇒ 它是**未标定的建议值**，不是已批准的验收阈值。因此 P99 ≤ 6.4 ms 这一条的"通过"只能记为"在建议值下通过"。

环境固定事实（影响所有实时性结论）：`nproc = 16`、无 CPU 隔离、cgroup `cpu.max = max`、**`ulimit -r = 0`**（非 root，**无法设置 `SCHED_FIFO` 实时优先级**）、无 `valgrind`/`heaptrack`。因此"受控调度"只做到 CPU 亲和性，实时优先级一路标 `UNVERIFIED_ENV`。

## A. S4-T17 实时性核查

### A.1 原条款（逐字）

规划 `:651`：

> **S4-T17** | 长时间实时性 | 台架连跑 10×638 = 6380 周期（≈51 s） | 无漂移、无累积退化 | `update()` P99、最大间隔、RSS 增长、句柄数增长 | `summary.json` → `long_run_*` | P99 ≤ 6.4 ms（`[待标定]`）；最大间隔 ≤ 1.5·dt；RSS 增长 ≤ 1 MB；句柄数不增长

`dt = 0.008 s` ⇒ 1.5·dt = **12.0 ms**，6.4 ms = 80% × 8 ms。

| A1_pinned：`taskset -c 0,1` | 388.4 | 10907.8 | **16570.7** | 4 | **3344** | 0 | 6761 | 2 |

判定（逐条按原标准）：

| 判据 | 结果 |
| --- | --- |
| 6380 周期 | PASS（6682–6761 采样，全部 ≥ 6380） |
| P99 ≤ 6.4 ms `[待标定]` | **PASS 4/4**（最差 3662 µs，是建议阈值的 57%） |

### A.3 归因分析（不是"挑最好的一轮"）

- **P99 与"最大间隔"是两个量级的事**：P99 在 350–3662 µs，皆远低于 6400 µs；而"最大间隔"是单次离群值，4 轮中 3 轮的 `单周期最大` 也在 10.9–11.3 ms，说明存在**约 11 ms 量级的成块停顿**（不是 QP 慢，QP 的 P99 只有 350 µs）。这与 §A.4 测到的"控制线程每周期分配 ≈75 次"互相印证：分配器在堆上取页/加锁时会把一个周期拖到毫秒级。
- **绑核反而更差**：把整个 ROS 图压到 2 个核，DDS 线程与控制线程竞争同一核 ⇒ 间隔 16.6 ms、RSS 3344 KB。**绑核不是"受控调度"，只是换了一种扰动。**
- **实时优先级未能验证**：`ulimit -r = 0`，`chrt -f` 不可用 ⇒ `SCHED_FIFO`/`SCHED_RR` 一律 **UNVERIFIED_ENV**。**不得**把本表当作"控制器实时性不合格"的结论，也**不得**把它当作"合格"的结论。
- 唯一一次全项 PASS 的观测：`timing_s4t17.csv` 那一轮（P99 415.0 µs、最大间隔 8845.5 µs、RSS 160 KB、0 次超 1.5·dt）。**它不能单独作为通过证据**，因为同一二进制在另外 4 轮都超限——这正是"不得只挑最好一轮"的理由。

原始证据：

- 日志：`/tmp/c43s4_env/A1_default.log`、`A1_pinned.log`、`A1_pinned_load.log`、`A1_load_wide.log`
- 逐周期 CSV：`/tmp/c43s4_rt/timing_s4t17.csv`、`timing_s4t2.csv`（列 `k,wall_ns,cycle_us,solve_us,interval_us`）
- 控制器自身日志：`/tmp/c43s4_rt/realtime_launch.log`

### A.4 控制路径动态内存分配审计

**方法**：自建 `LD_PRELOAD` 分配计数器（`/tmp/mallocwatch/mallocwatch.c`，16 KB 的 `.so`），钩住 `malloc/calloc/realloc/posix_memalign`，**按线程**计数，`SIGUSR1` 打快照、进程退出再打一次；每行带 `/proc/self/task/<tid>/comm` 以便区分线程。钩子内部不分配内存（表是静态数组、`dlsym` 结果缓存），因此计数不含测量工具自身开销。选它是因为本机没有 `valgrind`/`heaptrack`（规划点名的两种工具都不可用）。

三层区分（按要求）：

| 层 | 测法 | 分配数 | 结论 |
| --- | --- | --- | --- |
| 初始化/配置/启动/日志 | 进程启动到 `configure` 完成（同一次运行的早段快照） | 数十万级，集中在 DDS/参数/URDF 解析线程 | **合法**，不计入判据 |
| **控制循环实时路径** | L1：`RealtimeLayers.S4T2_Layer1OfflineMathCost`，纯数学、无 ROS、638 次 `solve()` | **32 671 / 638 = 51.2 次/solve** | **必须计入** |
| **控制循环实时路径** | L3：真实控制循环，两次 `SIGUSR1` 快照间隔 38 s（≈4750 周期） | 控制线程 **357 399 → ≈75 次/周期** | **必须计入** |
| 测量工具自身 | 钩子内零分配；快照写文件在信号处理里，属工具开销 | — | 已排除 |

关键读数（L3，`ros2_control_node` 内，38 s 窗口）：

```
 d_alloc      d_bytes       tid comm
  357399    167732533   1551641 ros2_control_no      <- 控制线程
  124176      6877440   1551682 ros2_control_no
   19048      3200064   1551681 ros2_control_no
```

L1 读数（同一 `.so`，单线程纯数学）：`samples=638`、`alloc = 32671` ⇒ **51.2 次/solve**。两者相减约 24 次/周期归 ROS 侧（状态发布、日志、`TransportTask::sample` 的临时量）。

**判定：FAIL**。原条款要求"无 `malloc`"，实测控制路径每周期分配 51–75 次。这不是"RSS 涨得少所以没问题"——分配被 `free` 回收，RSS 因此稳定（160–220 KB），但**分配器本身仍在实时路径里**，这正是 §A.3 那 11 ms 停顿的合理来源。

**为什么之前记 `UNVERIFIED`**：上一轮只有"跑 heaptrack/massif"这一条路，两者都没装，于是按实标记未验证。本轮用 `LD_PRELOAD` 计数器补上了测量，**结论从 UNVERIFIED 变成 FAIL**——这是被证据推翻，不是被标准放宽。

## B. W2「≤ 1 ULP」正式变更申请

### B.1 现行正式规定（原文）

规划 §5 W2 行 `:533`：

> 与 S3 `ff_1` 场景**逐周期比 `dq` 位相同**（≤1 ULP）；终点误差 ≤ S3 同量级

注意它**不是** §7 S4-T2（那条是实时性预算）；§7 S4-T3（`:637`）另有「`max|Δrow.J|`、`max|Δrow.e|`、`max|Δdq|` 全部 `== 0`；1 ULP 差异必须追到根因，不许放宽容差」——同一条要求的更严格表述。**不得**把 W0 的"同一实现迁移前后逐位一致"与 W2 的"两条不同计算路径数值一致"混为一谈（见 B.2）。

### B.2 失败证据（保留，不删）

| 证据 | 数值 | 来源 |
| --- | --- | --- |
| 逐周期决策一致数 | 0 处不一致（638/638 相同） | `test_mock_closure` S4-T2 输出 |
| 全程最大关节偏差 | `max|Δdq| = 9.024e-14 rad`（cycle 0 joint 6：`-1.8145642984102369e-14` vs `7.2097585154607034e-14`） | 同上 |
| 轨迹时钟差 | `max|Δt| = 3.553e-15 s` | 同上 |
| 冻结件自洽 | 638 行 `t == k·dt` **逐位相同** | `test_ulp_semantics` |
| 近零样本 | 7656 个 (周期,关节) 中 **570 个 `|dq| < 1e-9`**；`1 ULP` 在最小区间 `|dq| = 1.320e-18` 处 ≈ **1.926e-34**，在最大 `|dq| = 3.177e-03` 处 ≈ **4.337e-19** | 同上 |
| 换算 | 同一个 9.024e-14 rad 在小端是 **4.686e20 ULP**，在大端是 **2.081e5 ULP**；物理意义 5.170e-12 度，相对步长 1.128e-11 | 同上 |

**关于"巨大的 ULP 数"的正确读法**（按要求避免用 ULP 直接推断控制风险）：ULP 是**浮点分辨率**单位，`|dq| → 0` 时分辨率趋于 0，因此近零处的 ULP 距离会爆炸，这只是"用了一个在零点附近发散的度量"，**不等于 1e20 倍的物理误差**。物理量只有 9.0e-14 rad，是机械分辨率（1e-4 rad 量级）的 1e-9 倍。**但它仍使"≤1 ULP 覆盖全部 12 关节"这一条不成立**——不是因为误差大，而是因为该度量在近零处不可用。

同时**不得**宣称"任何两次独立运行必然不能逐位一致"：本轮只证明了"控制器的 `t += dt` 累积律与 S3 的 `t = k·dt` 相差 3.55e-15 s，且 QP 在近零关节上的取整会放大到 9e-14 rad"。若两条路径用同一条时钟律、同一编译器与同一运算顺序，逐位一致是可能的；W0 已经做到过（同实现两副本，208 行 `cmp = 0`）。**W2 做不到是因为路径不同，不是因为浮点不可靠。**

### B.3 根因（三条，互相独立）

1. **时钟律不同**：S3 冻结件用 `t = k·dt`；控制器用 `t_traj += dt` 累积，38 s 后漂移 3.553e-15 s（可逐位复现）。
2. **输入端点微差**：由 (1) 导致同一周期取到的 `T_d`、`v_ff` 末位不同。
3. **近零关节的取整放大**：两任务都要求"不要动"时 `dq ≈ 1e-14`，此时任何输入的末位差异都会被放大成"完全不同的尾数"，而绝对量仍是 1e-14 rad。

### B.4 建议的替代条款（完整文字，供批准）

> **S4-T3′（替代 §5 W2 的「≤1 ULP」，仅适用于 S4.1 台架的确定性数学路径）**
> 同一 `q0`、同一轨迹、同一 `DualArmQpParams`、无物理、无并发的前提下，与 S3 `ff_1` 冻结件逐周期比较，须同时满足：
> 1. **决策一致**：每个周期的 `committed`（以及 `failure_code`）与冻结件完全相同，不一致数 `== 0`；
> 2. **每关节绝对偏差**：`max|Δdq| ≤ 1e-12 rad`；
> 3. **轨迹时钟偏差**：`max|Δt_traj| ≤ 1e-12 s`；
> 4. **终点同量级**：终态 `‖e_O‖` 与冻结件的比值 ∈ [0.5, 2]；
> 5. **分层报告**：`|dq| ≥ 1e-9` 与 `|dq| < 1e-9` 两组分别给出 `max|Δdq|`、样本数与占比（近零组只报告、不设判定）；
> 6. **ULP 分布保留为诊断量**：输出 `max ULP`、`P99 ULP`、近零/非近零分组，但**不作为通过判据**。

**来源与依据**：判据 2 的 `1e-12 rad` 取自实测最大偏差 `9.024e-14` 的约 11 倍余量，同时比执行器分辨率（`v_max·dt = 0.02 rad/step`、编码器 1e-4 rad 量级）小 8 个数量级；判据 1 是**离散控制决策**层面的一致性，比连续量更贴近"会不会走出不同轨迹"；判据 3 覆盖根因 (1)；判据 5/6 保留了对近零区的可见性。

**适用范围**：仅 S4.1 台架的纯计算路径。**Gazebo 物理闭环与真机不适用**（沿用 S4-T13 的数值容差口径）。

**风险**：判据 2 是"绝对偏差"，理论上允许两条路径在近零关节上取不同符号而都通过（量级都是 1e-14，对轨迹无影响）；若不批准，则退化为 B.5 的方案。

### B.5 不批准变更时的可选处理

1. **保持 FAIL 并阻断**：S4.1 收口条件改为"W2 数值一致性 = FAIL（已知偏差 9.024e-14 rad，不影响决策）"，作为**已知偏差**记入 W3 的输入基线，后续任何数值回归以此为准。
2. **对齐时钟律**：把控制器改成 `t_traj = k·dt`（与 S3 一致），再复测 ULP——可能把差异压到 0，但这是**改控制器行为**，需单独授权，且会改变 §4.2.1 的"仅 committed 时推进"语义（两者不能同时成立）。
3. 接受"逐位一致只对同实现成立"的前提，把 §5 W2 行的措辞改为"决策一致 + 终点同量级"，其余删除。

## C. E4 截止期保护专项审查（优先级最高）

### C.1 原条款（逐字）

规划 `:484`：

> | E4 | 更新超时 | `update()` 实际间隔 > `2·dt` 连续 5 次 | `deadline_missed` | `~/resume` |

`dt = 0.008 s` ⇒ 阈值 **16.0 ms**，且**连续 5 次**才进入 `HOLD`。

### C.2 新旧实现对照

| 维度 | 旧实现（W1 之前，`kDeadlineFaultStreakMax` 不存在） | 新实现（本轮） | 与原条款关系 |
| --- | --- | --- | --- |
| 监控对象 | `PeriodMonitor::updateFromTime(now, fallback)` 对 **rclcpp 时钟**求差，得到 `update()` **入口到入口**的实际周期（不是求解耗时、不是 QP 时间） | 同 | 一致 |
| 阈值 | `period > nominal × fault_factor` = 8 ms × 2.0 = **16.0 ms** | 同 | 一致 |
| 触发条件 | **单次**超阈值即 `deadline_fault = true` | `deadline_fault_streak_ ≥ 5` | **旧实现偏离原条款，新实现符合** |
| 失败码 | `deadline_missed` | 同 | 一致 |
| 复位 | `on_activate` 重置 `period_monitor_` | 仍在 `on_activate` 重置；另加 streak 在**任一正常周期**归零（`raw ? +1 : 0`） | 一致（连续计数必须如此） |
| 计数位置 | — | `update()` 中，**在任何 HOLD 早退之前**（`dual_arm_qp_controller.cpp:656-671`）⇒ `HOLD/FAULT/ABORT` 期间监控仍在跑、streak 仍在计数/归零 | 一致 |

### C.3 ★ 关键裁定：这是"改回原条款"，不是"擅自放宽"

- 规划 `:484` 明写"连续 5 次"。
- 旧代码是"单次"，且已由提交历史确认：`git show df79d66:src/dual_arm_qp_controller/src/dual_arm_qp_controller.cpp | grep deadline_fault` 得到单行
  `:607 const bool deadline_fault = period_monitor_.updateFromTime(time.seconds(), period.seconds());`
  —— 没有任何 streak 计数。`kDeadlineFaultStreakMax` 是提交 `5e53cc8` 才引入的（`git log -S kDeadlineFaultStreakMax` 只命中这一条）。即：**单次实现早于本轮，本轮把它改回 `:484` 的"连续 5 次"**。
- 因此 E4 的现状**符合已批准的 E4 条款**；`kDeadlineFaultStreakMax = 5` 是把偏离改回。
- 旧单次实现**比批准条款更严**，但它在本机会把一个 **1.15 s 的调度停顿**直接判成 HOLD——这既不是"控制器失步"，也会掩盖真实故障（见 C.5 的实测日志）。
- **仍需你确认**：如果你认为"单次更严更好"应当成为新标准，那属于**收紧**标准，需要正式变更（并把 `S4-T15` 的"触发周期 ≤ 3 周期"重新对齐）；本轮**不**擅自这样做。

### C.4 六个定点问题的回答

1. **原条款精确定义**：`update()` 入口到入口的实际间隔 > 16.0 ms，连续 5 次 ⇒ `HOLD(deadline_missed)`，恢复需 `~/resume`。
2. **原实现监控的是哪个量**：既不是求解耗时，也不是 QP 时间，而是**整个控制周期的实际间隔**（`PeriodMonitor` 对节点时钟求差；`solve_time_ms` 另有统计但不参与该判据）。阈值 16 ms = 2×dt。
3. **新连续计数器监控什么**：同一个量、同一个阈值；只把"1 次"改成"连续 5 次"。
4. **单次严重超时是否仍立即阻止不安全输出**：**不会立即 HOLD**（实测：`deadline overrun 1/5 (measured period 1151.013 ms, threshold 16.000 ms)`，**未**产生 HOLD）。但**不会**发出基于陈旧状态的命令：`update()` 每拍都重新读 `q_state`，停顿结束后算的是新的 `dq`，且 `q_cmd_` 在停顿期间未被改写（命令值保持上一拍的合法值）。这条必须在验收记录里写明，不能只说"符合条款"。
5. **计数器在正常/HOLD/FAULT/ABORT/RESUME 中如何复位**：任一正常周期归零；`on_activate` 全清；`HOLD/FAULT/ABORT` 期间监控照常运行（计数位置在早退之前），RESUME 不清零（继续按当前 streak 判断，避免"一 resume 就掩盖持续超期"）。
6. **是否存在持续越限期间仍继续发运动命令**：**存在**，在 streak 达到 5 之前的 1–4 个周期里，`update()` 仍会求解并 `writeCommand()`。这段时间的输出是**基于新鲜 `q_state`** 的合法小步长命令，不是陈旧命令；但它确实不是"零输出"。这是原条款本身的语义，不是新引入的。

### C.5 故障注入（本轮实测，含未能覆盖的项）

| 注入 | 做法 | 实测 | 判定 |
| --- | --- | --- | --- |
| 一次**严重**超时（1.15 s） | 对 `ros2_control_node` 打 `SIGUSR1`，在控制线程内同步写 26 个线程的计数快照（人为制造阻塞） | `deadline overrun 1/5 (measured period 1151.013 ms, threshold 16.000 ms)`，**无 HOLD** | 与"连续 5 次"一致 |
| 再次严重超时（1.18 s） | 同上（第二次快照） | `deadline overrun 1/5 (… 1182.954 ms …)`，**无 HOLD** | 同上；且证明 streak 在每个正常周期归零 |
| 轻度超时（16–20 ms 连续） | 靠 CPU 抢占总制造 | 4 组环境中 `>16 ms` 的正常周期计数未在控制器日志中出现（见下"未能覆盖"） | **UNVERIFIED** |
| 连续 4 次 / 连续 5 次 | 需要**确定性**地让连续 N 个周期都 >16 ms | 无注入钩子，CPU 抢占无法按周期对齐 | **UNVERIFIED** |
| 超时与正常交替 | 同上 | 同上 | **UNVERIFIED** |
| HOLD 后 RESUME | 台架真实服务调用 | 既有 S4-T13/S4-T17 已覆盖 HOLD→RESUME（`holds_resumed=1..4`） | PASS（间接） |
| 超时期间心跳同时失效 | 可组合，但需对齐时序 | 未做（E8 单独已覆盖，见 S4-T13） | **UNVERIFIED** |

**未能覆盖的原因（要如实写明）**：控制器没有故障注入钩子（例如 `deadline_fault_streak_max` 参数、或"人工注入一次 deadline fault"的服务），而 CPU 抢占无法按周期对齐到"恰好 4 次 / 恰好 5 次"。**要确定性覆盖这 4 项，最小改动是**：把 `kDeadlineFaultStreakMax` 从 `constexpr` 改为 `declareIfNeeded<int>("deadline_fault_streak_max", 5)`（**只加参数、不改默认行为**），或加一个 `~/inject_deadline_overrun` 测试服务。**本轮未做，属于需授权的代码变更。**

### C.6 安全影响陈述

- **比原条款更严的旧行为已移除**：1.15 s 停顿不再立即 HOLD。按已批准条款这是正确的；但**若现场接受不了这 1–4 个周期的继续输出，应当收紧标准**（把 5 改回 1，或改为"单次 > 100 ms 即 HOLD、16–100 ms 需连续 5 次"）。这属于策略选择，**必须由你裁定，不得由实施方默认**。
- **不会**因为这条而让"控制器计算超时"与"操作系统调度停顿"混淆：`PeriodMonitor` 量的是入口到入口的实际间隔，两者在数值上不可区分；区分它们需要额外证据（`cycle_us` 只覆盖 `update()` 内部，`interval_us` 覆盖调度）。本轮的 11 ms 单周期最大 + 16 ms 间隔属于**调度/分配**侧，不是 QP（QP P99 = 350 µs）。
- **保护链仍不完整**：E2 `Degraded`、E7 `Missing`、`protection_complete == false`。**不得**据此开展依赖完整保护链的真实双臂搬运。

### E-1「最大间隔 ≤ 1.5·dt」的处置（二选一，不建议直接改判据）

- **现行规定**：规划 `:651`，最大间隔 ≤ 12.0 ms。
- **拟变更（若选 A）**：改为「`max interval ≤ 1.5·dt` **在隔离环境（`SCHED_FIFO` + `isolcpus`）下**为硬判据；非隔离环境下改为 `max interval ≤ 2·dt`（16 ms）且 `超 1.5·dt 次数 ≤ 1%`」。

### E-2「控制路径无 malloc」的整改（推荐整改而非放宽）

- **现行规定**：S4-T2 `:636`，无 `malloc`（heaptrack/massif 抽查一次）。
- **拟变更**：**不改判据**；改为"补一次基线测量 + 整改到 0，然后按原判据验收"。若时间不允许，退化为「控制路径分配 ≤ 1 次/周期 且 单周期最大 ≤ 1 ms」，并标 `[待标定]`。
- **为什么需要**：实测 51–75 次/周期，与 11 ms 级停顿一致；这是实时性根因，放宽判据等于放弃根因。
- **不变更的影响**：实时性永远无法稳定达标（分配器在实时路径上，抖动无法消除）。
- **变更后的验证**：同一 `LD_PRELOAD` 计数器，L1 与 L3 都回落到 0（或 ≤1），且 S4-T17 最大间隔复测。

### E-3 E4 是否维持"连续 5 次"（需你确认，默认维持）

- **现行规定**：规划 `:484`"连续 5 次"。
- **拟变更**：如果你要求"单次严重超时也立即 HOLD"，则改为「单次 > 100 ms 立即 HOLD；16–100 ms 连续 5 次」。
- **为什么可能需要**：1.15 s 停顿期间仍有 1–4 个周期发出合法小步长命令；若现场不接受任何"停顿后继续输出"，需收紧。
- **不变更的影响**：维持原条款，行为与规划一致；但"1–4 个周期继续输出"必须在验收记录里显式写明。
- **变更后的验证**：需要 §C.5 的注入钩子（`deadline_fault_streak_max` 参数或测试服务），否则 4/5 次边界无法确定性验证。

| 强制 **4** 个连续 deadline 故障 | **未 HOLD**：`deadline overrun 1/5`（日志节流 500 ms，故只打一条），状态 `IDLE→COMPLETE`，`exit=0` |

### 14.3 命令保持与过期语义（新增核查）

- `writeCommand()`（`dual_arm_qp_controller.cpp:906-912`）只把 12 个值写进 `command_interfaces_`，**没有时间戳、没有过期检查、没有看门狗**。
- ros2_control 的 position 接口语义：命令值一旦写入就**一直有效**，直到被下一次写入覆盖 ⇒ 停顿 1.15 s 期间，硬件/台架继续跟踪**上一条合法位置目标**（停止不动，不会飞车，但也不会自己退出）。
- 仓库内**没有**任何命令级过期机制（`grep timeout/watchdog/expire` 在控制器配置与源码中无命中）。唯一的"新鲜度"检查是 E8 的**执行器→控制器心跳**，而 S4.1 阶段**还没有真实执行器**（W3 才建），台架里由测试扮演执行器。
- 因此对 D2 的正确回答是：**"停顿期间继续执行上一条命令" 是真的**（位置保持），**但不会执行"基于陈旧状态的错误命令"**（`update()` 每拍重读 `q_state`）。风险等级：位置接口下为"保持"，非"失控"；但对**速度/力矩接口或真实执行器**（S4.3）必须补命令过期。
