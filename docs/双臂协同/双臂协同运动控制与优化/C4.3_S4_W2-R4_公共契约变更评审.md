## 2. 特别验证：`osqp_solver.cpp:188` 的 setup 分支分配是否与返回值分配同因？

**结论：不同因。** 逐行看：

```cpp
175: QpSolution OsqpSolver::solve(const QpProblem& problem) {
176:     QpSolution solution;                                  // x 为空，不分配
183:     if (impl_->work == nullptr || impl_->n != n || impl_->m != m) {
186:         if (!impl_->allocStructure(n, m)) return solution; // ← 建 P/A/q/l/u/x0 缓冲
187:         impl_->updateValues(problem);
188:         if (!impl_->osqpSetup()) return solution;          // ← osqp_setup 建 workspace
189:     } else {
190:         impl_->updateValues(problem);                      // ← 稳态路径，不分配
191:     }
...
210:         solution.x.resize(n);                             // ← 每次求解都分配
```

| 维度 | `:188` setup 分支 | `:210` 返回值 |
| --- | --- | --- |
| 触发条件 | **仅当** `work==nullptr` 或 `n`/`m` 变化（`:183`） | **每次 solve** |
| 实测次数 | 24 次（638 次 solve 中只发生一次 setup） | 1276 次（2.00/solve） |
| 生命周期 | 与 OSQP workspace 绑定，进程内常驻 | 每次调用一个新缓冲，随返回值交付 |
| 消除方式 | 已经最优（只建一次）；`test_qp_benchmark.cpp:116` 已在守它 | 需改契约（见下） |

⇒ **两者不具相同成因**。把 `:188` 与 `:210` 混为一谈会得出“改契约能省 2.04 次”的错误结论；
正确口径是：**可被契约变更消除的只有 `:210` 那 2.00 次/solve（+ 其返回侧 1.04 次）**，
`:188` 的 24 次是不可避免的一次性成本。

## 3. 三方案 × 七维逐项分析

### 方案 A：预分配缓冲 + 输出参数重载

```cpp
class QpSolver {
public:
    virtual QpSolution solve(const QpProblem&) = 0;                 // 保留
    virtual bool solveInto(const QpProblem&, QpSolution* out);      // 新增（默认实现=调 solve 再搬）
};
```

| 维度 | 分析 |
| --- | --- |
| ABI/API | 新增**虚**函数 ⇒ vtable 布局变化 ⇒ 对既有二进制不兼容；但工作区内 2 个子类 + 1 个调用点全量重编，实际影响可控。源码层兼容（旧接口保留） |
| Eigen 分配 | 调用方复用同一个 `QpSolution`，`x.resize(n)` 在容量足够时**不分配** ⇒ 稳态 0 次。首次仍 1 次 |
| OSQP workspace 生命周期 | 不受影响（`:183-191` 未变） |
| 返回值与所有权 | 出参由调用方持有；错误用 `bool` 返回 + `out->converged`。**双语义**（返回值 vs 出参）需文档化 |
| 线程安全/实时性 | 每调用方一个缓冲 ⇒ 无共享；稳态 RT 安全。但“首次分配”发生在控制路径首拍 |
| frozen baseline 影响 | 数值不变（同样的算术），`test_legacy_golden_c43s3` 应逐位不变 |
| 测试要求 | 现有测试全部保留；新增：`x.data()` 指针跨调用稳定（证明无 realloc）；`solveInto` 与 `solve` 结果逐位一致 |

### 方案 B：`QpSolution` 定长化（`Matrix<double, 24, 1>`）

| 维度 | 分析 |
| --- | --- |
| ABI/API | **结构体布局变化**（指针+尺寸 → 内联数组）⇒ 二进制不兼容；源码层 `.size()`/`.segment<>()` 仍可用，但 `x.resize(n)` 语义变化（定长不能 resize） |
| **致命问题** | `n` 真实存在 **12** 与 **24** 两种（`dual_arm_qp.cpp:350-355`）⇒ 定长 24 会让 12 分支的语义变得含混（尾部 12 个元素未定义） |
| Eigen 分配 | 完全 0 次 |
| 其余 | OSQP/所有权/线程安全与 A 相同；测试需覆盖 12/24 两分支 |

⇒ **方案 B 原样不可取**。

### 方案 B′（推荐的折中）：有界动态向量

```cpp
// 只改一行，kMaxVars = 24
using QpVec = Eigen::Matrix<double, Eigen::Dynamic, 1, 0, 24, 1>;
struct QpSolution { QpVec x; ... };
```

| 维度 | 分析 |
| --- | --- |
| ABI/API | 布局变化（内联 24 doubles）⇒ 二进制不兼容；**源码层零改动**：`.resize(n)`、`.size()`、`.segment<12>(0)`、`= x`、`x[i]` 全部照旧；12 与 24 两种尺寸都被容纳 |
| Eigen 分配 | `resize(n≤24)` **不触堆**（存储内联）⇒ 每次 solve **0 次**，无需预热、无“首拍分配” |
| OSQP workspace | 不受影响 |
| 返回值与所有权 | 语义完全不变（仍按值返回），`sizeof` 变大但 24 doubles = 192 B，拷贝可忽略 |
| 线程安全/实时性 | 与现状相同（值语义），且**不依赖调用方是否复用缓冲** ⇒ 最难用错 |
| frozen baseline | 数值不变；`test_legacy_golden_c43s3` 应逐位不变 |
| 测试要求 | 现有全保留；新增：`n=12` 与 `n=24` 两条路径的 size/内容正确；`EIGEN_RUNTIME_NO_MALLOC` 下整段 solve 不触发分配 |

### 方案 C：双接口过渡（旧接口 + 新接口并存，旧接口标 deprecated）

| 维度 | 分析 |
| --- | --- |
| ABI/API | 两者都在 ⇒ 最平滑；但需长期维护两套语义 |
| Eigen 分配 | **旧路径仍分配**（它要返回值），只有新路径零分配 ⇒ 整体改善取决于迁移完成度 |
| 其它维度 | 与 A 同；额外成本是“两套语义”文档 + 测试双份覆盖 |

⇒ C 适合作为 A/B′ 的**迁移策略**，不适合作为终态。

## 4. 推荐

1. **首选 B′**：一行类型改动把“每次 solve 的 3.04 次自有分配”变成 0，且不需要改任何调用点、
   不引入双语义、不依赖调用方纪律；缺点是 ABI 破坏（工作区内全量重编即可接受）。
2. 若评审认为“ABI 也不该动”，则退回 **A**，并接受“首拍分配 + 调用方必须复用缓冲”的约束。
3. **不采用** 方案 B（12/24 双尺寸冲突）；C 仅在需要平滑迁移时叠加。

## 6. B′ 的关键前提已实测（本轮新增证据）

原先只是“Eigen 固定容量不分配”的推断，本轮做了决定性实测（`EIGEN_RUNTIME_NO_MALLOC`，
该开关与 libc 走 `malloc` 还是 `posix_memalign` 无关）：

| 用例 | 代码 | 退出码 | 结论 |
| --- | --- | --- | --- |
| A | `Eigen::VectorXd v; v.resize(24);` | **134（SIGABRT）** | 确实分配 |
| B | `Matrix<double,Dynamic,1,0,24,1> a; a.resize(24→12→24)` | **0** | 容量内 resize **零分配**，`sizeof = 208` |

源码 `/tmp/w2r4/bounded_vec.cpp`，断言位置 `/usr/include/eigen3/Eigen/src/Core/util/Memory.h:164`。
⇒ B′ 的“每次 solve 自有分配 3.04 → 0”不再是推断，而是由独立实验支持的结论。
