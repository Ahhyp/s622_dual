## B-3-1 — origin 标记无法覆盖 `TransportTask::step()` 内部拒绝

**缺陷证据**
- 控制器侧只有 4 个 `transport_->hold(` 调用点：`dual_arm_qp_controller.cpp:703`（`collision`）、`:723`（`healthHoldCode(health)`）、`:744`（`executor_lost`）、`:760`（`joint_state_out_of_bounds`）。
- 第 5 个来源不在控制器：`transport_task.cpp:232` `hold(s.refusal_code)`，位于 `TransportTask::step()` 内（求解前拒绝：近 π / 行非法）。控制器**没有**调用点可挂标记。
- Rev.1 §4.3 声称"5 处 origin 标记" ⇒ 不可达；`hold_origin` 对这类冻结会显示上一次的值（可能为 `""`），使 N3 失效。

**修复设计（采纳 D-1：origin 下沉）**
```cpp
// transport_task.hpp
enum class HoldOrigin : std::uint8_t { None = 0, Controller = 1, Executor = 2 };
void hold(const char* code, HoldOrigin origin = HoldOrigin::Controller);
HoldOrigin holdOrigin() const { return hold_origin_; }
HoldOrigin hold_origin_ = HoldOrigin::None;
```
```cpp
// transport_task.cpp
void TransportTask::hold(const char* code, HoldOrigin origin) {
    state_ = TransportState::Hold;
    failure_code_ = (code != nullptr) ? code : "hold";
    hold_origin_ = origin;
}
```
- 控制器侧 0 处标记代码；`transport_task.cpp:232` 走默认实参 ⇒ 自动记 `Controller`。
- 执行器请求路径显式传 `HoldOrigin::Executor`。
- `start()` / `reset()` 各加一行置 `None`（避免跨次运行残留）。

**实时/并发/内存影响**：字段为 `uint8`，赋值一次普通写；`step()` 与 `hold()` 同在 RT 线程、同线程无竞争；无分配、无原子、无阻塞。

**失败语义**：`hold_origin=="controller"` 表示冻结由控制器安全层或求解前拒绝发起；`"executor"` 表示外部请求；`""` 仅出现在从未冻结过时。

**测试**
- 正：T-H1（`"executor"`）、T-H9（近 π 拒绝 ⇒ `"controller"`，且 `failure_code=="object_error_near_pi"`）。
- 负：构造"拒绝后 origin 仍为上一次值"的用例必须失败——即断言 `T-H9` 之后 `hold_origin != "executor"`。

**残留风险**：`TransportTask` 属 W1 已验收代码，本项是**签名扩展**（带默认值、源兼容）；需要 W1 的 21 用例回归确认无行为变化。若审批方要求"零接触 W1 代码"，替代方案是 `publishStatus()` 由 `failure_code` 反查 origin（脆弱，拒绝字符串匹配），**不推荐**。

## B-3-2 — 早退跳过状态发布，使拒绝的回执自我延后

**缺陷证据**
- Rev.1 §4.3 片段在拒绝分支 `return return_type::OK;`。
- `publishStatus()` 由 transport 分支末尾调用（`dual_arm_qp_controller.cpp:792`），早退会跳过它 ⇒ 该周期的回执写不进消息。
- `publishStatus()` 还有 10 Hz 抽稀（`:836`，`status_period_ticks_ = 13`）与 `trylock()` 丢拍（`:837`）⇒ 拒绝引起的回执延迟从"≤1 状态周期"恶化到"≤2 状态周期"，且与回执早写的目的自相矛盾。
- 同时该周期也跳过 `writeCommand(q_cmd_)`（`:786`），即"什么都没发"——与"维持上一命令"的等价性依赖于驱动侧保持，属未声明行为。

**修复设计**：**删除 `return`**，回执照写、控制流完全不变（§4.3 代码块）。

**实时/并发/内存影响**：减少一个分支出口；其余不变。

**失败语义**：拒绝时 `state` 不变、`failure_code` 不变、`q_cmd_` 照常写入（与未收到请求时逐位相同）。

**测试**
- 正：T-H2（拒绝后同一周期内状态里的 `hold_request_result` 即为 2，且 `failure_code=="collision"`）。
- 负：构造"拒绝但 `q_cmd` 该周期未写入"的检测（比较 `writeCommand` 调用计数）必须为 0 次跳过。

**残留风险**：无新增；但需在 R1a 明确"未发生请求的周期与原实现逐位相同"（回归基线：W1 的 21 用例 + `test_realtime_budget`）。

## B-3-3 — 单槽 `exchange(0)` 并发下丢请求

**缺陷证据**
- Rev.1 只写 `hold_req_seq_.exchange(0)`，服务 handler 直接 `store(seq)`。
- 若两个请求在 RT 消费前先后到达，后者覆盖前者 ⇒ 前者 `seq` 永无回执，执行器只能等超时（N2/N4 的可观测性被削弱）。

**修复设计（采纳 D-2：入队 CAS，拒绝而非覆盖）**
```cpp
// 服务回调（executor 线程，非实时）
std::uint32_t expected = 0;
if (!hold_req_seq_.compare_exchange_strong(expected, seq,
                                           std::memory_order_acq_rel)) {
    resp->accepted = false;
    resp->message = "busy: a hold request is already pending";
    return;
}
resp->accepted = true;
resp->message = "queued";
```
- RT 侧仍单次 `exchange(0, acq_rel)`（读取即消费）。
- 在飞请求数 **≤ 1**，且**从不静默丢弃**：占用时调用方立即得到 `busy`。

**实时/并发/内存影响**：CAS 在非 RT 线程，成本可忽略；RT 侧不变（1 次 exchange）。无锁、无分配。

**失败语义**：`accepted=false + "busy"` 表示"槽被占"，调用方应短退避重试；若长期 `busy`（控制器未消费），说明控制循环停止 ⇒ 执行器按 T-H14 超时处理（此时"控制器是否冻结"确实未知，符合事实）。

**测试**
- 正：T-H10（两个不同 `seq` 连续到达：第一个 `busy=false`、第二个 `busy=true`；随后第一个仍收到回执）。
- 负：构造"第一个请求无回执"的用例必须失败（轮询 208 ms 内必须出现其 `seq`）。

**残留风险**：`seq` 回绕（`uint32`，0 保留，跳过 0；100 Hz 下约 497 天）。已在 §11 登记为非问题。

## B-3-4 — 独立原子 `seq` 与 `result` 可错配

**缺陷证据**
- Rev.1 用 `hold_done_seq_` 与 `hold_done_result_` 两个独立 relaxed 原子，发布侧分别 load 后写入同一条消息。
- 两次 load 之间若恰好有新回执写入，会得到"新 seq + 旧 result"或反之 ⇒ 执行器可能把 `result=1` 配到错误的 `seq` 上（假阳性：以为自己的请求被接受）。

**修复设计（采纳 D-3：打包单原子）**
```cpp
static inline std::uint64_t packHoldAck(std::uint32_t seq, std::uint8_t r) {
    return (static_cast<std::uint64_t>(seq) << 32) | static_cast<std::uint64_t>(r);
}
static_assert(std::atomic<std::uint64_t>::is_always_lock_free, "ack must be lock-free");
std::atomic<std::uint64_t> hold_ack_{0};
```
- 写入 `store(packHoldAck(seq, r), release)`；读取 `load(acquire)` 一次，再拆位。
- `seq>=1` 且 `result<=2`，故 `packed != 0` 恒成立；`0` 保留给"尚无回执"。

**实时/并发/内存影响**：8 字节对齐原子，x86-64/aarch64 均 lock-free（编译期 `static_assert` 兜底）；仍零分配、无锁。

**失败语义**：`hold_request_seq==0` ⇒ 从未有回执；非 0 时 `result` 必与同一请求配对（不可撕裂）。

**测试**
- 正：T-H13（10⁵ 次交替写/读，断言每次读到的 `(seq,result)` 都来自同一次写入——用写入序列的合法对集校验）。
- 负：把实现改回两个独立原子后 T-H13 必须能失败（在压力下出现非法对）。

**残留风险**：无；`result` 只用低 8 位，未来若扩展语义需重新分配位域。

## B-3-5 — T-H7 的回执延迟判据过乐观

**缺陷证据**
- Rev.1 `:149` 写"≤ 2 个控制周期 + 1 个状态周期（≈116 ms）"。
- 实测代码：`status_period_ticks_ = lround(1/(dt·rate)) = lround(12.5) = 13`（`dual_arm_qp_controller.cpp:316-317`，`dt=0.008`、`rate=10`）⇒ 1 个状态周期 = **13 拍 ≈ 104 ms**。
- `publishStatus()` 有两道早退：`++status_tick_ < status_period_ticks_`（抽稀）与 `trylock()` 失败（丢拍，`:837`）。一次 `trylock` 丢失 ⇒ 再等 1 个状态周期 ⇒ **worst ≈ 208 ms**。

**修复设计**：判据改为
- **nominal**：`≤ 1 状态周期`，即 `≤ 104 ms`（13 拍）；
- **worst**：`≤ 2 状态周期`，即 `≤ 208 ms`（含一次 `trylock` 丢失）；
- 执行器侧 ack 超时取 **300 ms**（= worst + 1 拍余量），并在 R1a 用 100 次请求实测最大延迟写进记录。

**实时/并发/内存影响**：无（仅判据与超时参数）。

**失败语义**：超过 208 ms 未观测到 L2 ⇒ 执行器不得宣称 L2/L3，直接进入 T-H14 超时路径。

**测试**
- 正：T-H7 100 次请求，最大延迟 < 208 ms。
- 负：把 `transport_status_rate_hz` 调到 1 Hz 后 T-H7 的 worst 判据必须失败（证明判据不是空转）。

**残留风险**：若未来把状态发布提高到每拍，本判据自然变严，需同步下调超时。

## B-3-6 — 锁存语义在 Rev.1 中被误列为"待裁项"

**缺陷证据（其实是"无缺陷，但表述错误"）**
- Rev.1 §9 只列了 Q1/Q2/Q3 三问，其中没有"锁存策略"；而核查报告指出该策略**已由 W1 实现固定**：
  - `resume()` 仅对 `Hold` 生效（`transport_task.cpp:274-302`）；
  - FAULT 需 `reset`、ABORT 需新 `start`；
  - 无任何自动迁移。
- 风险在于：读者可能误以为"保守锁存"仍是开放选项，从而在实现阶段擅自改动。

**修复设计（D-6：确认为不变式，不新增裁决项）**
- 在 Rev.2 §1 的 N5/N6 与 §4.5 语义表中显式写明：**`Hold` 期间收到的 `hold` 一律 `refused`，不刷新、不延长冻结；解除唯一途径是 `~/resume_transport`**。
- 明确"锁存语义沿用 W1，C7-A 不改变 `§4.7.1` 与 `:513` 三级锁存表"。
- **不**把"保守锁存"包装成 Q1/Q2/Q3 的选项（核查报告已指出编号不对应）。

**实时/并发/内存影响**：无（纯文档约束）。

**失败语义**：若实现中出现在 `Hold` 期间被新请求刷新/延长，则违反 N5 ⇒ T-H5 必须失败。

**测试**
- 正：T-H5（`Hold` 期间再发新 `seq` ⇒ `result==2`，`t_traj` 与 `failure_code` 均不变）。
- 负：构造"`hold` 延长了冻结"（比较 `t_traj` 或状态字段变化）必须被 T-H5 抓住。

**残留风险**：无。
