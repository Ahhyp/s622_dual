## §0 结论（一句话）

W1 的接线目标达成：控制器现在**真的读取并使用**物体任务三参数，`update()` 每周期从
`dual_arm_object_task`（唯一数学定义）取 `AnchoredObjectTask`，按冻结符号契约组

W0 记录的缺陷是「三键在 `src/`+`include/` 中 0 命中」；现在它们在启动日志里被打印，
并且 `w_center` 来自 yaml（该次用的是基础 profile `0.01`，见 §4.6）。

### 3.2 库真的链接了唯一数学定义

```
$ objdump -p install/lib/libdual_arm_qp_controller.so | grep NEEDED
  NEEDED               libdual_arm_object_task.so
  NEEDED               libdual_arm_qp_core.so
  NEEDED               libdual_arm_kinematics.so
```

`transport_task.hpp:9-14` 与 `.cpp` 中没有任何锚定/前馈/误差的重新推导：位置误差、速率映射、
`adjoint` 全部来自 `dual_arm_kinematics::anchoredObject*` / `decoupled*`，任务对象来自
`dual_arm_object_task::AnchoredObjectTaskBuilder`。满足了 R24 与 W0 的「同一算法只有一份定义」。

### 3.3 符号契约在装配点是显式且被测试锁死的

`transport_task.cpp:97-101` 的 `step()` 装配点：

```cpp
row.J              = task.J;          // d(e_O)/dq
row.e              = -task.e;         // QP 槽位要的是「剩余误差」
row.body_twist_ff  = task.v_ff;       // 前馈是 +v_d，不是 -v_d
row.valid          = task.inputs_ok;  // 绝不用 anchor_ok
```

S4-T4 用「只改一处」的方式验证这三行不可拆：`2v_d` 严格翻倍（2.63e-17）、正负反称
（1.35e-17）、方向点积为负。若把 `row.e` 或 `row.body_twist_ff` 的符号单独翻掉，T4 立即失败。

### 3.4 相对任务仍用冻结闭链，不是现算

`transport_task.cpp` 在 `latch()` 里取 `builder_.leftTrightGrasp()`（= `G_L⁻¹ G_R`）作为
`solve()` 的第二参，之后永不重算。S4-T3 断言它与 builder 的值逐元相等
（`max|Δ| == 0.0`），并**记录**它与 `kin_.leftTright(q0)` 在本 fixture 上只差 2.65e-13
——这正是 S2 冻结基线的含义（在标定构型上两者重合），而两者在运动过程中会分离；
控制器只用冻结值，所以不随测量误差漂移。

### 3.5 轨迹钟只在 committed 时前进（P0-1）

`transport_task.cpp` `advance(bool committed)`：`committed` 为真才 `t_traj += dt`，并钳在
`duration()`。S4-T3 跑 40 个周期全 committed，`t_traj = 0.3200 = 40 × 0.008` 精确相符。
反方向证据：S4-T5 的拒绝周期 `committed == false`，`t_traj` 不动（拒绝路径直接 `hold()` 返回）。

### 3.6 HOLD / RESUME（P0-1 后半）

- HOLD 冻结 `t_traj` 与 `q_cmd`，不自动恢复（`state_ == Hold` 时 `step()` 直接返回冻结值）。
- `resume(q)` 三项检查（`e_O` ≤ 5 mm / 2°、越限、`row.valid`），通过则从 `t_traj` 继续；
  未通过则把**剩余轨迹整体平移** `Δ = p̂ − p_d`，只改 `T_d.translation()`，
  `v_ff` 因平移不变而**逐位不变**（§4.2.2 的要求）。
- 连续 2 次未通过 → `abort("resume_failed")`。
- 这部分的端到端测试在 W7（S4-T19），W1 只落实现（规划就是这样分的）。

### 3.7 E6：近 π 在**求解前**拒绝（P0-5 的 E6）

`transport_task.cpp` `sample()` 计算 `e_obj_rot_rad`，若 `> cfg_.obj_rot_error_refuse_rad`
则置 `refusal_code = "object_error_near_pi"`；`step()` 见 refusal 立即 `hold()` 返回，
`dq` 保持零、`iterations` 保持 0。冻结阈值 `3.0915926535897933 = π − 0.05`（S3 收口决定）。

## §4 与规划的偏差（必须披露）

### 4.1 库 target 改名（必需，非设计选择）

`rosidl_generate_interfaces(${PROJECT_NAME} ...)` 会创建一个名为 `dual_arm_qp_controller` 的
**custom target**，与同名 `add_library` 冲突：
`add_library cannot create target "dual_arm_qp_controller" because another target with the same name already exists`。

处置：库 target 改名 `dual_arm_qp_controller_lib`，并用
`set_target_properties(... OUTPUT_NAME ${PROJECT_NAME})` 保持安装出的文件仍是
`libdual_arm_qp_controller.so` —— 插件 xml 的 `<library path="dual_arm_qp_controller">` 因此
无需修改，已实测该文件存在且 pluginlib 可加载。**对外接口未变。**

### 4.2 msg/srv 的两处命名约束

- `float64`：ROS 2 IDL 没有 `double` 基本类型；写成 `double` 会得到
  `rosidl_adapter.parser.InvalidResourceName: 'double' is an invalid message name`。
- 字段名必须小写：`start_world_T_object`（srv）→ `start_world_t_object`。注意
  `TrajectorySpec::start_world_T_object`（C++ 成员，S3 定义）**未改名**，两者名字不同是刻意的。

### 4.3 E2 / E4 / E8 未在 W1 落地

规划 §4.7.1 列了 E1–E8 八条，§7.1 把对应测试（S4-T21/T22）排在 **W3**。W1 只落：
E1 越限、E3 solve_fail_streak、E5 row 非法、E6 近 π、E7 臂距。
E2（`q_state` 过期）、E4（`update()` 间隔）、E8（执行器心跳）需要额外的订阅/心跳接口，
按规划留到 W3 —— **W1 的控制器目前不能声称具备完整的本地故障保护**。

### 4.4 用的是 3 参「外置行」重载

规划文字写「调 4 参重载」，实际 `dual_arm_qp_core` 提供的是
`solve(q, left_T_right_target, const ObjectTaskRow&)`（3 参，W2 时加的）。语义与规划一致，
方案文字里的「4 参」指旧的三任务行写法。**未改 QP 核心。**

### 4.5 接口放在控制器包内

`src/s622_task_interfaces` 在仓库里不存在（W0 清点已记录）。规划 §6 的 W1 文件清单本身
就把 `srv/`、`msg/` 列在 `dual_arm_qp_controller` 内，故照此实现；若后续需要跨包共享，
再拆独立接口包。

### 4.6 基础 profile 的 `w_center` 仍为 1e-2

规划 §6 只要求改 `config/dual_arm_qp_gazebo_controllers.yaml`（已改 1e-4 + 注记）。
`config/dual_arm_qp_controllers.yaml:34` 保留 `0.01`：该 profile 在 W1 范围内
物体任务恒关（IDLE 强制 `w_obj=0`），而 S3 legacy 逐位回归（S4-T3/T5c 的祖先）就是在
`w_center=1e-2` 下建立的；此时改它只会让「相对任务」的历史对比失去基线。
Gazebo 场景（S4.2）才用 1e-4。

### 4.7 抓取变换用硬编码默认值 + 参数覆盖

`TransportTaskConfig::object_T_left_tcp/right_tcp` 默认硬编码 S2 冻结基线的 16 元数值，
并可由控制器参数（16 元 row-major）覆盖；`parseIso3()` 校验刚性。没有引入 baseline yaml
解析依赖，避免控制器反向依赖 S2 冻结包。

## 10.2 A：把"保护"从断言改成可机检的三值报告

**改法。** `transport_task.hpp` 新增

```cpp
enum class ProtectionCoverage : int { Implemented = 0, Degraded = 1, Missing = 2 };
struct ProtectionItem { const char* id; ProtectionCoverage coverage; const char* note; };
struct ProtectionReport { bool complete; std::string summary; std::vector<ProtectionItem> items; };
ProtectionReport buildProtectionReport(bool e7_arm_gap_enabled, bool e8_heartbeat_enabled);
```

八条 §4.7.1 判据**逐条**给出覆盖等级与理由（`note` 里写清为什么，不写"已实现"三个字了事）。
`~status` 新增 `protection`（摘要串）、`protection_complete` 两个字段；`on_configure` 时按实际参数
计算并打一条日志（不完整时 `WARN`）。

**结论必须坦白：S4.1 的默认配置下 `protection_complete == false`。**
报告串实测为

```
PARTIAL(e1_joint_bounds,e3_solve_streak,e4_deadline,e5_row_valid,e6_near_pi)
  degraded(e2_state_staleness)
  missing(e7_arm_gap,e8_executor_heartbeat)
```

- `e2_state_staleness` **本层不可测**：`ros2_control` 交来的是纯 `double`，没有采样时间戳；
  `readState()` 失败时控制器直接 `return ERROR`，所以"读失败"这条路径已经覆盖；
  但"值有限但已经冻结"的传感器在本层**无法与正常运行区分**。写 `Degraded` 而不是 `Implemented`。
- `e8_executor_heartbeat` 默认 `Missing`：W1 里还没有执行器。设
  `require_executor_heartbeat:=true` 后它变成 `Implemented`，且判定规则**失败即关闭**
  （从未收到心跳 = 陈旧）。该规则抽成纯函数 `executorHeartbeatStale(seen, last_s, now_s, timeout_s)`
  并单测，因为"实现了却不可测"正是审查批评的写法。
- `e7_arm_gap` 在 `collision_d_stop <= 0` 时记 `Missing`，而不是假装臂距联锁在工作。

**证据。**
1. 单测 `TransportLatches.A_ProtectionReportNeverClaimsWhatIsNotWatched`：
   默认配置 `complete == false`，`degraded` 恰 1 条、`missing` 恰 1 条、条目总数 == 8；
   两个联锁都开时 `missing(` 不再出现，但 `complete` 仍为 `false`（e2 仍在）。
2. 单测 `TransportLatches.A2_ExecutorHeartbeatStaleRule`：从未收到 / 恰好 100 ms（放行）/
   101 ms（陈旧）/ 时钟回跳（不放行）/ NaN（关闭）五种输入。
3. **台架实测**（mock，无 Gazebo）：`ros2 topic echo --once /dual_arm_qp_controller/transport_status`
   - 默认 yaml：`protection` 含 `missing(e7_arm_gap,e8_executor_heartbeat)`，
     `protection_complete: false`，`executor_heartbeat_required: false`；
   - 覆盖 `require_executor_heartbeat: true` 的临时 params 后：`e8_executor_heartbeat`
     从 `missing` 移入 `PARTIAL(...)`，`executor_heartbeat_required: true`，
     `executor_heartbeat_seen: false`，`executor_heartbeat_age_s: -1.0`。
   （`ros2 topic echo` 对长字符串会截断显示，完整串以单测输出为准。）

**没做到的（明确列出）。** E8 的"实际 HOLD 动作"没有在台架注入验证：
需要有一个执行器发心跳再停发，那是 W2 的东西。本轮只验证了规则与状态上报。

## 10.3 B：拒绝在非标准构型下启动搬运

**问题。** 运输的锚定起点是 `T̂_{O,L}(q_grasp)`。若允许在任意构型调用 `~/start_transport`，
轨迹起点会被悄悄重定义成"当前位姿"，于是物体目标、闭链残差、验收数字全部失去可比性——
这是**静默重构**，不是功能。

**改法。**
- `TransportTaskConfig` 新增 `home_q`（默认 `defaultHomeQ()` = S2 冻结 `q_grasp12`）
  与 `start_pose_tolerance_rad`（默认 `0.05` rad）。
- `TransportTask::start()` 计算 `max|q - home_q|`，超容差即拒绝并给出可读原因（含具体关节号）。
- `onStartTransport`（服务线程）先用当前 `q_state_` **预检**，不合格立即回
  `accepted: false`，不进实时路径。
- `~status` 新增 `start_pose_deviation_rad` / `start_pose_ok`，且在 **IDLE 也会算**
  （用 `q_state_`），这样操作员调服务之前就能看出会不会被拒。

**证据。**
- 单测 `B_StartIsRefusedAwayFromTheStandingConfiguration`：`q[3] += 0.2`（4 倍容差）时
  拒绝，消息含 `start pose deviation` 与具体关节；`tolerance = 0` 时放行（逃生门）；
  同时断言 `startedFromHome()` 与 `startPoseDeviation()`。
- 台架实测：mock 台架把 12 轴置零（不是 S2 的 `q_grasp`），`transport_status` 报
  `start_pose_deviation_rad = 2.795036909814`、`start_pose_ok: false`。
  这正是想要的：**台架当前构型确实不是标准起点**，不报 `true` 才是对的。

**没覆盖的。** 只比 12 个关节值的最大偏差；不检查是否碰撞、夹爪是否张开、物体是否真在指间。

## 10.4 C：`~/resume` 只对 HOLD 有效，且没有自动恢复

| 状态 | `~/resume` | 说明 |
|---|---|---|
| IDLE | 拒绝，码 `resume_requires_hold` | 没有在跑的搬运 |
| RUNNING | 拒绝，码 `resume_requires_hold` | 本来就在走 |
| HOLD | 允许（三项检查） | 唯一入口 |
| HOLD → 连续两次检查不过 | 转 **ABORT**，码 `resume_failed` | 不再"再试一次" |
| FAULT | 拒绝，码 `fault_requires_reset` | 需 `~/reset_transport` |
| ABORT | 拒绝，码 `abort_requires_start` | 需新的 `~/start_transport` |

另外修掉一处**假标签**：`update()` 原先把所有非周期类健康故障都写成 `stale_state`
（跟踪误差、注入停滞、求解失败全被叫"状态陈旧"）。现在按
`stream_health_monitor` 的真实原因映射：

```
"non-finite state/command" -> non_finite_state
"control period overrun"   -> deadline_missed
"injected stream stall"    -> stall_injected
"tracking error ..."       -> tracking_error
"QP solve failures"        -> qp_solver_failed
（其它）                    -> stream_unhealthy
```

**证据。** 单测 `C_ResumeIsHoldOnlyAndTwoFailuresAbort`（IDLE 拒绝 / 第一次失败平移后回 RUNNING /
第二次失败转 ABORT / ABORT 不可 resume / FAULT 不可 resume 需 reset / reset 回 IDLE 且 `failure_code` 清空）。
失败注入用的是 **yaw 30°**：`resume_shift` 只平移不改姿态，所以姿态误差不会自愈，
才能真正测到"连续两次失败"这条路径。

`config/dual_arm_qp_gazebo_controllers.yaml` 末尾新增注释块，逐个参数写明
