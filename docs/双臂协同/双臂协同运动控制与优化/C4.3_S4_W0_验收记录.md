## §5 端到端复核

迁移不只影响单元级数值，还可能通过链接顺序/内联变化影响整条闭环。因此用 S3 的 W8 运行器复跑两个场景（`--jobs 2 --sweep-samples 8`，与 S3 验收同参数），并与 S3 冻结表**逐格比对**：

| 场景 | ok | 终点位置 [m] | 终点姿态 [rad] | `max e_rel` | `max e_obj` | `max s_obj` | committed |
|---|---|---|---|---|---|---|---|
| `control`（只跑相对任务） | ✗ `terminal_pose_error` | `6.000e-02` | `9.196e-14` | `3.833e-13` | `7.810e-02` | `0.000e+00` | 638 |
| `ff_1`（`w_obj=1`，前馈开） | ✓ `ok` | `2.972e-08` | `2.750e-10` | `4.250e-05` | `5.022e-05` | `6.956e-09` | 638 |

与 `C4.3_S3_验收记录.md` §5 的冻结表**九个数值列全部相同**（`control` 6.000e-02 / 9.196e-14 / 3.833e-13 / 7.810e-02 / 638 / 0；`ff_1` 2.972e-08 / 2.750e-10 / 4.250e-05 / 5.022e-05 / 638 / 0）。

结论：迁移在端到端层面同样不可分辨。`control` 依旧必须以 `terminal_pose_error` 失败（它差 6.000e-02 m 正是轨迹要求的位移），这条负控制没有被迁移"抹平"。

## §6 偏差、限制与未做的事

1. **命名空间随包名改了**（`dual_arm_transport_mock` → `dual_arm_object_task`）。这是 W0-5 允许的唯一接口变化，代价是 11 个文件的性质替换；收益是生产包里不再出现"mock"字样。
2. mock 的 `mock_loop.hpp` 里保留了一条 `using namespace dual_arm_object_task;`。它是别名不是副本，但确实让 mock 内部仍以非限定名引用这些类型。
3. 测试**仍留在** mock 包里（没有随源码迁到新包）。理由：W0 的验收要求是"S3 所有原测试通过"，搬测试会改变口径；新包现有的测试只有那一条静态守卫。
4. 本包目前**没有**自己的单元测试覆盖 `build()` 的数值（覆盖仍在 mock 的 `test_object_task_c43s3` 等）。若后续要把 mock 删掉，这些测试需要先迁移。
5. 未做：W1（控制器接线）、Gazebo 相关任何工作。
6. 与规划 §W0 措辞的两处**有意偏差**（已同步改规划）：① 轨迹头文件沿用 `trajectory.hpp` 而非规划里写的 `frozen_trajectory.hpp`（改名的收益只是措辞，代价是再多改 4 个调用点）；② 新包不含 `version` 单元（`version.hpp/cpp` 记录的是 mock 可执行文件的构建溯源，不属于物体任务本身）。
