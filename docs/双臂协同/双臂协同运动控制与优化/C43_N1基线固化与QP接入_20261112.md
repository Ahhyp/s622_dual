# C43 N1基线固化与QP接入实测（2026-11-12）

依据：[11月12日后续规划](C43_后续规划与原规划对照_20261112.md)。本次先关闭上一轮GUI，随后只运行隔离的无GUI实验，未停止此前保留的其他无界面仿真。

## 1. 术语和本轮目标

- **固定驱动力**：搬运时每根手指持续接受5 N关节驱动力命令。不是FT传感器闭环恒力控制。
- **JTC**：Joint Trajectory Controller，关节轨迹控制器；参考组把预先计算的轨迹分别交给两臂，用同一个仿真起点同步执行。
- **FT**：Force/Torque，力/力矩传感器。本轮记录四指读数，未用它们闭环调节夹持力。
- **QP**：既有12轴二次规划控制器；根据物体参考运动、两手相对关系与已有约束在线计算关节命令。本轮复用已有求解器，没有重写QP核心。

固定轨迹能成功，是有效的参考组；要评价QP仍须在同工况下量化误差、节拍、约束和异常行为，不能因为“用了QP”就预先断言所有指标变好。

本轮完成N1的安装资源整理与复跑，并推进到N2的控制器级小幅/完整物理搬运试验。**没有把本轮控制器验证标成正式executor/W7完成。**

## 3. N2：真正切到已有QP

新入口支持`--backend qp-smoke`和`--backend qp-carry`。仍先通过JTC接近并建立四指固定驱动力夹持，再执行：

1. QP先加载为inactive。
2. 为本次候选生成独立参数副本：`home_q`改为新抓取候选，`object_T_left_tcp/right_tcp`由该候选与样件初始位姿计算，使用16元素row-major齐次矩阵。
3. STRICT切换：同时停用两个臂JTC，激活QP。
4. 查询控制器状态和claimed_interfaces：QP必须独占全部12个position接口，两个臂JTC inactive；手指JTC不激活。
5. 经既有StartTransport服务发送物体参考轨迹，记录TransportStatus和真实物体运动。
6. 完成/确认落座后reset，STRICT切回JTC，核验互斥状态，再释放与退回。

没有改既有QP求解器、正式状态机、冻结S2基线或已有QP保护阈值。运行参数副本与变换写入`qp_adapter.json`，控制器归属分别写入`ownership_qp.json`、`ownership_jtc_restored.json`。

### 小幅验证

`qp_smoke_r1`由实际QP完成10 mm抬升、保持和放回；物体峰值抬升约**10.009 mm**，之后释放、退回，样件留在源支撑。状态记录包含IDLE/RUNNING/COMPLETE，控制资源切换检查通过。

这是控制器实际接管的证据，不是仅生成了QP参数或运行了离线求解。

## 4. 首次完整QP尝试失败：目标到了，但尚未支承

`qp_carry_r1`已完成60 mm抬升、120 mm横移和下降。随后样件中心约z=0.275027 m，比名义落座高度高约**0.027 mm**。接触消息没有目标支撑对，流程在`before_release`拒绝继续：

```text
RuntimeError('destination support contact missing before release')
```

未将该轮补写为成功，未删除原始记录。它再次说明运动学估计或目标位置在容差内，不保证物体已经接触支撑。失败后的归零/清理属于仿真收尾，不是一次成功的释放阶段。

### 修复方式

不放宽支撑接触检查。新增明确记录的QP末段`seat`：最多向下0.2 mm、控制器轨迹时长2 s；这是独立诊断运动配置，不是更改正式安全阈值。

检测到最近5条完整消息均含目标支撑接触后，调用已有HoldTransport服务，使用非零序号，并要求Status给出相同序号、applied结果和HOLD状态。得到ACK后才reset并切回JTC。之后再次确认目标支撑存在，才能张爪。

若下探结束仍没有支撑/HOLD确认，仍失败；没有无限下探、没有关闭接触守卫。该方法是有界接触落座，不是FT闭环力控制。

### 修复后首轮结果

`qp_carry_r2`得到HOLD ACK：seq=1，t_traj≈25.512 s。整个物理流程完成并通过同级原生接触审计：

- 峰值抬升约60.032 mm；最终目标位置误差约**1.136 mm**。
- 搬运最大物体姿态偏转约**0.097°**；四指最大STL顶点深入见证约**0.0107 mm**。
- 四指空中持物、保持/横移无支撑、落座后无机器人接触及无非手指机器人碰样件均通过。
- QP负责主抬升、保持、横移、下降和有界落座；接近、释放后的退回由JTC完成。

当前工作区安装入口的复测`qp_carry_r3`也通过同级审计，并确认支撑接触对应的HOLD ACK。

|---|---:|---:|---:|---:|---:|---|

## 5. 新发现的时序问题：5 ms物理步长与8 ms控制配置

同日后续：2 ms隔离配置已验证t_traj/仿真时间约1.00003，并完成小幅与完整搬运审计。旧5 ms参考保留；新试验显式使用`--physics-step-ms 2`。完整落点误差约2.930 mm，未据此宣称精度优于旧参考；仿真频率与墙钟RTF分列。详见[调度对齐验证](C43_仿真调度对齐验证_20261112.md)。下面保留原问题记录。

配置为Gazebo max_step_size=0.005 s、controller_manager update_rate=125 Hz、QP dt=0.008 s。实际日志拟合得到：

`QP t_traj / Gazebo sim time ≈ 0.8000`

这与5 ms步长下控制器实际约每10 ms更新一次、每次轨迹时钟推进8 ms一致；据状态推算约100次更新/仿真秒。它是日志推断，不是原生实时性能认证。

因此QP设置6 s的一段实际约需7.5 s仿真时间，不能直接拿标称duration与JTC节拍比较。当前未为了让表格一致而改物理步长、QP dt、deadline保护或冻结周期。后续正式集成和W8性能比较前，须对齐实际调度周期并重跑受影响基线。

同时区分：

- 新脚本的阶段等待已改用仿真时间；
- QP内部`t_traj`仍按既有控制器dt推进，上述调度不整除是另一层问题；
- 控制器估计e_obj并非Gazebo真实物体误差；求解耗时字段在未启用测量时的0不能当成零耗时。

## 7. 范围与下一步

本轮是**现有QP控制器驱动的物理搬运实验**。正式`dual_arm_transport_executor`尚未接入该物理支路；不能标记正式W7、W8/W9全矩阵或真机完成。

已定位的正式对接差异：

1. 当前诊断轨迹增加`hold`、`seat`相位，正式PhaseDriver仅接受原约定相位，不能直接透传后宣称正式状态机已兼容。
2. 原理想单附着/夹爪JTC配置与当前无weld/原生手指驱动力必须分配置，不能删除原attach守卫来凑成功。
3. 本次验证的是局部落座HOLD/ACK，不等于完整executor的心跳、锁存、异常恢复与故障矩阵。
4. Controller保护报告明确为PARTIAL，包含state_staleness降级、arm_gap与executor_heartbeat缺失；没有把它改写成protection_complete。
5. 正式性能对照前先解决/明确5 ms与8 ms调度及指标时钟，之后做同工况JTC/QP比较。

下一步应把物理夹持、落座接触和控制器切换接入正式executor的明确配置与合法相位映射，沿用已有状态/ACK语义，再做必要故障验证。当前新增的安装基线和QP控制器实验保留为可重放参考。
