## 2. 一次假 PASS 的回溯登记（不可作为证据）

`after_cycles=0` 时 `T_H17_PositiveControl_FailureExitStopsTheController` 曾 **PASS（2829 ms）**。

**该 PASS 无效**：正控制用例当时从不调用 `start_transport`，而武装点在 `onStartTransport` 内 ⇒ 预算恒为 0 ⇒ 注入从未触发；状态流停止是**别的原因**。改为 `after=10` 后同一用例立刻 FAIL（`status kept flowing => the injected ERROR was not taken`），暴露了这一点。

修正后的正控制**先 start 再断言**，并把延迟抬到 150 拍（1.2 s，远大于 10 Hz 状态下 4 条消息所需时间），使「状态流停止」不可能被解释成「搬运跑完了」。

判据链（全部基于订阅到消息的时间戳与计数，不用 sleep、不用 `timeout+grep`）：

1. 服务 `start_transport` / `hold_transport` 均 ready；
2. `status_count_ > 2` —— 控制器存活且在发布（IDLE）；
3. `startTransport(400)` 成功；
4. `status_count_ > 4` —— **start 确实生效**（否则第 6 步的“停止”无意义）；
5. 等待 `now − last_status_s_ > 0.40` —— 注入 ERROR 生效，控制流停止；
6. `hold seq=41` 提交后，观察 500 ms：`ack_msgs_ == 0` 且 `max_ack_seq_ == 0`。

第 5 步成立即证明：参数被读到、预算被武装、`#ifdef` 分支被执行、ERROR 后不再有控制周期。

## 4. [PROOF] T-H17a-2：失败周期不会 drain 已入队请求（仅代码顺序）

`update()` 内的执行顺序（`src/dual_arm_qp_controller/src/dual_arm_qp_controller.cpp`）：

```
readState()                      // :~678，读失败在此返回
[#ifdef] 注入点                  // :692-700，新插入，返回 ERROR 前不再往下走
hold drain（exchange/hold/ack）  // 紧随其后
applyPendingStart()
const bool transport_active
安全层 / transport 分支 / IDLE 分支
```

⇒ 只要注入返回 `ERROR`，同一周期内的 **drain 不会执行**，`hold_req_seq_` 保持非零、`hold_ack_` 不更新、`publishStatus()` 也不会被调用。

**没有动态观测到的部分**（不得写成动态 PASS）：
- 未能构造「请求已入队 → 同一周期注入失败 → 请求滞留」的端到端时间线。原因是 drain 每周期都跑（周期 8 ms），从外部无法把请求稳定落在失败周期内；而要让它稳定就得让注入由「请求入队」事件触发——**这正是被否决的方案 B**，故未实现。
