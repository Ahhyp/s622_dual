## 2. drain 块（实时线程，唯一新增的控制路径）

```cpp
const std::uint32_t hold_seq = hold_req_seq_.exchange(0, std::memory_order_acq_rel);
if (hold_seq != 0) {
    const bool hold_ok = transport_active && transport_->running();
    if (hold_ok) transport_->hold("hold_by_executor", HoldOrigin::Executor);
    hold_ack_.store(packHoldAck(hold_seq, hold_ok ? kAckApplied : kAckRefused),
                    std::memory_order_release);
}
```

位置：`applyPendingStart()` 之后、`const bool transport_active` 之后、安全层（臂距胶囊 `:696`）之前。
- 无早退 ⇒ 本拍后续每条路径都会 `publishStatus()`（`result=1` 与 `result=2` 都在同拍可见）。
- 在 `if (transport_active)` 之外 ⇒ `Idle` 也 drain（否则槽永久占用）。**实测证据**：T_H3 在 IDLE 状态下发请求，4 s 内收到 `result=2`，且后续 T_H1 的请求仍被接受 ⇒ 无饥饿。

## 3. 实测结果（Layer 3：真控制器 + mock_components 台架，125 Hz）

| 用例 | 结果 | 实测 |
|---|---|---|
| T-H9 origin 字符串 | PASS | `""` / `"controller"` / `"executor"` |
| T-H11 `seq==0` | PASS | `accepted=false`，`message` 含 `invalid seq`，回执 seq 仍为 0 |
| T-H3 Idle 拒绝但回执 | PASS | `hold_request_seq=7`、`result=2`、`state=IDLE` |
| T-H1 Running→HOLD | PASS | `result=1`、`state=HOLD`、`hold_origin=executor`、`failure_code=hold_by_executor` |
| T-H6 回执延迟 | PASS | **6.8 ms**（执行器预算 300 ms） |
| F1/F2 冻结 | PASS | 300 ms 后 `t_traj` 逐位不变、`state` 仍 HOLD |
| T-H4 连续两次请求 | PASS | 两次 `accepted=1`（首次已 drain），`ack_seq=11`；无静默丢失 |

**300 ms 的表述**：这是**执行器侧超时预算**，不是控制器 ACK 的数学上界。Rev.2.1 (P-1) 使新回执立即发布（实测 6.8 ms），但每次 `trylock()` 失败仍会把发布推迟一个状态周期（104 ms），丢失次数无已证明的有限上界。不得把 6.8 ms 写成最坏情况保证。
