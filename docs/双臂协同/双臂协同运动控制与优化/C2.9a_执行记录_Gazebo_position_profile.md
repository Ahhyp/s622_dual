## 1. 做了什么

让 Gazebo 里的**臂关节暴露 position 命令接口**（原来是 velocity/JTC），使 QP 控制器能驱动 Gazebo：

| 改动 | 内容 |
|---|---|
| `s622_gazebo_ros2_control.xacro` | 新增宏参数 `arm_command_mode:='velocity'`；position 模式下臂改用 `position` 接口，并加 `position_proportional_gain=1.0`（gz_ros2_control 的 P 型位置伺服） |
| `s622_dual_arm_gazebo.urdf.xacro` | 新增参数 `arm_command_mode`、`controllers_yaml`（传给 gz_ros2_control 插件） |
| `dual_arm_qp_gazebo_controllers.yaml` | `update_rate: 125` + JSB + 双手 JTC + **QP 控制器**；**不含臂 JTC**（互斥） |
| `dual_arm_qp_gazebo_controllers_sweep.yaml` | 同上 + `test_sweep_amp_m=0.06`（闭环运动验证用） |
| `s622_dual_arm_qp.launch.py` | 精简独立 launch：headless Gazebo + RSP + spawn + 控制器；**不动**原 JTC launch |

xacro 校验：position 模式 **16 个 position 接口 / 0 个 velocity**；默认模式 12 velocity + 4 position（不变）。

profile 选择用**环境变量**（`QP_CONTROLLERS_YAML`）而不是 launch 参数——
因为 `load_xacro` 的 mappings 必须是**纯字符串**，塞 `LaunchConfiguration` 会在展开时报
`replace() argument 2 must be str, not LaunchConfiguration`（现网的 JTC launch 里也踩过同类坑）。

## 3. ⚠️ 发现 1：Gazebo 里 `period` 是**合成值**

`PeriodMonitor` 在 Gazebo 下报告 `mean=P95=P99=max=8.000 ms`、`overruns=0/2500`——
但用 `overruns` 计数与日志时间戳反算，**实际墙钟更新率只有 58.0 Hz**。

原因：**gz_ros2_control 传给控制器的 `period` 恒为 `1/update_rate`**，不是实际经过时间。
→ C2.R2 的"周期超期检测"在 Gazebo 里**永远不会触发**，它只在真机（`controller_manager` 真实计时）下有效。
**修正建议（C2.R2 的补充）**：控制器应**同时**用 `time` 参数自行差分算实际周期，而不是信任 `period`。

> ✅ **已修复**：见 [`C2.R2b_执行记录_实际周期测量.md`](C2.R2b_执行记录_实际周期测量.md)。
> 修复后追加一个更准确的结论：**Gazebo 里 `time` 是仿真时钟**，所以实测差分也是 8 ms——
> 周期监控只在**真实时钟**（mock/真机）上有意义，Gazebo 的 RTF 差距控制器看不到。

## 4. ⚠️ 发现 2：Gazebo RTF ≈ 0.46，仿真跑不满实时

58 Hz / 125 Hz = **0.464** → 本机 Gazebo 的实时因子约 0.46。
也就是说：**控制器在仿真时间里是 125 Hz**（`period` = 8 ms 是设计周期），
但墙钟上每秒只推进约 58 个控制拍。

**含义**：Gazebo **不能**用来验证"墙钟实时余量"；它只能验证**单拍计算量**与**闭环动力学行为**。
后者（solver P99 0.2 ms、相对位姿保持、CBF）依然有价值，前者的最终验收只能在真机做。
