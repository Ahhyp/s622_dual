## 4. Q1/Q2/Q3：正式申请书与设计方向的**差异对照**（不擅自替换选项）

| 方向（本次裁决基准） | 申请书的对应内容 | 对应关系 | 差异 / 结论 |
|---|---|---|---|
| **Q1 倾向独立 `HoldTransport` 最小接口**（不动 QP 数学、保持兼容） | §3 五方案 + 推荐 **方案 A**（新增 `HoldTransport.srv`）；§4.3 用独立原子量而非 `pending_cmd_`；§5 声明不触碰 QP 核心 | **实质一致**（方案 A 已体现该方向） | 申请书的 §9-Q1 **不是**这个问题，而是“`hold_origin` 用 `string` 还是 `uint8`”——**正交的子细节**。不得把两者混为同一编号。 |
| **Q2 倾向显式 ACK + 状态确认**（超时/拒绝/重复/状态不一致） | N2/N4/N5 + §4.2 三个回执字段 + §6 T-H1/H2/H5/H7 | **部分一致** | 申请书的 §9-Q3 才是“是否必须等回执”，与方向同向；但**缺**三类明确定义：① 拒绝时 `hold_request_result=2` 的判定延迟（回执可能延后一个状态周期，见 B-3-2）；② 单个在途请求被后续请求**覆盖丢失**（`exchange(0)` 单槽）没有任何规定；③ `seq` 与 `result` 是两个**独立原子量**，读侧可能配错（B-3-3）。 |
| **Q3 倾向保守锁存 + 显式恢复**（禁止自动恢复、禁止过期消息解 HOLD、FAULT/ABORT 不可被 RESUME 绕过） | §4.4 语义表（`Complete/Idle/Hold/Abort/Fault` 一律拒绝）+ W1 既有 `resume()` 三重守卫（E-10 `:274-302`）+ §4.4 最后一行“`hold_origin` 归 0 仅在 `~/resume` 后” | **一致，但申请书未把它列为待裁决项** | 申请书把它当**既定设计**而非 Q；本次方向与之相容。需补一条**明确条款**：“过期/重复的 hold 请求不得解除 HOLD；解除只允许 `~/resume` 显式触发”。 |

**结论**：三项设计方向与申请书**无实质冲突**，但存在三类问题：
1. 编号错位（方向 Q1 ↔ 申请书 §3 选型；方向 Q2 ↔ N2/N4 + §9-Q3；方向 Q3 ↔ §4.4，且申请书未设问）；
2. 申请书 §9-Q1（`string` vs `uint8`）与三项方向**无关**，属实现细节；
3. 方向 Q2 要求的三条边界在申请书中**缺失**（见 B-3-1/B-3-2/B-3-3）。

## 6. 裁决

- 方案方向与三项设计基准**相容**（§4），且**不触碰** QP 数学/求解器/轨迹/冻结基线（V4）——这是最关键的一条，成立；
