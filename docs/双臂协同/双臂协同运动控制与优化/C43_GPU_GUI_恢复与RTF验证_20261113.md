# C43 GPU GUI 恢复与 RTF 验证（2026-11-13）

本轮找到了能正常显示的 RTX 4000 渲染方式：**物理服务器留在 s622_yep，GUI 在独立的 NVIDIA 容器内通过 VirtualGL EGL + X11 proxy 显示。** 用户已确认该路径能正常看到机械臂与场景。直接 NVIDIA GLX 路径仍黑屏，不能只用nvidia-smi或glxinfo成功作为显示通过证据。

## 历史记录与本次复查

先读了[环境部署文档§8/§10](../../环境部署_Ubuntu26.04_Docker.md)：10月29日曾成功启用GPU，后因Wayland/双显卡环境的3D视口黑屏，采用“服务器GPU、GUI Mesa”的拆分方式。11月11～12日C43演示也显式选择了Mesa软件渲染。

本次实查：

| 检查 | 实际结果与处理 |
|---|---|
| 宿主机 | Quadro RTX 4000，驱动595.99.02，nvidia-smi正常 |
| 原s622_yep | 已有--gpus all及graphics能力，驱动库也在；但nvidia-smi报NVML Unknown Error，直接NVIDIA GLX创建上下文失败 |
| 相同基础镜像的新临时容器 | nvidia-smi正常，NVIDIA GLX为OpenGL 4.6，RTX 4000；说明不必重装宿主驱动 |
| 新容器直接Gazebo GUI | nvidia-smi看到图形进程约222 MiB，但用户确认整个3D区域黑屏，故该方案失败 |
| Intel /dev/dri/renderD128对照 | DRI3失败并回退llvmpipe，Accelerated=no；不当作硬件加速成功 |
| VirtualGL首次EGL探测 | 容器只有Mesa EGL厂商描述，仍选到llvmpipe；只加vglrun不够 |
| 显式NVIDIA EGL描述 | EGL vendor固定到libEGL_nvidia.so.0，vglrun的glxinfo确认RTX 4000；Gazebo图形进程约458 MiB，用户确认画面正常 |

NVIDIA官方记录了legacy runtime hook容器可能丢失GPU设备访问并报NVML Unknown Error的情况，`systemctl daemon-reload`是其中一种触发方式。本次没有足够记录证明当时的具体触发命令，不能直接断言就是它。新容器额外显式请求nvidia0/nvidiactl/nvidia-modeset设备，采用官方列出的预防方式之一；没有修改Docker全局cgroup驱动、重启Docker服务或重建原仿真容器。[NVIDIA故障说明](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/troubleshooting.html#containers-losing-access-to-gpus-with-error-failed-to-initialize-nvml-unknown-error)

VirtualGL EGL负责GPU离屏渲染，proxy负责把画面送到当前X11/Xwayland桌面，从而绕过本次失败的直接GLX显示路径。其配置依据[VirtualGL官方说明](https://raw.githubusercontent.com/VirtualGL/virtualgl/main/doc/advancedconfig.txt)中VGL_DISPLAY及VGL_COMPRESS，而不是强制软件OpenGL。

## 一键运行

宿主机仓库目录执行：

```bash
python3 src/gz_launch/scripts/run_c43_executor_gpu_gui.py
```

可选：

```bash
# 仅准备GPU窗口镜像，不启动仿真
python3 src/gz_launch/scripts/run_c43_executor_gpu_gui.py --build-only
# 窗口帧率上限，默认30；只改变显示
python3 src/gz_launch/scripts/run_c43_executor_gpu_gui.py --fps 30
```

首次从s622_yep当前基础镜像构建独立GUI镜像；VirtualGL版本3.1.5，官方deb下载地址与SHA256固定在 `src/gz_launch/docker/gpu_viewer/Dockerfile`。镜像标签包含基础镜像ID，不覆盖原镜像。

脚本读取当前DISPLAY/XAUTHORITY，只读挂载显示授权和工作区，给每轮建立唯一IGN分区与GUI容器。仿真仍为 `--backend qp-executor`，原容器执行 `--external-gui --keep-open`，实际Gazebo服务器带 `-s`。GUI运行在新容器，使用：

```bash
/opt/VirtualGL/bin/vglrun -d egl -c proxy ign gazebo -g -v 4
```

NVIDIA EGL描述在镜像 `/opt/VirtualGL/nvidia_egl.json`，由 `__EGL_VENDOR_LIBRARY_FILENAMES` 明确选择；GUI默认VGL_FPS=30。关闭GPU窗口或宿主命令Ctrl+C，脚本只按该轮输出目录清理对应lab和GUI。原有无关headless进程42900、299501不在匹配范围内。保持窗口打开时，实验结束后服务器也保留，方便观察末态。

原 `run_c43_executor_gui.sh` 仍是Mesa回退入口；本次没有把它悄悄改成另一种渲染器。原 `--gui` 参数行为保留；新加的 `--external-gui` 与它互斥。

## RTF与CPU证据

原软件GUI轮次：`log/c43_executor_20261113/gui_20261113T050545_4148612/`，已完成COMPLETE。主搬运轨迹日志拟合RTF为0.336129，t_traj/仿真时钟为1.000004；用户观察GUI常在40%左右。此前GUI进程ps平均CPU约403%，相当于约4个核心。

新的GPU演示：`log/c43_executor_gpu_20261113/gpu_gui_20261113T053926_932309/`。短时10条WorldStatistics的RTF范围0.4928～0.5858，均值0.5384；新GPU窗口3秒CPU采样约87.92%。这是本机单次运行/短时采样，不是严格同时间段的GPU消融；显示帧率上限、运行阶段及系统负载均影响数字。

完整主搬运日志拟合结果：

| 指标 | 原软件GUI | 独立GPU/VirtualGL GUI |
|---|---:|---:|
| 仿真秒/墙钟秒（RTF） | 0.336129 | 0.432069 |
| t_traj/仿真时钟 | 1.000004 | 0.999998 |
| 推算控制更新/墙钟秒 | 42.016 | 54.009 |

本次RTF提高约28.54%，同样轨迹的现实耗时减少约22.20%。短时WorldStatistics的0.5384不能替代完整QP搬运均值0.432069。作为其他日期的参考，11月12日无GUI物理r6主搬运RTF为0.47096；本次GUI加速并未使物理仿真实时化，也不是严格重复次数冻结后的性能结论。

新GPU演示退出码0，C++状态到COMPLETE，物理审计与14项状态协议审计通过，末态目标误差2.866512 mm，姿态峰值0.076382°。机器人URDF、world、控制器、候选、轨迹和任务输入归一化后与原软件GUI轮次完全相同。新物理服务器3秒CPU采样约117.22%，旧软件GUI进程已退出。原来两轮无关headless仿真未停止。

汇总：`log/c43_gpu_20261113/results.json`。GPU窗口与该轮服务器当前保持打开；未为验证清理逻辑而关闭用户正在观察的窗口。

## 范围与剩余瓶颈

本轮修改显示和进程组织，不改变2 ms物理步长、8 ms QP配置、5 N/指驱动、模型、接触参数或搬运路径。GPU窗口加速不等于物理求解器或QP求解器也迁移到GPU；CPU上的接触、关节控制、状态桥接和记录仍然存在。RTF没有达到1，不能通过把物理轨迹设得更快来冒充实时性能改善。

当前可用方案是独立GPU GUI。原s622_yep的失效GPU访问尚未原位修复，直接NVIDIA GLX黑屏也没有被全局修复；本轮避免为此中断其他任务。再次登录桌面、cookie变化或原服务器退出后，应重新运行入口，不能复用旧授权文件或旧IGN分区。
