## P-1 回执可见性：把"抽稀"改为"变更即发"

### 问题（核查报告 §4）
Rev.2 的回执依赖 `publishStatus()` 的 10 Hz 抽稀（`status_period_ticks_ = 13`，104 ms）与 `trylock()` 丢拍。
- 实测时序：`8 ms（drain）+ 104 ms（抽稀）+ 104·m（m 次 trylock 丢失）+ 1 ms（DDS）+ 8 ms（executor tick）`。
- `m=0` → **121 ms**；`m=1` → **225 ms**；`m=2` → **329 ms > 300 ms**。
⇒ **300 ms 不是硬上界**，只能覆盖 `m ≤ 1`；而 `trylock` 丢失次数无界。Rev.2 §6 的"worst ≤ 208 ms"应下调为"期望上界"，不得作为超时依据。

### 补丁
在 `publishStatus()` 的抽稀判断处引入"回执变更即强制发布"：

```cpp
    const std::uint64_t ack_now = hold_ack_.load(std::memory_order_acquire);
    const bool ack_changed = (ack_now != status_published_ack_);
    if (!ack_changed && ++status_tick_ < status_period_ticks_) return;
    status_tick_ = 0;
    if (status_pub_ == nullptr || !status_pub_->trylock()) return;
    if (ack_changed) status_published_ack_ = ack_now;   // 仅在真正发出后更新
```

- `status_published_ack_` 只在 `trylock()` 成功后更新 ⇒ 丢失那一拍下个 tick 仍会重试，**不会丢失强制发布**。
- 非回执周期仍按 10 Hz 发布，状态带宽不变。
- `status_published_ack_` 只在 RT 线程（`publishStatus()` 唯一调用上下文）读写 ⇒ 无数据竞争。

### 补丁后的预算
`8（drain）+ 8·(m+1)（发布重试）+ 1（DDS）+ 8（executor tick）`
- `m=0` → **≈17 ms**
- `m=1` → ≈25 ms
- 300 ms 可覆盖 **m ≈ 34** 次连续 `trylock` 丢失 ⇒ 裕量 ≥ 12×。

### 影响的测试
- **T-H7** 判据改为：`nominal ≤ 25 ms`、`worst ≤ 300 ms`，并要求 R1a 实测 100 次取最大并记录 `trylock` 丢失次数（可由消息间隔推断）。
- 新增 **T-H15**（同拍优先级）与 **T-H16**（重试语义，见 P-2）。

## P-2 重试语义：`result==2` 不等于"未冻结"

### 问题（核查报告 §5）
Q3 的"有界确认 + 重试"与 B-3-3 的单槽 CAS 组合出一个歧义：

1. 执行器发 `seq=7` → 控制器接受并 `hold`（L3 已成立）→ 回执因 `trylock` 丢失；
2. 执行器超时，用 **同一个** `seq=7` 重试 → 槽已空、CAS 成功；
3. 控制器此时 `state==Hold` ⇒ `ok=false` ⇒ 回执 `result=2`；
4. 若执行器把 `result=2` 读成"请求被拒绝 ⇒ 未冻结"，就会在**实际已冻结**的情况下 abort。

这是**假阴性**（fail-safe 方向），但会造成可复现的误中止，且使 L3 无法达成。

### 补丁（执行器侧判定规则，无需改控制器）
执行器对"`result != 1`"的处理必须分两步：

```
收到 hold 回执后：
  if (result == 1)                         → L2 成立，继续等 L3
  else if (state == "HOLD"
           && hold_origin == "executor"
           && hold_request_seq >= my_seq)  → 视为 L3 已成立（回执丢失或已被后续请求覆盖）
  else                                     → 真正被拒（Idle/Complete/Abort/Fault/已由控制器自身冻结）
```

- `>=` 而非 `==`：允许"我发出的请求被后续请求先行消费"的情形（单槽下 seq 单调，语义等价）。
- **必须同时满足 `hold_origin=="executor"`**：若 origin 是 `controller`，说明控制器是因自身安全层冻结，此时执行器的请求确实"未被应用"，不得算成功（否则会把安全事件的归因吞掉）。
- 重试必须**换新 `seq`**（避免与 §4.6 的"`Hold` 期间 `refused`"互相干扰），并由执行器记录"曾用过的 seq"用于 `>=` 比较。

### 影响的测试
- **T-H16**：注入一次回执丢失（测试侧丢弃第一条含 `hold_request_seq==7` 的状态），执行器必须仍能达成 L3（不得 abort）；再把 `hold_origin` 改成 `controller` 后必须 abort（负控制）。
- **T-H5** 保持：`Hold` 期间新 `seq` ⇒ `result==2`（控制器行为不变）。

## P-3 `seq` 回绕与 0 保留（不新增设计，明确实现约束）

- `next_seq()`：`seq = (seq == 0xFFFFFFFFu) ? 1u : seq + 1u`；**`0` 永不使用**（`0` 表示"无请求/无回执"）。
- 回绕时 `>=` 比较语义失效 ⇒ 执行器在检测到 `seq` 回绕（自己的计数器归 1）时，**清空已用 seq 记录**并重新开始；同时该情形 497 天才会出现，R1a 只做单元测试（T-H11）。
- 控制器侧无需变更：CAS 只依赖 `0` 与"非 0"。
