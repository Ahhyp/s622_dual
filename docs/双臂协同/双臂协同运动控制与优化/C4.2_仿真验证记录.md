# C4.2 仿真验证记录：规划算法 + 轨迹跟踪 + 保持相对距离

> 日期：2026-10-14
> 目的：把 C4.2 的规划结果真正接到 Gazebo 上，同时量化 C2.9b 遗留的
> "Gazebo 里相对位姿误差尚未量化"。
> 代码：`analysis/send_handover.py`、`src/c42_handover_target_main.cpp`、
> `launch/c42_handover_sim.launch.py`、`config/c42_handover_sim_controllers.yaml`
> 结论：**规划算法在仿真里跑通了**；轨迹跟踪与保持相对距离两项表现良好；
> **顺带发现 JTC profile 目前是坏的**。

---

## 一、必须先说清的前置事实

**C4.2 的 `dual_arm_pose_optimization` 是纯离线分析** —— 只有库和 CLI 探针，
**没有 ROS 节点、不发布任何话题**。所以它不会自动出现在仿真里，需要一座桥：

```
C4.2 推荐交接位 T_O → IK → q12 → FollowJointTrajectory → Gazebo
                   ← 用同一套 C4.2 库对实测关节角反算，与预测对比
```

本记录做的就是这座桥，以及三项测试。

## 三、测试 1：静态保持（无 sweep）

两臂静止在对称位形 `[0.5, −1.05, 1.05, −1.05, −0.8, 0]`，
1500 帧内 `^L T_R` **标准差精确为 0**，`|^L T_R| = 1.4055 m`。

⚠️ **这个结果没有信息量**：命令目标就是当前位姿，QP 无事可做。
只证明控制器不破坏稳定性。真正有意义的是测试 2。

## 四、测试 2：sweep 闭环运动（相对目标 ±60 mm / 4 s 正弦）

| 指标 | 结果 |
|---|---|
| **轨迹跟踪保真度** | 拟合幅值 **60.38 mm** / 命令 60 mm = **100.63%** |
| 实测峰峰 | **120.76 mm** / 命令 120 mm |
| **周期误差** | 拟合 **4.007 s** / 命令 4.000 s = **+0.18%** |
| **跟踪残差** | RMS **58.9 µm**，max 134.5 µm（幅值的 **0.097%**） |
| **未命令 y 漂移** | 范围 **0.16 mm**，std 0.056 mm |
| **未命令 z 漂移** | 范围 **0.054 mm** |
| **相对姿态漂移** | 测地角 max **0.035°**，std 0.0025° |
| 关节 | max \|Δq\| 0.066 rad，最活跃 `right_j1` |

**结论：两项都很好** —— 保持精度到亚毫米与 0.03°，跟踪残差 0.1%。
拟合出的周期 4.007 s **反过来独立印证了 RTF ≈ 0.489**。

### 口径说明（三条，必须随数字一起给）

1. 残差 58.9 µm 是**实测对最优拟合正弦**的偏差，度量的是"非正弦畸变"
   而非对命令参考的绝对误差。但幅值 100.63% + 周期 +0.18% 已说明系统性误差极小。
2. sweep 是**控制器内置的测试激励**（作用在*相对目标*上），不是外部轨迹输入；
   QP 控制器不接受外部轨迹。
3. 记录时踩了两个坑（已修）：
   - 第一版用 `rclcpp::Time` 相减，header stamp 是 `RCL_ROS_TIME`、无 sim time 的
     节点时钟是 `RCL_SYSTEM_TIME`，直接抛 `can't subtract times with different
     time sources [1 != 2]` → 改成原始 int64 纳秒相减；
   - `ofstream` 默认 6 位有效数字会把 1.79e9 的秒级时间戳抹成常数 →
     已设 `setprecision(12)` 并改为记录相对时间。

## 五、★ 发现：JTC profile 目前是坏的（C2.9b 遗留坐实）

启动 `ros2 launch gz_launch s622_dual_arm.launch.py` 后，臂控制器激活失败：

```
[resource_manager]: Not acceptable command interfaces combination:
[controller_manager]: Could not switch controllers since prepare command mode switch was rejected.
[spawner_left_arm_controller]: Failed to activate controller : left_arm_controller
```

**根因**：运行中的机器人只暴露 **position** 命令接口
（`left_j1/position [available]`，没有 `left_j1/position` 之外的选项），
而 `s622_moveit_config/config/dual_arm_controllers.yaml` 里臂 JTC 声明的是
`command_interfaces: [velocity]` → 接口不匹配，激活被拒。

这正是规划文档里记的 **C2.9b 遗留**："JTC↔QP profile 的互斥切换测试
（当前是'两套 launch 二选一'，没有自动化切换验证）"。它现在不是"没验证"，
而是**JTC 这一路已经跑不起来了**。

**未解的一致性问题（如实记录）**：用 `load_xacro` 单独复现 launch 的
xacro 调用时，`arm_command_mode` 的行为与运行结果**对不上**：

| 复现方式 | 生成的臂命令接口 |
|---|---|
| `load_xacro(..., arm_command_mode='position')` | **16 position**（正确） |
| 同样调用 + `arm_position_gain` + `controllers_yaml` | 16 position |
| **实际 spawn 出来的机器人** | **12 velocity + 4 position** |

也就是说 launch 里传的 mapping **没有按预期生效**。本记录**不掩盖这一点**，
它是下一步要查的（怀疑与 `MoveItConfigsBuilder` 的 robot_description 生成路径
或 gz_ros2_control 的配置装载有关）。

**本记录的绕行方案**（不修改任何已有文件）：在 C4.2 包里新建
`launch/c42_handover_sim.launch.py` + `config/c42_handover_sim_controllers.yaml`，
按**实测暴露的接口**（velocity）配臂 JTC（`p=100, d=1`），
手动 spawn 后两个臂控制器 **Configured and activated** ✅。

## 六、测试 3：C4.2 规划结果在仿真里执行

### 目标（C4.2 的最终推荐，S6 修完尺度缺陷后的 P95/V1 解）

```
p_O = [0.079164, −0.228536, 0.165815]   ‖δθ‖ = 10.0°
C4.2 预测：S4 可行、arm_arm 0.033658 m、arm_proximal 0.216672 m、joint_margin 1.138254 rad
```

### 第一步：位姿 → 关节目标（`c42_handover_target`）

```
S4 collision-free : yes        pair attempts : 1
FK 验证：物体位置误差 0.000000 µm，姿态误差 0.000000 deg，^L T_R vs T_rel^B = 0.000000
→ PASS：目标是 S4 可行的，且 FK 精确复现
```

### 第二步：发给 Gazebo（`send_handover.py`）

两臂从 home `[0.5, −1.05, 1.05, −1.05, −0.8, 0]` 出发，**实际到达 C4.2 目标位形**：

| | 最大关节误差 |
|---|---|
| 左臂 | 1.48°（`left_j6`） |
| 右臂 | 1.52°（`right_j4`） |
| **双臂** | **0.02655 rad = 1.52°** |

### 第三步：用同一套 C4.2 库反算实测位形，与预测对比

```
物体位置误差 : 7.79 mm   (Δ = [0.92, 5.68, −5.25] mm)
物体姿态误差 : 2.35 deg

净空          实测           C4.2 预测
arm_arm       0.042008 m    0.033658 m     ← 实测反而更安全
arm_proximal  0.215383 m    0.216672 m
joint_margin  1.137259 rad  1.138254 rad

S4 collision-free at the achieved pose: yes
```

### ★ 结论

**规划算法在仿真里跑通了。**
- 规划本身**精确**：FK 验证 0.000000 µm；
- 仿真执行后**仍然 S4 无碰撞**，净空甚至比预测更好；
- 7.79 mm / 2.35° 的物体位姿偏差**完全来自伺服稳态误差**（关节 1.52°），
  **不是规划误差**；
- `joint_margin` 实测 1.1373 vs 预测 1.1383 —— 与 S6 报的 +47.4%（相对 M4 基线）
  在仿真里成立。

## 七、复现

```bash
# 1) 规划：把 C4.2 推荐位姿变成关节目标
./build/dual_arm_pose_optimization/c42_handover_target --json /tmp/handover_target.json

# 2) 仿真（C4.2 自带的 position/velocity 适配 profile）
ros2 launch dual_arm_pose_optimization c42_handover_sim.launch.py gui:=true

# 3) 发送并测量
/usr/bin/python3 src/dual_arm_pose_optimization/analysis/send_handover.py \
    --target /tmp/handover_target.json --move-s 6 --settle-s 4

# 4) 用同一套库反算实测位形
./build/dual_arm_pose_optimization/c42_handover_target --verify-q12 "<实测 12 关节角>"
```

> 注意：步骤 2 之后若臂控制器未激活，按 `config/c42_handover_sim_controllers.yaml`
> 手动 spawn（见 §5）。

## 八、边界

1. **7.79 mm 不是精度上限**：JTC 增益（`p=100, d=1`）是我为这次测试临时选的，
   没有调优；稳态误差可通过提高增益或加积分项压下去。
2. **`send_handover.py` 的动作结果码报了 −999**：轨迹确实执行到位（关节实测已到位），
   但我的 `get_result_async` 等待超时了（仿真慢，RTF≈0.4）。
   **动作是否 SUCCESSFUL 未被独立确认**，这一点如实标注。
3. **未做真规划器验证**：C4.2 的 S4 仍是静态可行判据，仿真里也只是"能到位、无碰撞"，
   **没有验证"从当前构型无碰撞到达"**（S5 的线段可行性/真规划器对照仍是待办）。
4. **未验证保持相对距离在"到达 C4.2 位姿后"的持续表现**：测试 2 的 sweep 是在
   **home 位形**下跑的，不是在 C4.2 交接位形下。两者未合并测试。
5. **`/clock` 未被监控节点收到**（`use_sim_time` 未生效），已用 header stamp 绕过。
6. **Q1–Q4 未确认**，物体是参数化盒，Baseline B 是 `provisional_rebuilt`。
