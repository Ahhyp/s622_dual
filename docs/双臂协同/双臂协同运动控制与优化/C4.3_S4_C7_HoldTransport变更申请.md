# C7 变更申请：执行器 → 控制器的主动 HOLD 通道

> 变更编号：**C7**（对应 `C4.3_S4_W2-W3双轨门禁矩阵.md` 的 B-4 / P0）
> 状态：**申请中，未实施**。本文件只做设计、影响分析与最小面提议。
> 约束：`W2 = BLOCKED`、`W3 = IN PROGRESS`（R1 完成）；`C7` 获批前**不改控制器接口契约**；
> 本轮**未**修改 `src/dual_arm_qp_controller/` 任何文件、未提交/推送/暂存/清理。

## 0. 结论

B-4 的准确表述是：**控制器能被"它自己"停下来，但执行器没有请求它停下来的通道。**
现有唯一的向上通道是 `~/abort_transport`，而 ABORT 是终止性状态（必须重新 `start_transport`），
不满足"协同 HOLD 后可 RESUME"的语义。

建议以**最小附加面**补齐：新增 `HoldTransport.srv`（上行请求）+ `TransportStatus` 追加 3 个字段（下行回执），
RT 侧增加 **9 行**、不改动 W1 已有的 4 条命令分派。总改动约 **50 行、0 处删除既有语义**。

## 1. 现状（只读核对，带行号）

| 事实 | 位置 |
|---|---|

| `transport_->hold()` 由控制器**内部**调用（E1 越限、E7 臂距、E8 心跳、E6 近 π、求解失败等） | 同文件 `:750`（E8）、`:765`（E1）、`:214` 等 |

| 执行器侧当前兜底：超时后直接 `~/abort_transport` | `src/dual_arm_transport_executor/src/executor_node.cpp`（`abortController`） |

**因此**：R1 的"HOLD + 观测 + 违约升 FAULT + 超时 abort"是**兜底**，
它不能证明执行器具备主动冻结能力——`TransportStatus.state == "HOLD"` 无法区分
"控制器自己因碰撞停下"与"执行器请求它停下"。

## 2. 需求（C7 必须同时满足）

| 编号 | 需求 |
|---|---|
| N1 | 执行器能**请求**控制器冻结（不改轨迹、不终止任务） |
| N2 | 请求**可确认**：执行器必须能判定"我的请求被控制线程处理了"，而不是靠读 `state=="HOLD"` 猜 |
| N3 | **可区分来源**：`HOLD` 的发起者（控制器 E1–E8 vs 执行器）必须在状态里可读 |
| N4 | **可超时升级**：请求未被处理（队列丢失/被 abort 抢先）时执行器可判定并升级 |
| N5 | **幂等**：重复/延迟到达的请求不得二次改变状态 |
| N6 | **实时安全**：RT 路径零分配、零锁、零字符串解析 |
| N7 | **不重排既有语义**：`reset/resume/abort/start` 四条的优先级与行为不变 |

## 3. 候选方案

| 方案 | 上行通道 | 回执 | 判定 |
|---|---|---|---|
| **A** 新增 `HoldTransport.srv`（`reason` + `seq`）+ 状态加 3 字段 | 服务 | 状态回声（seq/result/origin） | **推荐** |
| B `std_srvs/Trigger` `~/hold_transport` | 服务 | 无 seq，无法幂等/对账 | 面最小但**不满足 N2/N5** |
| C 只加状态字段，复用 `~/abort_transport` | 无 | 无 | **拒绝**：abort 是终止性，违反 N1 |
| D 新增话题 `~/hold_request`（自定义 msg） | 话题 | 同上 | 比 A 多一个 msg 定义，且无请求-应答语义 |
| E 把 hold 塞进 `StartTransport.srv` | — | — | **拒绝**：语义混淆，且 start 会重置轨迹 |

**选 A 的理由**：它把"请求"和"回执"分开，请求走服务（能返回 `accepted=queued` 并携带 `seq`），
回执走既有的 10 Hz 状态（RT 侧只需两次 relaxed atomic 写）。B 省一个文件但丢掉了对账能力，
而 N2/N5/N4 全部依赖 `seq`。

## 4. 推荐方案的最小面（C7-A）

### 4.1 新文件 `src/dual_arm_qp_controller/srv/HoldTransport.srv`

```
# C4.3 S4 C7: cooperative HOLD request (executor -> controller).
# The controller freezes t_traj and q_cmd on the next control cycle and latches
# HOLD.  Recovery is ~/resume_transport (never automatic).  This is NOT abort:
# the latched trajectory is kept.
string  reason   # advisory, logged; the control thread latches a fixed code
uint32  seq      # caller-assigned, monotonic, 0 is reserved ("no ack wanted")
---
bool    accepted # true == queued (the verdict arrives in ~/transport_status)
string  message
```

### 4.2 `msg/TransportStatus.msg` 追加 3 个字段（**仅追加**）

```
# ---- C7: executor hold request acknowledgement ----------------------------
uint32  hold_request_seq     # seq of the last request the control thread handled (0 = none)
uint8   hold_request_result  # 0 = none, 1 = applied, 2 = refused (not running)
string  hold_origin          # "" | "controller" | "executor"
```

### 4.3 控制器（`dual_arm_qp_controller.{hpp,cpp}`）

- 成员：`std::atomic<uint32_t> hold_req_seq_{0};`、`std::atomic<uint32_t> hold_done_seq_{0};`、`std::atomic<uint8_t> hold_done_result_{0};`、`std::atomic<uint8_t> hold_origin_{0}`（0 none/1 controller/2 executor）+ 一个 `HoldTransport` 服务成员。
- 服务回调（executor 线程，非实时）：`hold_req_seq_.store(req->seq, relaxed)`；回 `accepted=true, message="hold queued"`。
- **RT 侧只加 9 行**，插在 `const bool transport_active = ...` **之后**（因此不与既有 `pending_cmd_` 分派重排，N7）：

```cpp
const uint32_t hseq = hold_req_seq_.exchange(0, std::memory_order_relaxed);
if (hseq != 0) {
    const bool ok = transport_active &&
                    transport_->state() == TransportState::Running;
    if (ok) {
        transport_->hold("hold_by_executor");   // keeps failure_code provenance
        hold_origin_.store(2, std::memory_order_relaxed);
    } else {
        hold_done_seq_.store(hseq, std::memory_order_relaxed);
        hold_done_result_.store(2, std::memory_order_relaxed);
        return return_type::OK;                 // nothing else to do this cycle
    }
    hold_done_seq_.store(hseq, std::memory_order_relaxed);
    hold_done_result_.store(1, std::memory_order_relaxed);
}
```

- 控制器**自身**发起的 hold（E1/E6/E7/E8/求解失败）在各自分支里加 `hold_origin_.store(1, ...)`，共 5 处各 1 行。
- `reset()` / `start()` 后清空：`hold_done_seq_=0; hold_done_result_=0; hold_origin_=0;`（各 1 行）。
- `publishStatus()` 里把三个原子量写进消息（3 行）。
- `TransportTask` 新增一个固定码 `kCodeHoldByExecutor = "hold_by_executor"`（1 行常量）。

**为什么不用 `pending_cmd_ = 4`**：`pending_cmd_` 是 `exchange` 消费的**单槽**，与 resume/abort 竞争会丢命令；
而且它在下发 `applyPendingStart()` 之前消费，与 start 同拍时顺序会变。独立原子量让 N5/N7 都成立。

### 4.4 语义表（状态 × 请求）

| 当前状态 | 请求 | 结果 | `hold_request_result` | 说明 |
|---|---|---|---|---|
| `Running` | hold | 置 `Hold`，`failure_code="hold_by_executor"` | 1 | `t_traj`/`q_cmd` 冻结 |
| `Complete` | hold | 忽略 | 2 | 已到终点，没有可冻结的推进 |
| `Idle` / `Hold` / `Abort` / `Fault` | hold | 忽略 | 2 | 不覆盖既有 `failure_code`（**关键**：`hold()` 是无条件的，必须由 `Running` 守卫） |
| `Hold`（控制器 E7） | hold | 忽略 | 2 | 保住 `collision` 这个原始归因 |
| `Hold`（执行器） | `~/resume` | `Running` | — | `hold_origin` 归 0 |

## 7. 回退

本变更**纯附加**：`HoldTransport.srv` + 3 个状态字段 + 9 行 RT + 5 处 origin 标记。
回退 = 删 srv、删 3 字段、删这 14 行；执行器侧回到"超时即 abort"的 R1 兜底。
**无数据迁移、无持久化、无 ABI 语义变更**（`TransportStatus` 是消息、`HoldTransport` 是服务，均无 C++ ABI 约束）。
