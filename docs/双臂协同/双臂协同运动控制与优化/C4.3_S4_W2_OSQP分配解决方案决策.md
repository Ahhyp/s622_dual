## 1. 背景

S4.1 W2 补验时按规划 §7 的 S4-T2“实时性预算”增加了逐周期探针（`TimingRecorder`），并对**纯数学层（L1：638 次 `solve()`）**做了分配计数。结果是：**每次 `solve()` 约 51 次堆分配**，因此 S4-T2 的“无 `malloc`”条款不成立。该阻断已由用户裁定为“实质性阻断，W2 暂不通过”（m08103：选 3）。本文给的是**怎么处理这个阻断**的可选路径与推荐，不替用户做决定。

## 2. 原始标准（原文）

| 出处 | 原文 | 说明 |
| --- | --- | --- |
| 规划 `:636`（§7 S4-T2） | 通过标准含“无 `malloc`（`heaptrack`/`valgrind --tool=massif` 抽查一次）” | **这是本阻断的唯一正式条款** |
| 规划 `:651`（§7 S4-T17） | 指标含“RSS 增长、句柄数增长”；通过标准含“RSS 增长 ≤ 1 MB；句柄数不增长” | **S4-T17 没有 malloc 条款**，分配条款不得挪到 S4-T17 判定 |
| 规划 `:6` | `[待标定]` = 尚无实测依据的建议值 | P99 ≤ 6.4 ms 属待标定，不是冻结标准 |
| 规划 `:911` 附近 | 冻结边界：不改 QP 数学核心、不改 S2 冻结基线 | 关闭 polish / 换求解器均落在该边界上 |

`技术推断`：条文的字面含义是“控制路径上不得出现堆分配”，而不是“不得出现第三方库内部的一次性分配”。条文没有区分这两种情形——这是本阻断需要**申请解释**的根源，而不是靠实测绕过。

### 3.1 实测数据（L1 纯数学，638 次 `solve()`，`t=0` 配置）

| 模块 | 次数 | 占比 | 每次 `solve()` |
| --- | --- | --- | --- |
| `libosqp.so`（第三方） | 21 075 | 74.94% | **33.0** |
| 测试仪表 `test_realtime_budget` | 4 988 | 17.74% | 7.8 |
| `libdual_arm_qp_core.so`（本项目胶水） | 1 980 | 7.04% | **3.1** |
| `libstdc++` / `libc` / 控制器库 | 69 + 6 + 4 | 0.28% | ≈0.1 |
| **明细合计** | **28 122** | — | 44.1 |
| 探针总数 `total_alloc` | **32 623** | — | **51.1** |

**闭合性（关键，必须如实披露）**：`28 122 ≠ 32 623`，缺口 **4 501 次（13.8%）**。原因不是“归属不明”，而是探针的取栈路径只覆盖 `malloc()`：`calloc/realloc/posix_memalign` 只递增计数器、不取栈。因此**上表的模块归属只代表 `malloc` 路径**，不能宣称“32 623 次已全部归属”。

- `已证明事实`：探针正/负控制成立（同一程序 N=0 → 9 次；N=1000 → 1009 次，delta 恰 1000，线性不丢不重）。
- `待验证假设`：若补齐 `calloc/realloc` 取栈后缺口主要由 `libosqp` 贡献（依据：QDLDL 的符号分解常用 `calloc`）。**未验证，不得当作结论引用。**

### 3.2 OSQP 内部调用栈（符号化后）

```
osqp_solve        libosqp+0x142ad   20.0 次/solve
  polish          libosqp+0x13419    4.0 次/solve
  init_linsys_solver_qdldl
                  libosqp+0x117d1    3.0 次/solve   （恰 3 × 638，与 n+m 相关的一次性分配同形）
  form_KKT        libosqp+0xc7d5     3.0 次/solve
```

上溯为：`dual_arm_qp::OsqpSolver::solve` ← `DualArmQp::solveImpl` ← `DualArmQp::solve(..., ObjectTaskRow const&)`。

`技术推断`：`polish` 每次都会重新做一遍求解后精化（含 QDLDL 因子重算），这是 OSQP 0.6.2 的既有行为，**不是本项目误用**；`osqp_update_*` 复用工作区已经是最优写法。

### 3.3 本项目胶水层剩余 3.1 次/solve 的位置

| 栈帧 | 次数/solve | 含义 |
| --- | --- | --- |
| `libdual_arm_qp_core.so+0x3412c`（`OsqpSolver::solve` 帧内） | 2.0 | 本项目代码，非 OSQP |
| `libdual_arm_qp_core.so+0x2244b`（`DualArmQp::solveImpl` 帧内） | 1.04 | 本项目代码，非 OSQP |

`技术推断`：这两处对应 Eigen 临时量 / 每拍新建的 `QpProblem` 容器（`C_ineq`、`d_ineq` 拷贝、`Vec12` 组装等）。**未逐个定位到源码行**（探针只给偏移，未做 DWARF 行号映射）——属 `未验证事项`，但它是**唯一可以不动数学就消除的部分**，且收益上限 3.1/51.1 = 6.1%。

### 4.1 A1 的关键论证（为什么它值得申请，以及它的代价）

- `已证明事实`：S4-T2（638 周期）`cycle_us` P99 = 376.9 / 388.6 / 409.0 / 430.0 / 524.2 µs（5 次运行），**max = 819.1 µs**；预算 6400 µs。分配没有把单周期耗时推到预算附近。
- `已证明事实`：时间分布由**调度器**主导，不由分配主导——`interval_max` 在空闲 WSL2 上也达 16.0 ms，且 `taskset` 绑核更差（核查报告 §A1 矩阵）。
- `技术推断`：33 次/solve 的分配若命中 `mmap`（大块）或 arena 扩展，最坏情况是**无界停顿**；这是 A1 必须付出监测代价的原因。
- `待用户批准事项`：接受“第三方求解器内部瞬时分配不计入 S4-T2 的 malloc 判据”，并同时接受 A4-c（或等效的堆预触碰）作为补偿措施。

## 5. 推荐方案

**首选 A1 + A4-a + A4-c（组合）**：

1. **A1**：把 S4-T2 的 malloc 条款改写为**分层判据**：
   - 控制路径上**本项目自有代码**零分配（可由探针机检，阈值 **0**）；
   - **第三方求解器**分配次数 ≤ **40 次/solve**（依据：实测 33.0，取 1.2× 余量；**该阈值属工程建议，需批准**）；
   - 分配**不得触发 `mmap`/`brk` 扩展**（判据：`/proc/self/status` 的 `VmPeak` 在 100 周期后不再增长），把“无界停顿”变成可机检的有界条件。
2. **A4-a**：消除胶水层 3.1 次/solve（先做 DWARF 行号定位，再预分配）。
3. **A4-c**：启动期预热堆（`mallopt(M_MMAP_THRESHOLD, …)` 或等价），并在 100 周期暖机后再开始计时。

**备选 A3**（若用户不接受“允许第三方分配”）：先做**只读数值研究**——用 `AdmmSolver` 复算 S3 的 638 周期，产出 `max|Δdq|` 分布与终点误差比；若落在新的 W2 判据内（见 `C4.3_S4_W2_ULP判据变更申请.md`），再申请切换。研究本身不改生产代码，但会改变数值证据链，**需单独批准**。

**明确不建议**：A2（0.6.2 无接口，只能打第三方补丁，超出授权边界）。

## 7. 未验证事项清单

1. 13.8% 缺口的实际模块归属（补齐 `calloc/realloc` 取栈后才可知）。
2. 胶水层 3.1 次/solve 的**源码行号**（需 DWARF 映射）。
3. `polish=false` 对 `dq` 的数值影响（本轮禁止实测；只作为决策输入建议）。
4. `AdmmSolver` 与 OSQP 的数值差异分布（A3 的前置研究，未做）。
5. 原生 Linux（非 WSL2）下分配是否仍为主要抖动源（见复测计划）。
