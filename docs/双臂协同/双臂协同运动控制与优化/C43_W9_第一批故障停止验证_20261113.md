# C43 W9 第一批：物理故障与停止链验证（2026-11-13）

本批已运行5类定向故障，验证了禁止松爪、实际控制器ABORT、两臂命令冻结和错误复位/重启拒绝。**这是W9第一批停止链证据，不是W9整体完成。** 实际单侧失持后出现约66°载荷倾斜；正向在线恢复、完整碰撞/跟随故障矩阵仍未完成。

## 1. 条件与范围

沿用已跑通的物理接触配置：无weld，四指原生驱动各5 N，2 ms物理步长、QP dt=8 ms，原抬升60 mm/横移120 mm轨迹。每轮创建独立IGN分区；新增`--ros-domain-id`，使用147/148/149，与当前GPU演示的146隔离。原42900、299501两轮无关headless仿真及GPU展示保留。

W8完整消融没有作为前置。本批只取故障判定需要的接触时间戳、状态/ACK、q_cmd、轨迹时间、动作结果和物体位姿。

## 3. 实测暴露的问题与修复

### 3.1 COMPLETE不等于控制器停止

首轮观测屏蔽`missing_support_r1`验证了释放守卫，但停止证据不足。代码复核发现生产TransportTask在COMPLETE时仍可求解/提交末态位置修正，原AbortRequester却可把COMPLETE当成already_complete确认停止。

本批新增显式停止语义重载，两个生产ROS适配器均传`complete_is_stopped=false`，必须观察真实ABORT；原单参数API仅保留历史“COMPLETE本来就停止”的bench兼容语义。未修改轨迹、QP求解器或故障阈值。新增两项回归，执行器包现为206项测试，0错误/失败/跳过。

`destination_absent_r1`已在修复后实测：没有目标支撑时，既不松爪，也不把控制器COMPLETE冒充冻结；真正ABORT后左右命令保持不变。

### 3.2 终态后的日志截断

为采集停止后证据，Python继续观测一秒。旧C++适配器在finish后仍追加证据，清理时可能留下半行。`carry_contact_loss_r1`仅在完整terminal_stop之后出现一条截断末行；独立停止窗口与terminal_stop完整，原文件保留。审计器只允许并明确告警这种“完整终态后的末尾半行”，终态前的任意坏行仍拒绝。

已修复为finished后不再写证据。随后三轮无此告警。审计器另做8项离线反例自测：假COMPLETE、缺ABORT确认、左右命令漂移、错误reset放行、停止后仍committed、终态前日志损坏等均能被拒绝；这些不计作物理实验轮次。

### 3.3 初始控制器就绪竞态

`stale_contact_r1`、`evidence_gap_r1`在故障触发前停在IDLE：动作服务出现时，控制器未必已active；原适配器只查询一次并永久缓存ready=false。已改为45墙钟秒内有界重查实际控制器归属。

两轮旧目录完整保留并标记“注入未到达，人工停止”，不计故障响应通过或失败。重跑r2均进入实际抓持/抬升，完成注入、停止和审计。

### 3.4 不能只靠父进程退出判断清理成功

清理复核发现evidence_gap_r1/r2的服务器仍在，原父进程已经退出。原先只发进程组SIGINT、等待8秒、再发TERM但不等待确认，可能在Gazebo退出卡住时留下孤儿。由于存在域148复用风险，evidence_gap_r2撤出合格结果；不是把它的原审计文件改成失败或删除。

新增精确world路径匹配，必要时TERM→KILL，并保存cleanup.json确认退出；不按通用Gazebo名称批量杀进程。旧两轮按精确路径清理后，以未使用的ROS域151运行evidence_gap_r3，重新完成抓持、注入、真实ABORT、一秒冻结窗口和拒绝重启。r3全部审计通过，cleanup.json的clean=true、remaining_world_pids为空；最终另查/proc确认本批W9活动进程为零。

## 4. 尚未解决的两个关键发现

### 4.1 失持后命令停止不保证载荷姿态

真实打开左夹爪后，控制停止有效，但停止观察末态的物体倾角约66.33°，中心z约0.31681 m。两臂命令冻结并未保持物体原姿态；右侧单独承担载荷的保持能力不能据此签发安全结论。

因此本批的`stopping_checks_passed=true`只针对检测/停止机制，`payload_retention_after_unilateral_loss_verified=false`。后续需要明确失持时的载荷处理策略和机械边界，不能直接reset后继续原轨迹。

### 4.2 执行器恢复后的HOLD过渡仍会升级FAULT

executor-pause中，控制器在executor进程仍暂停时已经HOLD/executor_lost，轨迹时钟冻结。进程恢复后，executor先因自身旧观测进入HOLD/stale_state，随后现有位级HOLD不变式发现“旧快照与停止确认前的q_cmd差异”，升级FAULT/hold_invariant_violated，最终仍收到真实ABORT。

这条路径证明没有自动继续，也证明现有协议尚不支持平顺的正向在线恢复。报告中的executor检测延迟约0.55 s包含进程被暂停的时间；不能拿它替代控制器独立心跳保护约116 ms的观测响应。

后续恢复工作必须区分“请求停止”“控制器确认已冻结”“允许显式恢复”，并继续核验抓持、位姿和资源归属。当前reset/start拒绝是实测结果，不冒充恢复成功。
