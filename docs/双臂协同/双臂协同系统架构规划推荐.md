# 三个方案
[双臂协同等级](./双臂协同等级.md)
## 方案 A: 用 plan_only + 双 controller 直接执行(L2)
绕开 move_group 的执行环节。arm_actions server 从 move_group 拿 plan,自己把 trajectory 发给 /left_arm_controller/follow_joint_trajectory action。
规划:走 move_group plan_kinematic_path service — 可并发(service 请求 MoveIt 内部并发处理没问题)

执行:走 left_arm_controller/follow_joint_trajectory action 和 right_arm_controller/follow_joint_trajectory action — 两个 controller 完全独立,天然并发

改动:moveit_planner.py(在 s622_arm_actions/utils/ 或类似位置)里执行那段,从"call execute_trajectory action"换成"call 各自 controller 的 follow_joint_trajectory action"。controller 名从参数读(arm_controller_action),配置里两侧不同。

## 方案B 把双臂当成一个 12 DOF 系统，一次规划一条联合轨迹 (L3, 勉强)

dual_arm planning group + 一次规划双臂 + 一条联合 trajectory + 一次执行
用于实现： L1：两臂同步运动 L2：共享空间内统一避碰 L3：双臂末端几何协同 / 非力控协作 
不用于实现：L4：力/位置闭环协同


不要这样： /left/move_to_pose → left_arm plan → left trajectory /right/move_to_pose → right_arm plan → right trajectory 
而是这样： 
```
/dual_arm/move_to_poses 
↓
dual_arm plan 
↓
RobotTrajectory: joint_names: left_j1 ... left_j6 right_j1 ... right_j6 
↓
一次 execute
```
trajectory 的时间轴是统一的：
```
t=0.0s left_q0 + right_q0 
t=1.0s left_q1 + right_q1 
t=2.0s left_q2 + right_q2 
...
``` 
所以两臂不是“碰巧同时动”，而是同一条联合轨迹里的两个子系统同步执行。


## 方案C 
必须要求机械臂有六维力传感器, 有六维力传感器后，接触阶段做实时力控/阻抗/导纳协同
L4；需要 F/T、实时 controller、安全监控
暂时不写这个方案。

# 
一般社区里的推荐做法可以概括成一句话：

**双臂系统不要只有一种运动入口，而是分层：任务层调度、MoveIt 做非接触规划、ros2_control 做执行/实时控制，中间必须有一个 MotionCoordinator/资源仲裁器。**

也就是：

```text
Task / BT / MTC
    ↓
MotionCoordinator / Scheduler
    ↓
A. 单臂独立运动
B. 双臂联合轨迹
C. 力控/接触协同
    ↓
ros2_control controllers
    ↓
Gazebo / 真机
```

---

# 1. 社区常见的基础结构

## 统一 robot model

双臂一般放在**同一个 URDF / SRDF / PlanningScene** 里，而不是两个完全互相不知道的机器人模型。

典型 SRDF group：

```text
left_arm
right_arm
dual_arm / both_arms
left_hand
right_hand
```

MoveIt 官方 dual-arm 教程也是这个方向：给左右臂加 prefix，配置多个 planning group、kinematics、controller，并让 MoveIt 能看到完整双臂系统。([MoveIt][1])

社区里也有类似经验：多个机械臂应放在同一个 URDF 里，每个 arm 有自己的 group；如果需要同步运动，再定义一个 combined group。([GitHub][2])

所以你现在“单 `move_group` + 双臂同一个 robot_description + left/right/dual group”的方向是对的。

---

# 2. 社区常见的三类运动模式

## 模式 A：独立任务并发

用于：

```text
左臂在左侧工作
右臂在右侧工作
两者空间基本不重叠
追求吞吐
```

常见做法：

```text
left_arm plan  → left controller
right_arm plan → right controller
```

这类动作可以绕开 `move_group` 的全局执行队列，直接发给各自 `FollowJointTrajectory` controller。`JointTrajectoryController` 本身就是 ros2_control 里常用的轨迹执行器，接收带时间戳 waypoint 的 joint trajectory。([ROS控制][3])

但社区里一般不会让它“无脑并发”，而是加 scheduler / lock，至少保证两臂不会同时进入共享空间。

---

## 模式 B：双臂联合规划

用于：

```text
handover
双臂靠近中心区
同步撤离
双臂共享空间避碰
非力控协作
```

常见做法：

```text
dual_arm planning group
    ↓
一条包含 left_joints + right_joints 的 RobotTrajectory
    ↓
MoveIt 执行时拆给 left/right controllers
```

这就是比较标准的 L2/L3 做法。
社区里对于“两个 group 同步动”的常见建议也是定义一个包含双臂的 `dual_arms` group，让 MoveIt 生成一条联合轨迹，再由执行层拆给对应 controller。([Google Groups][4])

这种方式的优点是：规划时 MoveIt 能在同一个 PlanningScene 里考虑左右臂自碰、环境碰撞和共享空间。

缺点是：不适合大量异步独立任务。所有东西都走 `dual_arm` 会变重，12 DOF 规划也可能比 6 DOF 单臂规划更慢、更不稳定。

---

## 模式 C：接触力控协同

用于：

```text
双臂共同搬物体
一臂扶持一臂装配
插入 / 压装 / 恒力接触
```

这类不是 MoveIt 的强项。社区里通常把 MoveIt 用在**接触前规划**，接触后切到 ros2_control 的实时控制器，例如 admittance / impedance / 自定义 cooperative controller。ros2_control 的 controller manager 负责 controller 生命周期、切换和硬件接口管理；这正是做实时控制更合适的位置。([ROS控制][5])

如果没有腕部 F/T 或可靠 torque feedback，就不要把它叫真正 L4。

---

# 3. 社区越来越认可的关键组件：Scheduler / MotionCoordinator

多臂系统里，最容易出问题的不是“能不能发 trajectory”，而是：

```text
谁现在拥有左臂？
谁现在拥有右臂？
谁能进入 shared zone？
当前 active trajectory 会不会和新 trajectory 撞？
controller 是否已经被别的模式占用？
```

MoveIt 社区关于 simultaneous / asynchronous trajectory execution 的工作也正是围绕这个问题：新 trajectory 进入时要检查 controller 是否可用、是否会和 active trajectory 或当前 PlanningScene 碰撞，然后才允许执行。([MoveIt][6])

相关论文也把多臂异步执行的核心归纳为：central scheduler + continuous collision checking，让多个 robot/arm 能独立执行，同时维持碰撞安全。([arXiv][7])

所以社区比较成熟的结构不是：

```text
每个 action server 自己想发就发
```

而是：

```text
所有 motion request → MotionCoordinator → 决定走 A/B/C → 执行
```

---

# 4. Task 层常见做法

如果只是简单 pick-place，用 BT 很常见。
如果任务变复杂，比如 grasp、handover、place、retreat、recovery 多阶段耦合，MoveIt Task Constructor 也常用。MTC 官方定位就是把任务拆成多个 stage，每个 stage 解决一个子问题，并在 stage 之间传递 PlanningScene / solution hypothesis。([MoveIt][8])

典型结构是：

```text
BT / MTC / TAMP
    ↓
Decide:
  independent task → A
  cooperative non-contact task → B
  contact force task → C
```

你的项目已经用了 BT.CPP，这没问题。后面如果 handover 流程复杂，可以在 BT 里调 action，也可以逐步引入 MTC 做 grasp/handover stage 生成。

---

# 5. 工业/工程里常见的最终结构

比较推荐的最终架构是：

```text
BT.CPP / Task Planner
    ↓
MotionCoordinator
    ├── A: IndependentArmExecutor
    │       left_arm / right_arm controller_direct
    │
    ├── B: DualArmTrajectoryExecutor
    │       dual_arm MoveIt planning + one joint trajectory
    │
    └── C: CooperativeForceController
            F/T feedback + admittance/impedance
```

资源规则：

```text
A-left 申请 left_arm_lock
A-right 申请 right_arm_lock
B 申请 left_arm_lock + right_arm_lock
C 申请 left_arm_lock + right_arm_lock + cooperative_mode_lock
shared zone 动作额外申请 shared_zone_lock
```

这就是“多模式共存 + 中央仲裁”。

# 6. 不推荐的做法

## 1. 两个独立 move_group 各管一只手臂

不是绝对不能做，但一般不推荐作为共享空间双臂系统的主方案。

问题是：

```text
左 move_group 不知道右臂未来轨迹
右 move_group 不知道左臂未来轨迹
共享 PlanningScene / robot_description / tf namespace 容易麻烦
```

社区经验里也提到，完全 namespaced 的多 MoveIt 实例会比较 fiddly，甚至可能不稳定，而且两个实例互相不知道对方，这对双臂避碰是问题。([GitHub][2])

## 2. 所有动作都走 dual_arm

这太保守，吞吐低。

左臂在左边工作、右臂在右边工作，本来可以并发；如果全都走 `dual_arm`，很多独立任务会被迫整体规划、整体等待。

## 3. 所有动作都走 controller_direct

这又太激进。

如果双臂进入 handover 区，两个独立 trajectory 彼此不知道对方未来运动，只靠当前 PlanningScene 不够安全。

## 4. 没有仲裁器

这是最危险的。

```text
MoveToPose
Servo
DualArmMove
手动 action send_goal
```

如果都能直接抢 controller，就会出现 controller goal 抢占、BT 状态错乱、急停恢复困难。

按你当前项目阶段，最合理的是：

```text
  先实现左右臂真正独立并发

中期：
```


# 8. 一句话总结

**社区常见推荐不是单一方案，而是分层多模式：统一双臂 robot model + 单 MoveIt PlanningScene；独立任务用 decoupled execution，协作/共享空间用 dual_arm centralized planning，接触力控用 ros2_control 实时 controller；中间必须有 scheduler / MotionCoordinator 做资源锁、controller 切换和安全仲裁。**

# 将来要引入 VLA 怎么做？

一般现代 VLA / 具身智能系统，**不是把 ROS、MoveIt、controller 全部替掉**，而是在你现有机器人系统上方加一层“学习型决策/策略层”。

推荐架构大概是这样：

```text id="4byfbe"
用户语言指令 / 任务目标
        ↓
VLM / LLM / VLA 高层理解
        ↓
任务分解 / 技能选择 / 参数生成
        ↓
MotionCoordinator 资源仲裁
        ↓
A / B / C 执行模式
        ↓
MoveIt / Servo / ros2_control / 真机
```

也就是说，VLA 一般不直接裸控电机，而是和传统机器人栈结合。

---

# 1. 现代 VLA 常见两种路线

## 路线 1：端到端 VLA Policy

输入：

```text id="sysil5"
图像 + 语言指令 + 机器人状态
```

输出：

```text id="5ceo7m"
末端位移 / 关节动作 / action chunk
```

代表：

```text id="s0ttbt"
OpenVLA
π0 / pi-zero
GR00T N1
RT-2 类模型
```

OpenVLA 是 7B 参数开源 VLA，训练在大规模真实机器人演示数据上，用视觉编码器 + LLM 输出机器人动作。论文中提到它训练于约 970k 条真实机器人演示，并支持 fine-tune 到新任务。([arXiv][1])

π0 则是 Vision-Language-Action flow model，用预训练 VLM 继承语义能力，再通过 flow matching 生成机器人动作。([arXiv][2])

GR00T N1 也是类似方向：视觉语言模块负责环境理解，后续 diffusion transformer 生成实时动作。([arXiv][3])

这种路线先进，但对数据、算力、安全验证、真实机器人部署要求很高。

---

## 路线 2：VLA / VLM 做高层，传统系统做执行

这是目前工程上更稳的路线。

VLA 不直接控制关节，而是输出：

```text id="8uyffr"
选择哪个技能
目标物体是谁
目标位姿在哪里
调用 left_arm 还是 right_arm
是否需要 dual_arm
是否进入 handover 流程
```

然后仍然由：

```text id="38hjxr"
MoveIt 负责规划
Servo 负责小范围视觉伺服
ros2_control 负责执行
MotionCoordinator 负责资源锁
BT 负责流程和 recovery
```

这条路更适合你当前项目。




## 阶段 V2：VLA 做局部视觉伺服 policy

比如让 VLA 只控制很小范围：


输出不是完整轨迹，而是 bounded delta：


```text id="7ylod8"

最大位移

碰撞检查
```

这样比直接让 VLA 控整条轨迹安全得多。

现代 VLA 研究通常强调大规模、多 embodiment 数据和 fine-tuning；OpenVLA 这类模型也强调可以在新环境上 fine-tune。([arXiv][1])

# 6. 关键原则

## 原则 1：VLA 不绕过安全层

不要让模型直接控制：

```text id="u1u2cc"
joint command
controller action
servo topic
```

除非经过：

```text id="w27s1b"
限幅
碰撞检查
资源锁
速度限制
急停监控
```

## 原则 2：先 skill-based，再 end-to-end

对你的项目，先做：

```text id="04m3jw"
VLA 选择技能
```

不要一上来做：

```text id="r9r18n"
VLA 直接输出连续 joint command
```

## 原则 3：保留 BT

BT 在具身智能里仍然很有用，因为它负责：

```text id="84m0gj"
可解释流程
失败恢复
安全 fallback
状态机
实验复现
```

VLA 负责“更聪明地生成/选择 BT 子树”，而不是完全替代 BT。

## 原则 4：所有运动仍然进 MotionCoordinator

无论是人写的 BT，还是 VLA 生成的任务，都必须走：

```text id="tg361r"
MotionCoordinator
```

否则 A/B/C 会抢 controller。
