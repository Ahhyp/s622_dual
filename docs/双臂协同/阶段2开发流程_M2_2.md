## 关键发现：xacro 现状与"双 CM"决策不匹配

你贴的 `robot_gazebo.urdf.xacro` 里 `gz_ros2_control` 插件在 **macro 外部**，全局只有一个实例；`<parameters>` 只读一份 YAML。而 xacro 的 macro 被调两次只会生成两个 `<ros2_control>` 块（两组硬件接口），全都挂在**同一个 controller_manager** 下。

也就是说,当前结构天然只支持**单 CM**。要走"双 CM + 双 namespace"必须把插件挪进 macro 内实例化两次,但 gz_ros2_control 同 model 下双插件的可靠性我不敢打包票（社区例子极少,`<ros2_control>` 块的归属过滤未明确文档化，风险高）。

**建议调整架构决策为"单 CM + 4 个前缀化 controller"**。理由：

| 项                        | 单 CM                                           | 双 CM                       |
| ------------------------- | ----------------------------------------------- | --------------------------- |
| M2.1 xacro 改动           | 零                                              | 需重构（有风险）            |
| M2.4 `/joint_states` 合并 | 免（JSB 单例直接发全局）                        | 需要合并节点                |
| `/tf` namespace remap 坑  | 免                                              | 需处理                      |
| controller 名             | `left_arm_controller` 等（名字前缀区分）        | `arm_controller`（ns 区分） |
| 双臂物理隔离              | 无（Gazebo 本就一个物理引擎）                   | 无（同上）                  |
| 真机迁移                  | 那时硬件驱动天然独立，自动就是双 CM，此处不影响 | —                           |

在 Gazebo 阶段，双 CM 的"隔离"其实是伪隔离（物理引擎共享）。真正需要双 CM 的场景是真机上两组独立 driver，那时候是被硬件强制拆的。仿真单 CM 是社区主流。

**你之前提示词里最初写的 `left_arm_controller` 命名（controller 名带前缀），恰好就是单 CM 方案对应的形态**。转了一圈回到起点。

下面就按单 CM 给M2.2。如果你坚持双 CM，说一声，我另给一版并把 macro 重构方案一并写出（但会告诉你哪里可能踩坑）。

## 常见坑

1. **`update_rate` 只能在 `controller_manager:` 段声明一次**。单 CM 下所有 controller 共享一个 update 循环。别在下面每个 controller 里也写 `update_rate`。

2. **finger joint 命名要跟 URDF 严格对齐**。你 URDF 里就是 `finger1_joint` / `finger2_joint`，前缀化后必须是 `left_finger1_joint`（不是 `left_finger_1_joint`、不是 `finger1_joint_left`）。V2 grep 步骤就是防这个。

3. **finger mimic 关系在 URDF 层做**。`hand_controller` 声明 2 个 joint 只是让 CM 都能写 command_interface；实际物理运动由 URDF `<mimic joint="left_finger1_joint">` 保证一致。gz_ros2_control 会自动镜像 mimic joint 的 command。别在 controller 里再做同步逻辑。

4. **YAML 参数解析器不支持 anchor/alias**（Humble 版 `rcl_yaml_param_parser`）。所以每组 gains 只能全展开写，不能 `<<: *base`。上面就是全展开。

5. **`cmd_timeout: 0.0` 必须保留**。Servo 会以 100–500Hz 连续发 trajectory，超时非 0 会因间隙触发 abort。M1.7 就踩过一次，这里继承。

6. **`joint_state_broadcaster` 名字不能带前缀**。它是 CM 层的单例，双臂共用。名字带前缀会造成 M2.4 里 move_group 找不到 `/joint_states`（或需要 remap，画蛇添足）。

7. **spawner 顺序**：JSB 要先 spawn（其他 controller 才有 state 可读）。`controller_manager/spawner` 一次传多个时是并行 spawn 的，为了稳可以拆两个 TimerAction：先起 JSB（period=8s），再起 arm/hand（period=12s）。M1.7 你这块已 OK，双臂同样处理。

8. **原 `ros2_controllers.yaml` 保持不动**。M1.7 launch 依然引用它、依然叫 `robot_arm_controller`。M2 完整跑起来后如果稳定，M3 阶段再考虑收敛为一份。

## 文件拆分（可选，若坚持"双份"）

如果非要按 side 拆文件：

* `left_arm_controllers.yaml`: 包含 `controller_manager:` 段（只声明 left 那两个 controller + JSB) + `left_arm_controller:` + `left_hand_controller:` 三节
* `right_arm_controllers.yaml`: `controller_manager:` 段（只声明 right 那两个 controller，不含 JSB，避免重复注册）+ `right_arm_controller:` + `right_hand_controller:` 三节

然后 `robot_gazebo.urdf.xacro` 顶层 plugin 段改成：

```xml
<plugin filename="gz_ros2_control-system" name="...">
    <parameters>$(arg left_controllers_yaml)</parameters>
    <parameters>$(arg right_controllers_yaml)</parameters>
</plugin>
```

gz_ros2_control 支持多`<parameters>`，参数会合并加载。但同一 key 在两份文件冲突时行为未文档化，风险点。我不推荐这么拆——**没实际收益,只是给自己找 bug**。真要拆等 M3 有明确需要再说。
